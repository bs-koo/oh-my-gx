# oh-my-gx

### 프로젝트 이해부터 개발·검증·PR까지.

프로젝트 지식 관리, 요구사항 정의, 설계·구현·리뷰·검증과 PR 생성을 지원하는 개발 워크플로.

**Claude Code · Codex 지원**

---

oh-my-gx는 프로젝트의 도메인 지식과 개발 규칙을 바탕으로 개발 업무를 수행하는 AI 플러그인입니다. 전문 에이전트와 스킬이 요구사항 정리부터 개발·검증·PR까지 지원합니다.

- **프로젝트 이해** — 도메인 지식·요구사항 정리, 코드 정책·변경 영향도 분석, 기술 부채 점검
- **기능 개발** — PRD 작성, 기술 설계, 구현계획 수립, 테스트 주도 개발(TDD)
- **품질 확인** — 코드·보안 리뷰, 교차 검증, 테스트·빌드 실행
- **결과 정리와 공유** — 리서치·문서 정리, 구조·변경사항 시각화, 커밋·PR 생성

## gx-work로 시작하기

**목표를 말하면, AI가 필요한 스킬을 연결합니다.**

`gx-work`가 요청과 프로젝트 상태를 파악해 필요한 스킬과 다음 작업을 연결합니다. 개별 스킬을 직접 실행해 필요한 업무만 맡길 수도 있습니다.

```text
oh-my-gx:gx-work로 사용량 조회에 엑셀 다운로드를 추가해줘.
기존 권한 정책은 유지하고 PR까지 올려줘.
```

AI가 기존 코드와 문서를 확인하고 필요한 스킬을 선택합니다. 결과와 다음 단계를 제안하며, **개발로 넘어가기 전에는 범위와 완료점을 확인받습니다.**

| 원하는 결과 | 이렇게 요청하세요 |
|---|---|
| 문서와 작업 정리 | “이 요구사항을 등록하고 작업을 나눠줘. 개발은 나중에 할게.” |
| 정책 확인 | “다운로드 권한 정책을 확인해줘. 코드는 바꾸지 마.” |
| 기능 개발 | “엑셀 다운로드를 추가하고 검증해줘.” |
| 작업 재개 | “아까 하던 작업 이어서 PR까지 올려줘.” |

## 시작하기

### Claude Code

Claude Code 입력창에서 설치합니다.

```text
/plugin marketplace add bs-koo/oh-my-gx
/plugin install oh-my-gx@oh-my-gx
```

프로젝트에서 처음 사용할 때 `/oh-my-gx:gx-setup`으로 환경을 설정하고, `/oh-my-gx:gx-work <요청>`으로 시작하세요.

### Codex

Windows PowerShell에서 설치합니다. Bash에서는 `codex.cmd` 대신 `codex`를 사용합니다.

```powershell
codex.cmd plugin marketplace add bs-koo/oh-my-gx
codex.cmd plugin add oh-my-gx@oh-my-gx
```

작업할 프로젝트 폴더에서 새 Codex 세션을 열고 **채팅창**에 요청합니다.

```text
oh-my-gx:gx-setup 스킬로 이 프로젝트를 준비해줘.
oh-my-gx:gx-work로 이 기획서의 기능을 구현하고 검증해줘.
```

`/skills`에서 설치된 스킬을, `/hooks`에서 보호 훅의 등록·신뢰 상태를 확인하세요. [설치·업데이트·문제 해결 →](docs/codex-guide.md)

## 동작 방식

**요청 → AI의 스킬 선택 → 결과·다음 단계 제안 → 사용자 결정 → 후속 작업**

1. **이해합니다.** 목표와 기존 코드·문서·진행 상태를 확인합니다.
2. **필요한 작업을 연결합니다.** 문서 정리는 `gx-context`, 정책 분석은 `gx-lens`, 외부 조사는 `gx-research` 등 필요한 스킬만 사용합니다.
3. **다음 단계를 확인합니다.** 개발이 필요하면 범위·관련 문서·완료점을 보여주고 TDD로 진행할지 묻습니다.
4. **계획하고 구현합니다.** `gx-tdd`가 PRD·설계·구체 구현계획을 작성합니다. 계획을 검토하고 현재 세션 중심 또는 구현 서브에이전트 방식을 선택하면 TDD로 개발합니다.
5. **검증하고 마무리합니다.** 코드 리뷰와 관련 문서 갱신 후 최종 검증합니다. 커밋·PR은 요청한 경우에 진행합니다.

**문서만 요청하면 문서에서 끝납니다.** `gx-context`는 도메인 문서와 작업 목록을 관리하고, 구체 구현계획은 `gx-tdd`가 맡습니다. 기존 자료와 유효한 결정은 재사용합니다.

명시적으로 선택한 **핵심 모드(core)**도 AC 작성 뒤 실제 대상 코드를 읽고 간단한 구현계획을 세웁니다. AC와 계획을 함께 검토·승인한 다음 TDD로 구현하며, 같은 계획의 유효한 실행방법 선택은 재사용합니다. 중요한 설계 판단이 필요하면 전체 모드 전환을 제안합니다.

Git으로 공유한 `.dev`에 관련 설계·결정이 있으면 후속 변경까지 대조합니다. 새 요구와 중요한 충돌이 있을 때 출처·시점·판단 차이를 제시하고 유지할지 변경할지 확인합니다. Git 기록 기여자와 실제 결정자는 구분합니다.

작업이 여러 개라면 `.dev/plan.md`에서 관리할 수 있습니다. `gx-work`에 “W01을 진행해줘”라고 요청하거나 `--work W01`로 작업을 지정하세요.

## 스킬 안내

**GX 스킬 16개 = 총괄 진입점 1개 + 전문 스킬 15개.**<br>
처음에는 `gx-work`로 시작하세요. 필요한 스킬을 알고 있다면 개별 호출도 가능합니다.

<a id="gx-work"></a>

| 총괄 스킬 | 역할 |
|---|---|
| **gx-work** | 요청과 진행 상태를 파악해 필요한 스킬을 연결하고, 다음 단계 제안·사용자 결정·작업 재개를 관리합니다. |

### 문서·분석

| 스킬 | 하는 일 |

| <a id="context"></a>**gx-context** | 도메인 지식·요구사항을 정리하고 작업계획표를 갱신합니다. |
| <a id="lens"></a>**gx-lens** | 코드 근거를 바탕으로 비즈니스 정책과 변경 영향을 분석합니다. |
| <a id="research"></a>**gx-research** | 도메인·기술·대안을 조사하고 출처와 함께 정리합니다. |
| <a id="tech-debt"></a>**gx-tech-debt** | 기술 부채를 진단하고 개선 우선순위를 제안합니다. |
| <a id="visualize"></a>**gx-visualize** | 명시적 요청에 따라 코드 구조·작업 흐름·변경 영향을 시각화합니다. [사용 가이드](docs/gx-visualize-guide.md) |

### 개발·검증

| 스킬 | 하는 일 |
|---|---|
| <a id="tdd"></a>**gx-tdd** | PRD·설계·구현계획부터 TDD 개발·리뷰·최종 검증까지 진행합니다. |
| **gx-red** | 구현에 앞서 실패하는 테스트를 작성합니다. |
| **gx-green** | 실패한 테스트를 통과시키는 최소 코드를 작성합니다. |
| **gx-refactor** | 동작과 테스트를 유지하며 코드 구조를 정리합니다. |
| **gx-verify** | 테스트·빌드 결과와 현재 변경의 일치를 확인합니다. |
| <a id="cross-review"></a>**gx-cross-review** | 요구사항·설계·검증 기록을 근거로 구현 결과를 교차 검토합니다. |

## 알아두기

- **요청한 범위까지 진행합니다.** 기본 개발 완료점은 검증입니다. PR 머지는 별도로 명시적으로 요청해야 합니다.
- **관련 테스트부터 실행합니다.** 변경 영향에 따라 범위를 정하고 유효한 실행 증거를 재사용합니다. 공통 설정·의존성이 바뀌거나 영향 범위가 불명확하면 전체 검증으로 확장합니다.
- **판단과 근거를 함께 전달합니다.** 중요한 선택의 이유·원문 위치·검증한 범위·남은 미확인 사항을 설명합니다. 문서의 사실과 추정을 구분하며 퀴즈나 추가 승인을 기본 절차로 강제하지 않습니다.
- **프로젝트 환경에 맞춥니다.** 빌드·테스트 명령은 `gx-setup`에서 설정합니다. SVN은 검증까지 지원하며 커밋은 직접 수행합니다.
- **설치 환경을 확인하세요.** 자연어 스킬 발견과 보호 훅 실행은 하네스·설치·신뢰 상태에 따라 달라집니다. 인식되지 않으면 스킬 이름을 명시하세요.
