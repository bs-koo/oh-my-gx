공통 진입과 개발 실행

AI가 연결하고,
큰 전환은 함께 결정합니다

gx-work가 필요한 조사·문서 작업만 선택하고 결과와 다음 단계를 보여줍니다. TDD 진입에 답하면 gx-tdd가 PRD·설계·구체 구현계획을 확정하고 실행 방식을 선택받아 개발합니다. 실제 결과를 문서에 반영한 뒤 최종 검증합니다.

  1. 01

    의도와 상태 파악

    원하는 결과, 기존 문서와 코드, 중단한 작업을 확인합니다. 필요한 조사·문서 스킬을 선택합니다.

    gx-work · 필요한 전문 스킬
  2. 02

    다음 단계 확인

    결과와 추천 작업을 보여줍니다. 개발이 필요하면 범위·관련 문서·종료점을 제시하고 실제 답변을 기다립니다.

    사용자 결정
  3. 03

    구체 계획과 개발

    gx-tdd가 PRD·설계·구현계획을 만듭니다. 계획 검토와 실행 방식 선택 후 TDD로 구현합니다.

    gx-tdd · 현재 세션 또는 구현 서브에이전트
  4. 04

    검증과 요청한 완료점

    리뷰와 문서 정합성을 확인하고 영향 범위에 맞게 검증합니다. 커밋·PR은 요청한 경우에 진행합니다.

    리뷰 · gx-verify · 커밋·PR
문서만 요청하면 문서에서 끝납니다.

gx-context는 도메인 문서와 작업 목록을 관리합니다. 구체 구현계획은 gx-tdd가 맡습니다. 이미 유효한 문서와 결정은 다시 만들거나 묻지 않습니다.

gx-tdd 전체 실행 흐름 · 핵심 모드(core)에서도 TDD와 검증 기준은 유지합니다

개발 업무별 전문 스킬

문서·분석, 개발·검증, 결과 정리와 공유를 담당하는 17개 전문 스킬을 제공합니다. gx-work로 필요한 스킬을 연결하거나 개별 스킬을 직접 호출할 수 있습니다.

도메인과 작업 계획

gx-context · 도메인·요구사항 관리

문서·대화·코드에서 도메인 지식과 요구사항을 정리하고, 변경된 요구사항을 원장과 작업 계획에 함께 반영합니다. 후속 작업은 관련 컨텍스트와 결정 근거를 참조합니다.

  • 도메인 정리 — 용어·정책·아키텍처와 출처를 기록
  • 계획 동기화 — 요구사항 변경을 작업 단위와 의존성에 반영
  • 준비 상태 구분 — 실행 가능한 작업과 미정·차단 항목을 표시
  • 진행도 갱신 — Git 이력과 PR 근거로 상태를 동기화
context/사용량분석/
context/사용량분석/ ├─ README.md # 도메인 개요 ├─ PROJECTS.md # 저장소 매핑 ├─ glossary.md # 용어 사전 ├─ architecture.md # 구조 요약 ├─ status.md # 요구사항 진행도 └─ 집계/README.md # 주제별 정책
개발 실행

gx-tdd · 구현계획과 테스트 주도 개발

수용 기준을 테스트로 확인하고 기능을 구현합니다. 실패 테스트 작성, 최소 구현, 코드 정리를 진행한 뒤 문서와 실제 결과를 대조하고 최종 검증합니다.

  • 수용 기준 — Given-When-Then으로 관찰 가능한 동작 명시
  • 테스트 우선 — RED 작성과 구현의 역할을 분리하고 실패 근거 확인
  • 검증 범위 선택 — 변경 영향에 맞는 테스트를 실행하고 근거가 부족하면 전체 검사로 확대
  • 검증 근거 재사용 — 같은 실행에서 코드·명령·설정·범위가 일치할 때만 사용
  • 핵심 모드(core) — 단계를 줄여도 수용 기준·TDD·verify 유지
  • Ralph 전환 — 명시 요청 시 기준선 확인 후 무인 반복 경로로 인계
RED · GREEN · REFACTOR
RED 실패 테스트 작성 ▸ test FAILED · 의도한 실패 GREEN 통과 최소 구현 ▸ test PASSED ✓ REFACTOR 통과 상태에서 정리 ▸ test PASSED ✓ verify 현재 변경의 근거 확인
✻
gx-red · 실패 테스트 작성

요구사항을 테스트로 표현하고 의도한 실패를 확인합니다. RED 단계를 단독 실행할 때 사용합니다.

✻
gx-green · 최소 구현

확인된 실패 테스트를 통과시키는 최소 코드를 작성하고, 요청 범위를 벗어난 구현을 점검합니다.

✻
gx-refactor · 코드 정리

테스트 통과와 기존 동작을 유지하며 중복과 복잡한 구조를 정리합니다.

✻
gx-verify · 변경 검증

현재 변경의 테스트·빌드 결과와 실행 근거를 확인해 완료 및 커밋·PR 진행 가능 여부를 판단합니다.

무인 반복

gx-ralph · 반복 개발 준비

승인된 요구사항을 수용 기준 원장으로 정리하고 외부 러너의 반복 실행을 준비합니다. 반복 세션은 수용 기준을 한 건씩 구현·검증·커밋하고, 진행 근거를 파일과 Git 이력에 기록합니다.

  • 명시적 진입 — gx-ralph 직접 요청 또는 gx-work·gx-tdd에서 Ralph 실행 요청
  • 반복 제어 — 횟수·시간·무변화·무진전·중복 실행을 감시
  • 검증 기준 유지 — 테스트 실패나 필요한 커밋 권한 부재 시 진행 중단
  • 내부 실행 스킬 — gx-ralph-iterate는 러너가 반복 한 회를 수행할 때 사용
  • 진입 조건 — Git 작업 브랜치·요구사항·검증 명령 등 실행 준비 상태 확인

분석 · 협업 · 글쓰기

분석과 협업을 지원합니다

정책·기술 조사, 교차 검토, 환경 설정, 커밋·PR 작성과 문장 교정을 목적에 맞게 요청할 수 있습니다.

◆

gx-lens · 비즈니스 정책 분석

정책별 파일·라인 근거와 확인 수준을 표시하고, 현재 구현과 요구사항의 차이를 설명합니다. 조회 후 종료하며 변경안이 있으면 필요한 영향 분석을 수행합니다.

◆

gx-tech-debt · 기술 부채 진단

코드·아키텍처·의존성·테스트의 기술 부채를 조사하고, 심각도·수정 난이도·영향 범위에 따라 개선 순서를 제안합니다.

◆

gx-research · 도메인·기술 조사

웹 검색과 문서 분석으로 도메인·기술 정보를 조사하고, 출처를 포함한 보고서·비교표·요약을 작성합니다.

◆

gx-cross-review · 구현 교차 검토

요구사항·설계·검증 기록을 바탕으로 수용 기준 충족, 범위 이탈, 새 위험을 검토합니다. Codex에서는 --advisor native로 현재 환경의 역할 리뷰를 요청할 수 있습니다.

◆

gx-commit / gx-pull-request · 커밋·PR 작성

gx-commit은 변경 검증과 브랜치 조건을 확인하고 한국어 커밋을 작성합니다. gx-pull-request는 변경 이력과 검증 결과를 정리해 PR을 생성합니다. 각각 요청한 경우에 실행합니다.

◆

gx-setup · 프로젝트 설정

Git·SVN과 개발 도구·인증 상태를 확인하고 프로젝트의 테스트·빌드 명령을 설정합니다. 기존 사용자 설정을 보존하며 필요한 준비 항목을 안내합니다.

문장 검토와 교정

gx-humanizer · 문장 교정

한국어·영어 문장의 반복 표현과 과도한 수식을 점검하고 의미를 보존하며 교정합니다. 검토만 하거나, 교정하거나, 별도 검증을 포함하는 정밀 모드를 선택할 수 있습니다.

  • audit — 표현상의 문제와 근거 보고
  • rewrite — 문장 교정과 변경 범위 점검
  • strict — 교정 후 의미 보존과 과도한 윤문을 별도 검토
AI 흔적 교정
- before (AI 초안) "혁신적인 솔루션을 통해 요구사항과 구현 계획을 정리하여 TDD 구현과 검증을 효율적으로 수행합니다." 검토 — 추상적 수식과 중복 표현 + after (교정) "요구사항과 구현 계획을 정리하고 TDD 구현과 검증으로 연결합니다." 교정 — 수행 대상과 작업을 구체화
요구사항과 구조 시각화

gx-visualize · 구조·흐름 시각화

요구사항·진행 상태·변경 영향·서비스 구조를 근거와 연결된 한국어 HTML로 시각화합니다. 작업 산출물과 코드 위치를 함께 확인할 때 사용합니다.

  • trace · progress — 요구사항 연결과 작업 단계별 상태
  • impact · service — 변경 영향과 화면·API·서비스·데이터의 연결
  • 코드 근거 — 구조도에 관련 file:line 위치 표시
  • 출력 경로 — 작업별 결과는 .dev/{branch-slug}/visual/, 도메인 구조는 .dev/architecture/
  • 분석 범위 — 작업 산출물과 코드의 정적 근거를 사용하며 운영 인프라 탐색은 제외

시각화 사용 가이드에서 뷰별 출력과 검증 기준을 확인하세요.

안전장치

요청 범위와 검증 근거를 지킵니다

기본 완료점은 검증입니다. 커밋·PR·머지는 각각 사용자 요청에 따라 수행하며, 훅은 설치와 신뢰 상태를 확인해야 작동 여부를 판단할 수 있습니다.

명시한 완료점 — 계획·검증·커밋·PR 가운데 요청한 범위에서 종료합니다. 머지도 별도 명시 요청이 필요합니다.
강제 푸시 금지 — 강제 푸시를 허용하지 않는 운영 규칙과 훅 가드를 제공합니다.
브랜치 확인 — 커밋 스킬은 main·master·develop과 detached HEAD에서 중단합니다.
민감 파일 점검 — 환경 설정·키·인증 정보가 변경에 포함되면 커밋 전에 경고합니다.
생성 파일 점검 — 빌드 결과나 의존성 폴더가 추적되면 제외 규칙 보완을 제안합니다.
완료 검증 — 현재 코드와 검증 근거가 맞지 않으면 완료·커밋·PR 진행을 보류합니다.

Codex 사용법

설치하고, 채팅으로 요청하세요

설치 패키지는 oh-my-gx입니다. 마켓플레이스에서 설치하고, 작업할 프로젝트의 새 세션에서 스킬과 훅 상태를 확인하세요. 아래는 PowerShell 기준 설치 예시입니다.

1. PowerShell에서 설치

Codex 로그인, Git, Python 3.10 이상과 Git Bash를 준비합니다. 처음 설치할 때 아래 두 명령을 실행하세요.

codex.cmd plugin marketplace add bs-koo/oh-my-gx
codex.cmd plugin add oh-my-gx@oh-my-gx

Bash에서는 codex.cmd 대신 codex를 사용합니다. 최신 릴리스 노트에서 배포 변경사항을 확인할 수 있습니다.

2. 프로젝트에서 Codex 실행

작업할 프로젝트 폴더에서 새 세션을 엽니다. /skills에서 GX 스킬을, /hooks에서 훅 정의와 신뢰 상태를 확인하세요.

cd C:\path\to\your-project
codex.cmd

테스트·빌드 설정이 필요하면 gx-setup을 요청합니다. 프로젝트 이해나 계획 요청은 설정 변경 없이 시작할 수 있습니다.

3. 채팅에서 목표와 완료점 요청

아래는 Codex 채팅에 입력할 요청 예시입니다. 필요한 스킬 이름을 명시하고, 중요한 미정 사항에 대한 질문이 나오면 답변하세요.

oh-my-gx:gx-work로 이 프로젝트 구조를 파악해줘.
oh-my-gx:gx-work로 로그인 입력 검증의 구현 계획만 세워줘.
oh-my-gx:gx-work로 이 계획대로 구현하고 검증해줘.
oh-my-gx:gx-cross-review --advisor native로 변경사항을 검토해줘.
oh-my-gx:gx-work로 중단한 개발을 이어서 PR까지 만들어줘.

기본 완료점은 verify입니다. 검증된 변경의 커밋·PR만 필요하면 oh-my-gx:gx-commit, oh-my-gx:gx-pull-request를 직접 요청할 수 있습니다. 작업 브랜치와 환경별 실행 권한은 각 스킬에서 확인합니다.

자주 묻는 질문

시작 전에 확인할 사항

어떤 스킬로 시작하나요?
gx-work가 공통 진입점입니다. 프로젝트 이해, 계획 작성·검토, 구현, 중단 작업 재개 가운데 원하는 결과를 요청하세요. 구현은 gx-tdd가 TDD로 수행합니다. 환경에서 자연어로 스킬을 발견하지 못하면 oh-my-gx:gx-work처럼 이름을 명시하세요.
context 없이도 시작할 수 있나요?
네. 사전 등록 없이 시작할 수 있습니다. 필요한 경우 관련 문서를 대조하고 이번 요청의 최소 요구사항 원장·W작업 목록을 연결합니다. context가 구체 구현계획을 만들지는 않습니다. 결과를 보고 TDD 진행·문서 보완·종료를 선택할 수 있으며 전체 context 인터뷰나 재스캔은 강제하지 않습니다. 읽기 전용·명시 문서 수정 금지는 유지합니다.
계획만 요청하거나 기존 계획을 가져올 수 있나요?
네. 이해·계획·상태만 요청하면 별도 저장 요청 없이 파일을 만들거나 실행 환경을 바꾸지 않고 해당 결과에서 종료합니다. 기존 계획은 출처와 결정을 보존해 부족·충돌만 보완합니다. 새 요청의 PRD·설계·구체 구현계획은 TDD 진입 답변 뒤 gx-tdd에서 작성합니다. 최초 구현 요청이나 문서의 승인 표시가 이후 진입 질문의 답변을 대신하지 않습니다.
도중에 멈추면 처음부터 다시 해야 하나요?
gx-work에 이어서 진행할 작업을 요청하면 저장된 목표·완료점·현재 단계를 확인해 재개합니다. 기존 실행의 계획과 결정은 이어서 사용합니다. 이전 파이프라인이나 호환되지 않는 상태는 자동으로 혼합하지 않고 전환이 필요한지 안내합니다.
검증할 때마다 전체 테스트를 실행하나요?
변경 영향에 맞는 범위를 선택합니다. 같은 실행에서 코드·명령·설정·검증 범위가 정확히 일치하는 결과만 재사용합니다. 필요한 근거가 부족하거나 영향 범위를 판단하기 어렵거나 사용자가 전체 회귀 검사를 요청하면 검사를 확대합니다.
커밋·PR·머지까지 자동으로 진행하나요?
구현 요청의 기본 완료점은 검증입니다. 커밋이나 PR이 필요하면 처음부터 완료점으로 지정하거나 검증 후 요청하세요. 같은 범위에서 이미 허용한 작업은 허가를 반복해서 묻지 않으며, 머지는 별도 명시 요청이 있을 때 수행합니다.
SVN 프로젝트에서도 사용할 수 있나요?
네. gx-setup에서 VCS를 확인하고 요구사항·설계·구현·리뷰를 진행할 수 있습니다. Git 전용 커밋·PR 스킬과 무인 Ralph 반복은 적용되지 않으며, SVN 커밋은 직접 수행합니다. SVN 검증은 Git의 영향 범위 선택·증거 재사용 대신 프로젝트별 테스트·빌드 명령을 직접 실행합니다.
Codex에서도 쓸 수 있나요?
Codex용 역할·설정·실행 규약과 훅을 함께 제공합니다. Codex 시작 안내에 따라 설치한 뒤 새 세션에서 /skills·/hooks를 확인하세요. 기존 Windows 실측 기록과 현재 배포 내용의 차이는 하네스 지원에 표시했습니다. 세부 절차와 권한 제약은 Codex 사용 가이드에서 확인할 수 있습니다.
설치·업데이트 정보는 어디서 확인하나요?
환경별 설치와 업데이트 절차는 저장소 README와 Codex 사용 가이드를 참고하세요. 배포 변경사항은 릴리스 노트에서 확인할 수 있습니다. 업데이트 후에는 새 세션에서 스킬 목록과 훅 상태를 확인하세요.
