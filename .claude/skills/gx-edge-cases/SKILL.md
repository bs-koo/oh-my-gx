# 구현 후 엣지케이스 조사

변경된 동작을 실제 진입점부터 따라가고, 기존 테스트가 사용자에게 보이는 결과와 부수 효과를 검증하는지 확인한다. 변경점과 연결된 코드만 읽고 발견 사항을 대화로 보고한다. 허용 범위는 코드·문서·테스트 열람 및 읽기 전용 Git 조회다. 빌드, 테스트 실행, 파일 수정, 스테이징, 네트워크 조회와 후속 수정은 별도 작업이다.

**하네스 적응**

Codex에서는 [Codex 실행 규약](../gx-work/references/codex-runtime.md)을 읽는다. `Read`는 파일 열람, `Glob`·`Grep`은 `rg --files`·`rg`, Git 조회는 작업 디렉토리를 지정한 셸 명령으로 수행한다. Windows PowerShell에서는 `Get-Content -Encoding UTF8`로 파일을 읽는다. 설치된 실행 규약의 경로는 이 파일 기준이다.

## 1. 조사 범위 잡기

1. 지정한 파일·디렉토리를 우선한다. 기능이나 사례만 주어지면 변경 목록과 저장소 검색에서 관련 진입점과 테스트를 좁힌다. 파일이나 기능이 명확하면 Git 비교 기준 없이도 지정 범위를 조사할 수 있다.
2. Git 프로젝트에서는 `git --no-optional-locks status --short`로 상태를 확인한다. 이어지는 Git 조회에도 `--no-optional-locks`를 적용한다. `--base <ref>`가 있으면 `rev-parse --verify --end-of-options '<ref>^{commit}'`으로 확정한 커밋을 `merge-base HEAD <커밋>`에 전달한다. 지정한 ref가 유효하지 않거나 공통 조상을 읽을 수 없으면 범위 오류를 알리고 해당 비교를 중단한다.
3. 기준을 지정하지 않은 기능 브랜치에서는 다음 순서로 유효한 첫 기준을 쓴다.
   1. `.dev/{branch-slug}/state.md`의 `base`. 브랜치명의 `/`를 `-`로 치환한 경로를 읽고, `branch`가 적혀 있으면 현재 브랜치와 일치하는지 확인한다.
   2. `.claude/config.json`의 `conventions.baseBranch`.
   3. `origin/HEAD`가 가리키는 ref, 로컬 `develop`, `main`, `master` 순서.

   기록된 브랜치명을 로컬에서 찾지 못하면 기존 `origin/<브랜치명>`도 확인한다. 현재 브랜치 자체와 그 원격 동명 브랜치는 후보에서 제외하고, 커밋과 HEAD의 공통 조상을 확인할 수 있을 때만 그 기준을 쓴다. 보호 브랜치, detached HEAD, 유효한 기준이 없는 경우에는 HEAD 이후 작업트리 변경을 조사한다. 첫 커밋 전에는 작업 상태에 표시된 파일을 조사한다.
4. 저장소 루트에서 `diff --no-ext-diff --no-textconv <기준> -- <pathspec>`로 커밋과 인덱스·작업트리의 최종 변경을 함께 읽는다. `ls-files --others --exclude-standard -- <pathspec>`로 아직 추가하지 않은 파일도 확인한다. 기본 변경 목록에는 두 명령 모두 `':(exclude).dev'`를 적용하며, 첫 커밋 전의 작업 상태 목록에도 같은 제외 조건을 적용한다. 사용자가 `.dev` 안의 경로를 명시하면 그 경로를 조사한다. 삭제된 계약은 비교 시작점의 파일에서 읽는다. 범위가 비었으면 변경 기준이나 대상 경로가 필요하다고 보고한다. Git 외 프로젝트에서 대상이 없을 때도 파일이나 기능을 지정할 수 있다고 안내한다.

## 2. 실패 경로와 테스트 대조

1. PRD, 수용 기준, 공개 API 계약과 기존 호출자에서 기대 동작을 확인한다. 파일이 있으면 관련 부분만 읽는다. `.dev` 문서도 조사 대상의 계약을 담고 있으면 직접 읽는다. 현재 구현의 동작만으로 요구사항을 추정하기 어려우면 확인할 정책을 적는다.
2. 변경된 로직에 도달하는 호출 경로를 찾고 입력·초기 상태·사건 순서를 바꿔 따라간다. 직접 연관되는 항목을 택한다.

   | 바뀐 동작 | 확인할 상황 |
   |---|---|
   | 유효 범위·형식 | 빈 값, 경계 바로 안팎, 기존 포맷 |
   | 상태 전이·저장 | 금지 전이, 중복 요청, 동시에 같은 상태를 읽은 요청, 부분 실패 뒤 재시도 |
   | 외부 호출·fallback | 응답 지연, 호출 성공 뒤 응답 유실, 오류가 성공으로 처리되는 경로, 정리 누락 |
   | 응답·기존 데이터 | 삭제된 필드나 기본값, 구버전 레코드, 호출자별 기대 동작 |

3. 후보마다 진입점·가드·저장 제약·트랜잭션으로 도달 가능성을 확인한다. 관련 테스트의 설정과 assertion을 읽어 그 조건과 관찰할 결과를 모두 다루는지 확인한다. 이미 차단되는 경로나 동일한 효과를 검증하는 테스트가 있는 경우 해당 근거로 후보를 해소한다.

## 3. 결과 보고

첫 줄에 조사한 기준 ref 또는 파일 범위와 테스트 실행 상태 `미실행`을 적는다. 확인한 항목은 영향이 큰 순서로 보고한다.

| 판정 | 필요한 근거 |
|---|---|
| 코드상 결함 | 도달 가능한 조건과 위반된 기대 동작이 코드에서 확인됨 |
| 테스트 공백 | 지켜야 할 동작은 확인됐고, 해당 조건이나 결과를 기존 테스트가 검증하지 않음 |
| 확인 필요 | 계약이 불명확하거나 실행 환경·데이터·동시성 보장을 확인할 자료가 부족함 |

각 항목에 **발생 조건 → 기대 동작과 근거 → 코드 위치 → 영향 → 회귀 테스트 제안**을 넣는다. 테스트는 진입점, 초기 상태, 입력 또는 사건 순서, 확인할 결과를 명시한다. 하나의 결함과 직접 연결된 테스트 누락은 같은 항목에 적는다. 확인할 근거가 부족한 경우 다음 확인 사항을 적는다. 검토를 마친 범위에서 근거 있는 발견이 0건이면 `발견 0건`과 확인한 경로를 보고한다. 범위를 확보하지 못했다면 `조사 범위 미확보`로 표시한다.

예를 들어 취소 계약이 재고 복구 1회를 요구하고, 재고 변경 후 취소 상태 저장이 실패할 수 있으면 상태 저장 실패 뒤 같은 주문을 다시 취소하는 경로를 확인한다. 중복 복구가 가능하면 최초 상태 저장만 실패시키고 재시도한 뒤 최종 상태와 재고 증가량을 함께 검증하는 테스트를 제안한다.
