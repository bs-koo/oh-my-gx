# context

도메인 컨텍스트와 요구사항 원장, 작업 계획을 생성·갱신하고 진행도를 동기화한다. 상황에 따라 자동으로 적절한 모드를 선택한다.

**하네스 적응**: 이 문서는 Claude Code 도구명으로 서술한다. 다른 하네스에서 실행 중이면 아래 대응으로 옮겨 수행한다.

Codex에서는 먼저 `Read("../gx-work/references/codex-runtime.md")`로 공통 실행 규약을 읽고, 이 스킬의 절차·게이트를 유지한다. 상대경로는 이 SKILL.md 위치 기준이다.
Codex on Windows: read this SKILL.md and referenced files as UTF-8; use `Get-Content -Encoding UTF8`.

- `AskUserQuestion` → 공통 codex-runtime의 질문 대기 계약으로 옮긴다. 실제 모드·용도가 허용하는 `request_user_input`·`request_user_input_async` 또는 자연어를 사용한다. 필수 질문은 pending 상태를 저장하고 실제 답변·결정 기록 전 다음 단계로 넘어가지 않는다. async 반환은 답변이 아니며 본문·선택지를 표시한다.

질문은 한 번에 1~3개, 질문마다 선택지는 2~3개로 제한한다. 추천 답변은 첫 번째에 놓고 label 끝에 `(Recommended)`를 붙인다. UI가 자유 입력을 제공하므로 Other를 option으로 직접 추가하지 않는다. Codex 변환에서는 `../gx-work/references/codex-runtime.md`와 실제 도구 스키마를 우선한다.

도구 이름이 다르다는 이유로 게이트를 건너뛰지 않는다. 확인·검증 단계는 하네스와 무관하게 유지한다.

## 인자 파싱

Arguments 문자열에서 아래 규칙으로 파싱한다:
- `--from <경로>`: `--from` 다음 토큰을 파일 경로로 사용. 경로에 공백이 있으면 따옴표로 감싸진 것으로 간주.
- `--sync`: 진행도 동기화 모드. git 히스토리 기반으로 status.md 갱신.
- `--from`과 `--sync`를 제외한 나머지 텍스트:
  - 공백 없는 한 단어(또는 따옴표로 감싼 이름)면 도메인명으로 사용.
  - 여러 단어로 된 문장·목록이면 **요구사항 본문**으로 사용. 첫 단어가 기존 `context/{단어}/` 디렉토리명과 같으면 그 단어만 도메인명으로 떼어내고 나머지를 본문으로 본다.
- `--sync`와 `--from`은 동시 사용 불가. 동시 지정 시 "`--sync`와 `--from`은 동시에 사용할 수 없습니다." 안내 후 중단. `--sync`와 요구사항 본문도 같은 이유로 함께 쓰지 않는다.
- 인자 없음: 도메인명과 `--from`, `--sync` 모두 없음. 다만 스킬이 인자 없이 호출됐어도 이번 사용자 메시지에 요구사항 문장이나 요구사항 문서 경로가 있으면 그것을 요구사항 본문·`--from`으로 쓴다. 사용자는 대개 "이 요구사항 정리해서 작업 나눠줘"처럼 말하지 플래그를 붙이지 않는다.

`--from` 파일과 요구사항 본문을 합쳐 `REQUIREMENT_INPUT`이라 부른다. 둘 중 하나라도 있으면 요구사항 입력이 있는 것이다.

예시:
- `결제` → 도메인명=결제
- `정산 --from docs/req.md` → 도메인명=정산, from=docs/req.md
- `--from docs/req.md` → 도메인명=없음, from=docs/req.md
- `결제 --sync` → 도메인명=결제, sync=true
- `계량기 사용량을 엑셀로 내려받는 기능 추가` → 요구사항 본문 (`context/계량기/`가 있으면 도메인명=계량기, 본문=`사용량을 엑셀로 내려받는 기능 추가`)
- (빈 인자) → 도메인명=없음, from=없음, sync=없음

## 수칙

- **공통 정규화**: 대화·문서 입력은 `Read("references/intake.md")`의 같은 절차로 출처·결정·미정을 정리한다. 전체 원문을 단계마다 반복해서 읽거나 전달하지 않는다.
- **질문은 중요한 빈칸만**: 범위·동작·설계 제약·인수 기준을 바꾸는 미정 사항만 묻는다. 이미 근거가 있는 사실은 재확인하지 않고, 비차단 누락은 ❓로 남긴다.
- **관측과 요구 구분**: 코드의 현황은 observed-facts에 기록한다. 요청되지 않은 미래 요구사항·수치·담당자를 만들지 않는다.
- **승인 근거 유지**: 실제 사용자 승인과 위임을 기록해 동일 결정을 다시 묻지 않는다. 명시적 제거·변경·계획 승인 경계는 유지한다.
- **반환 후 종료**: context와 공통 계획을 정리한 뒤 `references/intake.md`의 짧은 구조화된 인계를 gx-work에 반환한다. context-only면 여기서 종료한다.

## 모드 자동 판단

인자와 현재 상태를 기반으로 모드를 결정한다. **위에서부터 처음 맞는 행 하나만** 적용한다. 같은 조건이 두 행에 걸리면 위 행이 이긴다.

| 순서 | 조건 | 모드 | 동작 |
|------|------|------|------|
| 1 | `--sync` | **동기화** | git log/PR 분석 → status.md 갱신 |
| 2 | 요구사항 입력 있음 + `context/` 폴더 없음 | **스캔 → 문서 기반** | 코드베이스로 도메인을 먼저 잡고(A-1~A-5), 요구사항을 그 도메인에 배분 |
| 3 | 요구사항 입력 있음 + `context/` 있음 | **문서 기반** | 요구사항을 도메인별로 배분해 생성/갱신. 대상 도메인이 이미 있어도 이 모드다 |
| 4 | `context/` 폴더 없음 | **스캔** | 코드베이스 분석 → context 초안 자동 생성 (도메인명이 있으면 그 도메인 우선) |
| 5 | 도메인명 지정 + `context/{도메인}/` 있음 | **갱신** | 사용자에게 갱신 대상 확인 후 Q&A |
| 6 | 도메인명 지정 + `context/{도메인}/` 없음 | **신규** | Q&A 기반 새 도메인 생성 |
| 7 | 인자 없음 + `context/` 있음 | **선택** | 아래 질문으로 모드를 정한다 |

요구사항 입력이 있으면 도메인 존재 여부와 상관없이 문서 기반 모드가 원장과 작업 계획을 끝까지 맡는다. 갱신 모드로 먼저 보내면 요구사항이 원장에 들어가지 않은 채 끝날 수 있기 때문이다.

**선택 모드 질문**:

```
AskUserQuestion(
  questions: [{
    header: "작업 선택",
    question: "context/가 이미 있습니다. 무엇을 할까요?",
    multiSelect: false,
    options: [
      { label: "요구사항 추가 (Recommended)", description: "선택하면 후속 질문에서 요구사항 내용이나 파일 경로를 받아 원장과 작업 계획에 반영합니다" },
      { label: "도메인 추가·갱신", description: "선택하면 후속 질문에서 도메인명을 받아 신규 또는 갱신으로 진행합니다" },
      { label: "코드베이스 재스캔", description: "코드베이스를 다시 분석해 도메인 구조를 갱신합니다" }
    ]
  }]
)
```

- "요구사항 추가" → 요구사항 본문이나 파일 경로를 후속 질문으로 받고 실제 답변을 기다린 뒤 문서 기반 모드로 진행한다.
- "도메인 추가·갱신" → 도메인명을 후속 질문으로 받고, 그 도메인이 있으면 갱신, 없으면 신규로 진행한다.
- "코드베이스 재스캔" → 스캔 모드로 진행한다.

## 모드 실행

모드를 결정한 직후 아래 해당 파일 하나만 Read하고 그 절차를 실행한다. 상대경로는 이 SKILL.md 위치 기준이다.

- `신규` → `Read("modes/create.md")`
- `문서 기반` → `Read("modes/from-document.md")`
- `갱신` → `Read("modes/update.md")`
- `동기화` → `Read("modes/sync.md")`
- `작업 계획` → `Read("modes/plan.md")` (모든 모드의 마지막 단계, 아래 "작업 계획 마무리")

`스캔`은 아래 모드 A를 이 SKILL.md에서 계속 실행한다. `스캔 → 문서 기반`은 모드 A를 A-5까지 마친 뒤 `Read("modes/from-document.md")`로 넘어간다. 스캔 중 수동 생성으로 전환하거나 A-3에서 루트 README.md·glossary.md 초기화에 B-0 템플릿이 필요할 때 또는 새 도메인의 status.md에 B-9-1 템플릿이 필요할 때, 문서 기반 모드가 내부에서 신규·갱신 절차를 호출할 때, 갱신 모드에서 요구사항 추가를 골라 문서 기반 절차로 넘어갈 때, 신규 B-1에서 기존 도메인의 갱신을 선택할 때만 해당 mode 파일을 추가로 Read한다. B-1의 갱신 선택에서는 `Read("modes/update.md")` 후 모드 D를 실행하고 모드 B를 종료한다.

## 작업 계획 마무리

선택한 모드의 절차가 끝나면, 사용자가 중간에 취소한 경우가 아니면 **항상** `Read("modes/plan.md")`의 작업 계획 갱신을 실행한 뒤 종료한다. 사용자가 plan.md나 작업 계획을 말하지 않았어도 실행한다.

이 스킬은 요구사항 원장(`context/*/status.md`)을 바꾸는 경로다. 원장이 바뀌었는데 계획이 그대로면 새 요구사항은 아무도 착수하지 않고, 원장에서 빠진 요구사항은 계획에 남아 누군가 시작하게 된다. 원장과 계획이 어긋나는지 확인하는 지점을 모드마다 두지 않고 여기 하나로 모은 이유는, 어느 경로로 들어오든 같은 기준으로 계획이 맞춰져야 하기 때문이다. 맞출 것이 없으면 그 절차가 한 줄로 끝난다.

문서 기반 모드는 자기 절차 안(C-5)에서 같은 파일을 실행하므로, 그 모드에서 이미 끝냈으면 다시 실행하지 않는다.

계획 마무리 후 `Read("references/intake.md")`의 반환과 종료를 수행한다. 원장·계획 전문 대신 경로·절·관련 ID·변경분만 인계한다. `/gx-work`나 `/gx-tdd`를 이 스킬에서 호출하지 않는다.

## 모드 A: 스캔 (코드베이스 분석)

`context/` 폴더가 없거나 사용자가 재스캔을 선택한 경우 실행한다.

### A-0. 사용자 확인

사용자가 이미 코드베이스 스캔·자동 생성을 요청했거나 gx-work의 승인된 정리 범위에 포함했으면 그 근거를 기록하고 A-1로 간다. 같은 수행 방식을 다시 묻지 않는다. 자동 생성과 수동 생성의 선택이 미정일 때만 아래 질문을 한다.

```
AskUserQuestion(
  questions: [{
    header: "context 생성",
    question: "context/ 디렉토리가 없습니다. 코드베이스를 분석하여 도메인 구조를 자동 생성할까요?",
    multiSelect: false,
    options: [
      { label: "자동 생성", description: "코드베이스 스캔으로 도메인 구조를 자동 생성합니다" },
      { label: "수동 생성", description: "질문에 답하며 도메인을 수동으로 생성합니다" }
    ]
  }]
)
```
- "자동 생성" → A-1로 진행
- "수동 생성" → `Read("modes/create.md")` 후 모드 B(신규)로 전환하여 수동 생성

### A-1. 프로젝트 구조 스캔

아래 항목을 병렬로 탐색한다:

1. **디렉토리 구조**: 소스 루트 하위 최상위 2레벨을 스캔하여 도메인 후보를 추론한다. 언어 무관 휴리스틱:
   - 파일 확장자 클러스터로 소스 루트를 판별한다 (`.java`/`.kt`/`.ts`/`.py`/`.c`/`.h`/`.go`/`.rs` 등)
   - 업무 명사 디렉토리명 군집을 도메인 후보로 본다 (payment/, order/, sensor/, protocol/ 등)
   - 언어별 예시: Java `src/main/java/{base-package}/` 하위 패키지, Node `src/` 하위 modules/·features/·domains/, C `src/`·`include/` 하위 모듈 디렉토리
2. **도메인 모델**: 네이밍 패턴 군집으로 탐색한다 — 접미사형(`*Entity.java`, `*.entity.ts`, `*Model.*`) 또는 C 계열 모듈 쌍(`{이름}.h`/`{이름}.c`)의 구조체(typedef struct) 정의.
3. **진입점/인터페이스**: API 라우팅(`*Controller.java`, `*Router.*`, `routes/`) 또는 C 계열 공개 헤더(include/ 디렉토리, extern 함수 선언이 밀집한 헤더).
4. **설정 파일**: `application.yml`, `application.properties`, `.env`, `package.json`, `Makefile`/`CMakeLists.txt`, `Kconfig` 등을 읽는다.
5. **README/문서**: 프로젝트 루트의 `README.md`, `docs/` 디렉토리를 확인한다.

### A-2. 도메인 분류

스캔 결과에서 도메인을 추론한다:
- 패키지 구조 기반: `com.example.payment` → 결제 도메인
- 엔티티 클러스터 기반: 관련 엔티티를 그룹핑
- API 엔드포인트 기반: `/api/orders/**` → 주문 도메인
- 모듈 접두사 기반 (C 계열): `uart_*.h`/`sensor_*.c` 군집 → 통신/센서 도메인

### A-3. 초안 생성

`context/README.md` 또는 `context/glossary.md`가 없으면 초기화 전에 `Read("modes/create.md")`로 B-0의 해당 루트 파일 템플릿을 읽는다. 새 도메인의 `status.md`를 생성할 때는 두 루트 파일이 모두 있어도 생성 전에 `Read("modes/create.md")`로 B-9-1의 5열 요구사항 원장과 `<!-- gx-sync ... -->` cursor 템플릿을 읽는다. 같은 A-3에서 두 조건이 모두 참이면 한 번만 Read한다.

각 감지된 도메인에 대해:
1. 도메인별 디렉토리 생성: `mkdir -p context/{도메인}/`
2. `context/` 루트 파일 초기화 (필요시):
   - `test -f context/README.md` 가 false인 경우, `Read("modes/create.md")`의 B-0과 동일하게 `context/README.md` 생성
   - `test -f context/glossary.md` 가 false인 경우, `Read("modes/create.md")`의 B-0과 동일하게 `context/glossary.md` 생성
3. 스캔 결과를 기반으로 각 문서 초안 작성:
   - **README.md**: 도메인 개요 (스캔에서 파악한 범위, 주요 기능)
   - **PROJECTS.md**: 현재 레포를 자동 등록한다. git은 `git remote get-url origin`의 레포명을 사용한다. svn은 `svn info --show-item url` 종료 코드 != 0이면 진단 후 중단한다. URL 끝에서 `trunk`, `branches/<name>`, `tags/<name>`을 제거하고 남은 마지막 세그먼트를 `REPOSITORY_ID`로 쓴다. 성공했지만 URL·ID가 비거나 모호하면 경고 후 `basename(PROJECT_ROOT)`를 쓴다.
   - **glossary.md**: 엔티티명, 주요 상수, enum 값 등에서 추출한 용어 초안
   - **architecture.md**: 패키지 구조, 레이어 구조 요약
   - **status.md**: 빈 템플릿

### A-4. 사용자 검토

생성된 초안을 사용자에게 보여주고 확인을 받는다:
- "N개 도메인을 감지했습니다: {목록}. 확인해주세요."
- 사용자가 도메인을 추가/제거/이름 변경할 수 있다.
- 각 도메인의 README.md 초안을 보여주고 수정 사항을 반영한다.
- 담당자는 입력에서 확인되면 기록하고 없으면 ❓로 둔다. 실제 승인권자·배분 가능 여부를 바꾸는 경우에만 필요한 정보를 질문한다.

### A-5. 확정 및 인덱스 생성

사용자 확인 후:
- 수정 사항을 반영하여 최종 문서를 Write한다.
- `context/README.md` 도메인 테이블을 업데이트한다.
- 완료 안내: 생성된 도메인 수, 파일 수, ❓ 항목 안내.

요구사항 입력이 있는 `스캔 → 문서 기반` 경로면 여기서 확정한 도메인을 배분 후보로 넘기고 `Read("modes/from-document.md")`의 C-1부터 실행한다. 요구사항 입력이 없으면 작업 계획 마무리로 간다 — 그 절차의 P-0이 요구사항이 있는지 묻는다.
