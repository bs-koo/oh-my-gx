> 호출 전제: gx-context/SKILL.md가 인자 파싱·모드 선택·하네스 적응을 완료했고, 선택한 모드의 절차가 끝났다. 이 파일의 상대경로는 gx-context/SKILL.md 위치를 기준으로 해석한다.

## 작업 계획 갱신 (모든 모드 공통 마무리)

개발에서 호출한 관련 문서 대조는 `references/development-sync.md`를 따른다. 이번 run의 새 W행/버그 수정 작업은 원장의 기존 ✅만으로 완료시키지 않는다. 구현 후 현재 AC·인수 근거와 최종 verify까지 확인한 뒤 gx-tdd의 완료 단계에서 해당 W행을 갱신한다. 이 모드의 후보 목록은 검토 자료이며 검증·병합을 인증하지 않는다.

`context/*/status.md`의 요구사항 원장과 `.dev/plan.md`를 대조해 계획을 만들거나 고친다. 사용자가 "plan.md"나 "작업 계획"을 말하지 않아도 모든 모드의 마지막에 실행한다.

이 단계를 모드마다 따로 두지 않는 이유가 있다. 원장은 문서 기반·갱신·동기화 어느 경로로든 바뀔 수 있는데, 계획 갱신이 한 모드에만 붙어 있으면 다른 경로로 들어온 요구사항은 계획에 들어가지 않는다. 계획에 없는 요구사항은 아무도 착수하지 않고, 원장에서 사라진 요구사항이 계획에 남으면 누군가 하지 않아도 될 일을 시작한다. 그래서 갱신의 기준을 "이번에 무엇을 입력받았나"가 아니라 **"지금 원장과 계획이 맞는가"**로 둔다. 이렇게 하면 어느 모드로 들어왔든 결과가 같다.

### P-0. 진입 판단

- 사용자가 모드 진행 중에 취소했으면 이 단계를 건너뛴다.
- `context/`가 없으면 원장도 없으므로 건너뛴다.
- 원장에 `⬜` 항목이 하나도 없고 `.dev/plan.md`도 없으면 계획을 만들 대상이 없다.
  - 이번 실행이 스캔 또는 신규 모드였다면 요구사항이 있는지 묻는다. 단 사용자가 컨텍스트만 정리하도록 종료 지점을 지정했거나 요구사항 입력을 나중으로 정했으면 추가 입력을 유도하지 않고 빈 원장 상태와 인계 경로를 안내하고 끝낸다. 막 도메인을 만든 사람은 대개 다음으로 작업을 나누고 싶어 한다.
    ```
    AskUserQuestion(
      questions: [{
        header: "요구사항",
        question: "요구사항 문서나 목록이 있으면 원장에 넣고 작업 계획(.dev/plan.md)까지 만듭니다. 지금 입력할까요?",
        multiSelect: false,
        options: [
          { label: "지금 입력 (Recommended)", description: "선택하면 후속 질문에서 파일 경로나 요구사항 내용을 받습니다" },
          { label: "나중에", description: "context만 만들고 끝냅니다" }
        ]
      }]
    )
    ```
    "지금 입력"이면 파일 경로나 요구사항 본문을 후속 질문으로 받고 실제 답변을 기다린다. 원 질문 UI Other에 직접 붙여 넣은 내용은 그대로 받는다. 받은 내용을 `REQUIREMENT_INPUT`으로 두고 `Read("modes/from-document.md")`의 C-1~C-4-1을 실행한 뒤 P-1로 돌아온다.
  - 그 밖이거나 "나중에"면 다음 한 줄을 안내하고 끝낸다: "원장에 미반영 요구사항이 없어 작업 계획을 만들지 않았습니다. 요구사항이 생기면 `/gx-context --from <파일>` 또는 `/gx-context <요구사항 내용>`으로 부르세요."

### P-1. 수집

1. 모든 `context/{도메인}/status.md`의 `## 요구사항 원장` 표를 Read하여 `(도메인, ID, 요구사항, 상태)` 목록 `LEDGER`를 만든다. 예약 도메인(`공통`·`통합`)은 디렉토리가 없으므로 여기에 나오지 않는다.
2. `.dev/plan.md`가 있으면 `| ID | 작업 | 도메인 | 요구사항 | 의존 | 작업 위치 | 상태 |` 표를 Read하여 각 행의 `요구사항` 열을 개별 ID로 펼친다.
   - 범위 `FR-4~6`은 `FR-4`·`FR-5`·`FR-6`, 쉼표·가운뎃점은 나열이다.
   - 일반 도메인 행의 ID는 그 도메인 원장의 ID다.
   - `공통`·`통합` 행은 `{도메인}:FR-N`처럼 출처 도메인을 붙여 쓴다. 원장 ID는 도메인마다 따로 매겨지므로 접두사가 없으면 어느 원장의 FR-1인지 알 수 없다. 접두사가 없는 기존 행은 원장 도메인이 하나뿐이면 그 도메인으로 읽고, 둘 이상이면 P-2의 끊긴 참조로 보고한다.
3. 이번 실행에서 원장을 바꿨다면(문서 기반 모드의 `LEDGER_REQUIREMENTS`) 그 ID 목록을 `CHANGED_IDS`로 받아 둔다. 판정의 근거는 아니고, P-7 보고에서 "이번에 들어온 요구사항"을 구분해 보여주는 데만 쓴다.

### P-2. 대조

기존 계획이 있으면 확인한 설치 스킬 경로의 `scripts/plan.py --project-root <프로젝트 절대경로>`를 실행한다 (Windows PowerShell은 `python`, POSIX는 `python3`). 이 helper는 실제 표와 도메인 원장을 읽어 아래 대조 목록과 `ready`를 계산하며 파일을 수정하지 않는다. 오류가 있으면 다음 작업을 추천하거나 착수시키지 않는다. helper의 `progress-review`는 완료 승인 후보이며 종료 근거를 대신하지 않는다.

`LEDGER`와 계획 행을 맞대어 아래 목록을 만든다. 기존 계획이 있으면 **변경 없음 판정 전에 항상** P-8의 다섯 검사를 수행한다. 참조는 `(도메인, ID)`로 구분한다 — 서로 다른 도메인의 `FR-1`은 중복이 아니다. 열린 요구사항의 배정이 0건이면 `UNASSIGNED`, 2건 이상이면 `PLAN_ERRORS`에 넣고, ID 중복·없는 의존 대상·순환·폐기 작업 의존도 `PLAN_ERRORS`에 넣는다. 검사에서 오류를 찾았다는 이유로 `진행`·`완료` 행을 자동 수정하지 않는다.

| 목록 | 조건 | 처리 |
|------|------|------|
| `UNASSIGNED` 미배정 | 원장의 `⬜` 항목이 `폐기`가 아닌 어떤 계획 행에도 없다 | P-3에서 기존 대기 행에 넣거나 새 행으로 묶는다 |
| `DISCARD_CANDIDATES` 폐기 후보 | `대기` 행의 요구사항이 모두 `🚫` | P-6 규칙으로 `폐기` 제안 |
| `DONE_CANDIDATES` 완료 후보 | 요구사항이 모두 `✅`인 `대기` 행, 그리고 아래 "진행 행의 완료 판정"을 통과한 `진행` 행 (파이프라인 밖에서 구현되어 `--sync`로 반영된 경우) | `완료` 제안 |
| `BROKEN_REFS` 끊긴 참조 | 계획 행의 ID가 원장에 없거나, 접두사 없는 `공통`·`통합` 행이 여러 원장과 겹친다 | 보고하고 P-7에서 바로잡을 값을 묻는다 |
| `PARTIAL_DISCARDS` 부분 폐기 | `대기` 행의 요구사항 일부만 `🚫` | 폐기 ID만 제거하는 수정을 P-7에서 제안한다 |
| `PLAN_ERRORS` 계획 오류 | 열린 요구사항의 중복 배정, 작업 ID 중복, 없는 의존 대상, 순환, 폐기 작업 의존 | P-7에서 바로잡을 값을 확인하고 검증을 다시 수행한다 |

- `PARTIAL_DISCARDS`는 다른 목록이 비어 있어도 반영할 변경이다. 폐기 ID를 뺀 뒤 남은 요구사항이 모두 `✅`이면 같은 제안에서 `완료` 후보로도 판정한다.
- `완료` 행은 이 목록의 대상이 아니다. `진행` 행은 아래 완료 판정에만 쓰고, 폐기·미배정 판정에서는 건드리지 않는다.

**진행 행의 완료 판정**: gx-work·gx-tdd로 착수했다가 다른 도구로 마무리하면 phase-complete가 돌지 않아 행이 `진행`으로 남는다. 요구사항이 모두 `✅`라는 사실만으로는 부족하다 — 같은 브랜치에서 아직 작업 중일 수 있다. 그래서 그 작업이 끝났다는 근거를 하나 더 확인한다.

원격 브랜치 삭제나 후보 표시는 그 자체로 테스트 통과·merged 근거가 아니다. 실제 종료/검증 근거가 없으면 완료 후보로 제시하더라도 자동 적용하지 않는다. 새 W행의 별도 AC·위험 수용/미검증 항목이 남으면 원래 행은 진행을 유지한다.

1. 요구사항이 모두 `✅`인 `진행` 행만 대상으로 한다.
2. git이면 `작업 위치` 열의 브랜치를 확인한다.
   - `git ls-remote --heads origin {브랜치}`가 성공했고 결과가 비어 있으면 원격 브랜치가 지워진 것이다. 대개 머지 후 삭제이므로 완료 후보로 본다.
   - 결과가 있으면 그 커밋 해시가 현재 HEAD에 포함되는지 `git merge-base --is-ancestor {해시} HEAD`로 확인한다. 종료 코드 0이면 이미 머지된 것이므로 완료 후보다. 1이면 아직 머지되지 않은 작업이 남아 있으므로 후보가 아니다. 해시가 로컬에 없어 오류(2 이상)가 나면 판정하지 않는다.
   - `ls-remote`가 실패하면(원격 없음·네트워크) 판정하지 않는다.
3. svn이면 `.dev/{작업 위치}/state.md`를 읽어 `status: completed`이거나 파일이 없으면 완료 후보로 본다. `in_progress`면 후보가 아니다.
4. 판정하지 못한 행은 P-7에서 "요구사항은 모두 ✅인데 작업 종료를 확인하지 못함"으로 따로 보여주고 사용자가 고르게 한다. 근거 없이 `완료`로 바꾸면 아직 작업 중인 사람의 착수 기록이 사라진다.
- 위 여섯 목록이 모두 비고, 진행 행의 완료 확인 대기도 없으며, 기존 계획의 다섯 검사까지 통과했고 `.dev/plan.md`가 있으면 "작업 계획이 원장과 맞습니다 (미배정 0건)." 한 줄로 끝낸다. `PARTIAL_DISCARDS`나 `PLAN_ERRORS`가 있으면 이 종료 경로를 쓰지 않는다.

**미배정이 1건이어도 계획에 넣는다.** 요구사항 한 건이 추가될 때가 가장 흔한 갱신이다. 건수 기준으로 건너뛰면 그 요구사항은 계획 밖에 남는다.

### P-3. 작업 묶기

`UNASSIGNED` 항목을 작업으로 묶는다.

- 한 작업은 **AC 3~5개로 환산 가능한 크기**여야 한다 (gx-work·gx-tdd의 AC 상한과 맞춘다)
- 화면·기능·컴포넌트 단위로 묶는다
- **파일 경계가 겹치지 않도록** 나눈다 — 겹치면 나중에 여러 사람이 동시에 작업할 수 없다
- 도메인을 가로지르지 않는다. 여러 도메인이 걸리는 작업만 예약 도메인 `통합`을 쓴다
- 기존 `대기` 행의 범위(같은 화면·같은 파일)에 들어가는 항목은 새 행을 만들지 않고 P-6의 **겹침**으로 처리한다

기존 소스 코드가 있으면 `architecture.md`와 실제 디렉토리 구조를 보고 파일 경계를 판단한다. 요구사항 문장만 보고 나누면 같은 컨트롤러를 두 작업이 함께 고치는 계획이 나오기 쉽다.

### P-4. 의존 판정

아래를 선행 작업으로 본다.

- 스키마·공통 모듈을 만드는 작업 (다른 작업이 그 테이블·타입을 쓴다)
- 데이터를 생산하는 작업 (소비하는 작업보다 앞선다)
- 인증·권한 기반 (보호 대상 기능보다 앞선다)

**근거 없이 의존을 만들지 않는다.** 판정 근거를 표 아래 각주로 남긴다. 확신이 없으면 의존을 비우고 P-7의 확인 게이트에서 사용자에게 묻는다. 새 작업이 기존 `완료`·`진행` 작업에 의존해도 된다. 반대로 기존 작업의 의존 열에 새 작업을 넣는 것은 그 행이 `대기`일 때만 한다.

### P-5. 예약 도메인

도메인에 속하지 않는 작업은 아래 예약어를 쓴다. 이 둘은 `context/{도메인}/` 디렉토리를 만들지 않으며, 파이프라인도 context를 읽지 않는다.

| 값 | 의미 |
|----|------|
| `공통` | 스키마·기반 모듈 등 도메인 이전의 선행 작업 |
| `통합` | 여러 도메인이 걸리는 작업 |

예약 도메인 행의 `요구사항` 열은 `건물:FR-1, 계량기:FR-2`처럼 출처 도메인을 붙인다.

### P-6. 재계획 판정 (plan.md가 이미 있을 때)

기존 계획을 덮어쓰지 않는다. P-8의 저장 분기(`Edit` 사용)와 함께 적용된다 — 방식만 지키고 아래 보존 규칙을 어기면 행이 사라지는 것은 같다.

**먼저 상태로 손댈 수 있는 범위를 가른다.**

| 상태 | 처리 |
|------|------|
| `완료` | 건드리지 않는다 — 이미 코드가 들어갔다 |
| `진행` | 건드리지 않는다 — 누군가 작업 중이다. 단 P-2의 진행 행 완료 판정을 통과하고 사용자가 승인하면 `완료`로 바꾼다 |
| `대기` | 재조정 대상 |

**그다음 대기 작업 각각을 원장과 대조해 하나로 판정한다.**

| 판정 | 조건 | 처리 |
|------|------|------|
| **유지** | 요구사항이 그대로 살아 있다 | 변경 없음 |
| **겹침** | 미배정 요구사항이 기존 작업의 범위에 들어간다 | 기존 행의 `요구사항` 열을 확장한다. 새 행을 만들지 않는다 — 같은 파일을 건드리는 작업이 둘로 갈리면 병렬 배분이 깨진다 |
| **범위 축소** | 요구사항 일부만 원장에서 `🚫` | `PARTIAL_DISCARDS`의 폐기 ID만 빼고 기존 ID·작업 위치를 유지한다. 남은 항목이 모두 `✅`이면 완료 제안도 함께 한다 |
| **폐기** | 요구사항이 삭제되어 할 일이 없어졌다 (원장에서 모두 `🚫`) | `상태`를 `폐기`로 바꾼다. 행을 지우지 않는다 — 왜 사라졌는지가 git 이력에만 남으면 나중에 추적이 어렵다 |
| **완료** | 원장에서 요구사항이 모두 `✅` (`진행` 행은 작업 종료 근거까지 확인) | `상태`를 `완료`로 바꾼다. `작업 위치` 열은 그대로 둔다 — 어느 브랜치에서 끝났는지가 기록으로 남는다 |

폐기는 원장의 `🚫`만 근거로 삼는다. 이번 입력 문서에 어떤 요구사항이 없다는 사실만으로는 폐기하지 않는다 — 추가분만 담은 문서를 넣었을 때 기존 작업이 모두 폐기되는 사고를 막기 위해서다. 원장의 `🚫`는 문서 기반 모드에서 사용자가 전체본이라고 확인하고 제거를 승인했을 때만 생긴다.

새 요구사항에서 나온 작업은 뒤에 추가한다. 새 ID는 표 전체(`폐기` 포함)의 최댓값 다음 번호를 쓰고 폐기된 번호를 다시 쓰지 않는다. 변경 내역은 git이 기록하므로 파일 안에 시점별 이력을 쌓지 않는다.

**완료·진행 작업의 요구사항이 폐기된 경우**는 상태를 되돌리지 않는다. 이미 들어간 코드를 걷어내는 것은 별개의 작업이므로, 필요하면 제거 작업을 새 행으로 추가한다. 완료를 `폐기`로 뒤집으면 "무엇이 언제 들어갔는지"가 사라진다.

**폐기된 작업은 의존 대상이 될 수 없다.** 다른 작업이 폐기된 작업에 의존하고 있으면 그 의존을 끊거나 대체 작업으로 바꿔야 한다. 확인 게이트에서 함께 제시한다.

### P-7. 확인 게이트

묶음과 의존 판정은 추론이므로 저장 전에 반드시 확인받는다. 이미 동일 변경분의 묶음·의존을 명시적으로 승인받았으면 그 승인 source를 기록하고 재질문하지 않는다. 내부 묶음·파일 경계를 사용자에게 위임받은 경우 그 선택 자체는 재질문하지 않지만, 아직 받지 않은 계획 저장 승인은 유지한다. 관련 사실 다섯 개나 이미 확정한 요구사항을 다시 확인하지 않는다.

```
AskUserQuestion(
  questions: [{
    header: "작업 계획",
    question: "요구사항 {N}건을 반영해 작업 계획을 {만들었/고쳤}습니다. 이대로 저장할까요?",
    multiSelect: false,
    options: [
      { label: "그대로 저장 (Recommended)", description: "제안된 묶음과 의존 관계를 그대로 반영합니다" },
      { label: "묶음 조정", description: "선택하면 후속 질문에서 합치거나 나눌 작업을 묻습니다" },
      { label: "의존 관계 수정", description: "선택하면 후속 질문에서 바로잡을 선후 관계를 묻습니다" }
    ]
  }]
)
```

"묶음 조정" 또는 "의존 관계 수정"을 선택하면 해당 작업이나 선후 관계를 후속 질문으로 묻고 답변을 기다린 뒤 계획을 수정하여 다시 확인한다. 원 질문 UI Other에 직접 입력한 조정 내용은 후속 질문 없이 받아 같은 확인 절차에 넣는다.

새 계획 제시 형식:

```
요구사항 30건을 5개 작업으로 묶었습니다.

  W00 기초 스키마·공통 모듈   공통      재고관리:FR-1~3   선행 없음
  W01 이관 이력 조회          재고관리   FR-4~6            W00 이후
  W02 분류 규칙 관리          재고관리   FR-7~9            W00 이후
  W03 정산 연동               정산      FR-1~3            W00 이후
  W04 통합 대시보드           통합      재고관리:FR-10    W01·W03 이후

W01·W02·W03은 서로 독립이므로 동시에 진행할 수 있습니다.
의존 근거: W00이 공통 테이블을 만들고 나머지가 이를 참조합니다.
```

재계획 제시 형식:

```
추가 요구사항 8건을 반영했습니다.

  유지  W02 분류 규칙 관리      FR-7~9      변경 없음
  겹침  W03 정산 연동           FR-1~3 → FR-1~3,FR-4   (FR-4가 같은 화면)
  폐기  W05 레거시 이관 배치     FR-25~26    원장에서 🚫
  완료  W06 코드 정리            FR-27       원장에서 ✅ (--sync 반영)
  완료  W04 사용량 수집 배치      FR-3        진행 → 완료 (feat/meter-batch 머지 확인)
  확인  W09 알림 설정            FR-35       요구사항은 모두 ✅, 브랜치 종료 확인 못함 — 완료로 바꿀까요?
  신규  W07 알림 연동           FR-32~34    W03 이후

  W00(완료)은 대상이 아니고, W01(진행)은 아직 작업 중이라 그대로 둡니다.
  주의: W08이 W05에 의존합니다 — 폐기 시 의존을 정리해야 합니다.
```

`BROKEN_REFS`가 있으면 같은 화면에 함께 보이고, 바로잡을 값을 후속 질문으로 받는다.

`PARTIAL_DISCARDS`의 제거할 ID와 `PLAN_ERRORS`의 중복 배정·의존 오류도 같은 제안에 포함한다. 오류를 해소할 값은 사용자에게 확인하며, 승인된 수정안이 P-8의 다섯 검사를 통과하기 전에는 저장하지 않는다. 기존 `진행`·`완료` 행을 바꿔야만 해소되는 오류는 자동 수정하지 않고 사유와 필요한 조정을 보고한다.

### P-8. 저장

**저장 전 공유 확인**: git 저장소면 `Read("../gx-work/references/dev-ignore-check.md")`의 `.dev` 공유 확인을 먼저 수행한다. `.dev/`가 git에서 무시되면 계획을 저장해도 커밋되지 않아 팀원이 같은 계획을 볼 수 없다. 사용자가 그대로 두기를 골라도 저장은 진행하고, P-9 안내에 "`.dev`가 무시되어 이 계획은 공유되지 않습니다"를 덧붙인다.

**기존 파일이 있으면 Write를 쓰지 않는다.** 저장 방식이 두 갈래다.

| 상황 | 방식 |
|------|------|
| `.dev/plan.md`가 없다 | `.dev/`를 만들고 `Write`로 새로 저장한다 |
| `.dev/plan.md`가 있다 | **`Edit`로 행을 추가·수정한다.** P-6의 보존 규칙을 따른다 |

`Write`는 파일을 통째로 대체하므로, 이미 `완료`·`진행` 상태인 행이 있는 계획에 쓰면 그 상태가 사라진다. 누군가 작업 중인 사실과 이미 끝난 이력이 함께 날아가므로, 기존 파일에는 절대 쓰지 않는다.

```markdown
# 작업 계획

| ID | 작업 | 도메인 | 요구사항 | 의존 | 작업 위치 | 상태 |
|----|------|--------|----------|------|-----------|------|
| W00 | 기초 스키마·공통 모듈 | 공통 | 재고관리:FR-1~3 | - | - | 대기 |
| W01 | 이관 이력 조회 | 재고관리 | FR-4~6 | W00 | - | 대기 |
```

작성 규칙:

- ID는 `W` + 두 자리 숫자. **하이픈을 넣지 않는다** — `config.json`의 `issueKey.pattern`(`^[A-Z]+-[0-9]+$`)에 매칭되면 파이프라인이 이를 이슈 키로 오인해 브랜치명이 오염된다
- 새 계획은 `W01`부터 매긴다. 다른 모든 작업의 선행인 `공통` 작업이 있으면 그 작업만 `W00`을 쓸 수 있다
- 새 행의 `작업 위치`는 착수 전이므로 `-`, `상태`는 `대기`
- **병렬군 열을 만들지 않는다.** 의존 열에서 계산되는 파생 정보이므로 저장하면 여러 사람이 동시에 완료할 때 같은 줄을 서로 덮어쓴다

**저장 후 검증**: 아래 다섯은 P-2의 변경 없음 판정 전 기존 계획, P-7에서 승인받은 저장 전 수정안, P-8에서 저장 후 다시 읽은 표에 동일하게 적용한다. 파이프라인의 phase-setup은 행을 찾을 뿐 그래프를 검사하지 않으므로 이 공통 마무리에서 검증을 마쳐야 한다. 변경이 없다는 이유로 검증을 건너뛰면 통과하지 못한 계획이 그대로 의존 확인의 근거가 된다.

- ID가 중복되지 않는다
- `의존` 열의 모든 ID가 표에 실제로 있다
- 자기 자신에 의존하거나 서로 물려 순환하지 않는다
- `폐기` 상태인 작업에 의존하는 행이 없다 (그 작업은 영영 시작할 수 없다)
- 원장의 모든 `⬜` 요구사항이 `폐기`가 아닌 행 하나에만 들어 있다 (빠지면 아무도 착수하지 않고, 둘에 들어가면 두 사람이 같은 일을 한다)

문제가 있으면 사용자에게 사유를 보고하고 수정 후 다시 저장한다.

설치 스킬 내부의 `scripts/plan.py`로 다섯 검사를 수행한다. 소비 프로젝트의 scripts/를 가정하지 않는다. 승인된 수정안을 별도 임시 표 파일에 작성한 경우 `--plan <임시 표 절대경로>`를 전달해 저장 전 검증하고, Edit 후에는 실제 `.dev/plan.md`를 다시 검사한다. 입력 원장·계획은 helper가 수정하지 않는다. `errors`가 있으면 저장/완료/다음 작업 추천을 중단하고 사유를 보고한다. 저장소 개발용 `python3 scripts/plan-lint.py .dev/plan.md`도 같은 설치 helper의 표 파서·그래프 검사 정본을 사용하며, CLI 경로와 종료 코드를 유지한다.

### P-9. 안내

변경한 계획 경로, 요구사항/작업 건수, 이번 변경과 필요한 미정만 짧게 안내한다. 묶음 기준은 파일 경계·기능 단위와 실제 의존 근거 중 이번 판단에 필요한 것만 한두 문장으로 덧붙인다. 사용법 전문을 매 실행마다 반복하지 않는다.

helper의 `ready`에 있는 대기 작업만 "지금 할 수 있는 작업"으로 안내한다. 미완료 의존은 `blocked`, 전체 폐기 후보는 `discard-candidates`, 일부 제거는 `partial-discards`, 종료 근거가 필요한 진행 작업은 `progress-review`로 구분해 ID와 사유를 보여준다. 계획 수정이나 상태 전환은 P-7 승인·P-6 보존 규칙을 따른다. `errors`가 하나라도 있으면 추천 목록을 비우고 먼저 바로잡을 항목만 안내한다. 동일 파일로 재실행해도 ID·원장 상태·작업 상태·작업 위치는 바꾸지 않는다.

```text
작업 계획 .dev/plan.md 갱신: 요구사항 8건 → 작업 3개.
변경: W02에 FR-4 추가, W07 신규. W01 완료 후 W02·W07 착수 가능.
미정: ❓ 담당자 (착수 판단에 영향 없음).
다음: gx-work에 목표·종료 지점·원장/계획 포인터를 인계합니다.
```

처음 만드는 계획이면 `"W01 시작해줘"`로 착수할 수 있다는 사용법 한 줄을 덧붙인다. 공유가 제한된 경우 P-8의 `.dev` 무시 경고를 표시한다. `Read("references/intake.md")`의 helper로 최종 인계를 만들고 호출자에게 경로와 관련 변경분만 반환한다. context-only면 여기서 종료한다. 실제 구현·검증·커밋·PR은 이 모드에서 시작하지 않는다.
