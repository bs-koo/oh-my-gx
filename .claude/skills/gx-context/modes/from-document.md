## 모드 C: 문서 기반 (--from)

요구사항 입력(`REQUIREMENT_INPUT`)을 읽어서 context를 생성하거나 갱신하고, 요구사항 원장과 작업 계획까지 반영한다. 입력은 `--from` 파일, 프롬프트에 직접 쓴 요구사항 본문, 또는 둘 다다. 문서 하나에 여러 업무 영역의 요구사항이 섞여 있어도 요구사항마다 도메인을 정해 나눈다.

### C-1. 입력 읽기

- `--from` 파일이 있으면 Read한다.
  - 지원 형식: `.md`, `.txt`, `.pdf` (PDF는 최대 20페이지)
  - 이미지 파일(`.png`, `.jpg`): Read로 멀티모달 분석
- 인라인 요구사항 본문이 있으면 그 텍스트를 그대로 입력으로 쓴다. 파일과 함께 오면 둘을 합친다.

### C-2. 내용 분석

입력에서 다음을 추출한다:
- **요구사항**: 기능 요구사항, 비기능 요구사항. 문장 하나에 요구가 둘 이상이면 나눈다.
- **도메인 배분**: 요구사항마다 속할 도메인을 정한다.
  - 인자로 도메인명이 지정되었으면 모든 요구사항을 그 도메인에 넣는다. 사용자가 범위를 정했기 때문이다.
  - 지정되지 않았으면 기존 `context/` 하위 도메인(스캔 직후라면 A-5에서 확정한 도메인)을 후보로 삼아 요구사항마다 가장 가까운 도메인을 고른다. 근거는 도메인 README의 범위, glossary의 용어, architecture의 패키지·화면이다.
  - 어느 후보에도 맞지 않는 요구사항끼리 업무 명사로 묶이면 새 도메인을 제안한다. 한두 건짜리 도메인을 억지로 만들지 말고 가장 가까운 기존 도메인을 우선한다.
  - 여러 도메인에 걸치는 요구사항은 주된 도메인 하나에 넣고, 작업 계획에서 `통합` 작업으로 묶을 후보로 표시한다.
- **배경/문제**, **용어**, **아키텍처**(시스템 구조, 기술 스택), **담당자**: 도메인별로 나누어 추출한다.

### C-3. 추출 결과 요약 및 검증 질문

#### C-3-1. 추출 결과 요약과 배분 확인

추출한 내용을 아래 형식으로 먼저 보여준다:

```
📄 요구사항 분석 결과

  도메인        요구사항   상태
  건물          FR 5건     기존 도메인 (원장 12건)
  계량기        FR 3건     기존 도메인 (원장 4건)
  평가결과      FR 4건     새 도메인

  용어 9건 · 아키텍처 언급 있음 · 담당자 ❓
```

기존 원장에 행이 있는 도메인이 하나라도 있으면 입력이 전체본인지 추가분인지 함께 확인한다. 전체본이면 아래에서 확정할 대체 범위 안에서 입력에서 사라진 기존 요구사항을 폐기 후보로 보고, 추가분이면 보지 않는다. 이 구분이 없으면 추가 요구 몇 건만 넣었을 때 나머지 기존 요구사항이 모두 폐기 후보로 올라온다.

```
AskUserQuestion(
  questions: [
    {
      header: "도메인 배분",
      question: "요구사항 {N}건을 위와 같이 도메인에 나눴습니다. 이대로 진행할까요?",
      multiSelect: false,
      options: [
        { label: "그대로 진행 (Recommended)", description: "제안한 도메인 배분으로 원장에 반영합니다" },
        { label: "배분 조정", description: "선택하면 후속 질문에서 옮길 요구사항과 도메인을 묻습니다" }
      ]
    },
    {
      header: "입력 성격",
      question: "이 입력은 기존 요구사항에 더하는 추가분인가요, 기존 요구사항 전체를 대신하는 전체본인가요?",
      multiSelect: false,
      options: [
        { label: "{추정 성격} (Recommended)", description: "추가분이면 기존 요구사항을 그대로 두고, 전체본이면 빠진 요구사항을 폐기 후보로 보여줍니다" },
        { label: "{나머지 성격}", description: "다른 쪽으로 처리합니다" }
      ]
    }
  ]
)
```

- 입력 성격 추정: 인라인 본문이거나 기존 원장 행 중 입력과 일치하는 행이 절반 미만이면 `추가분`, 절반 이상이면 `전체본`을 권장한다. 대상 도메인의 원장이 모두 비어 있으면 두 번째 질문은 빼고 `전체본`으로 둔다.
- 결과를 `INPUT_SCOPE`(`추가분`·`전체본`)로 둔다. 갱신 모드의 "요구사항 추가"에서 들어온 경우는 묻지 않고 `추가분`이다.
- "배분 조정"이면 옮길 요구사항과 도메인을 후속 질문으로 받고 실제 답변을 기다린 뒤 배분을 고쳐 다시 보여준다.

#### C-3-1-1. 전체본의 대체 범위

`INPUT_SCOPE`가 `전체본`이면 원장을 수정하기 전에 대체할 도메인 집합 `REPLACEMENT_DOMAINS`를 확정한다. **이번 입력에 요구사항이 배분된 도메인만으로 범위를 정하지 않는다.** 어떤 도메인의 요구사항이 전체본에서 통째로 빠지면 입력은 0건이지만 그 원장도 대조해야 한다.

- 사용자가 대체할 도메인을 이미 명시했으면 그 범위를 사용한다. 명시적 도메인 인자로 범위를 지정한 경우는 그 도메인으로 한정한다.
- 범위가 명확하지 않으면 기존 원장 도메인과 새 입력 도메인을 모두 보여주고, 각 도메인의 입력 건수(0건 포함)와 대체 대상·범위 밖 여부를 제안한다. `AskUserQuestion`으로 "제안 범위로 진행 (Recommended)" 또는 "범위 조정"을 묻는다. 조정은 후속 질문으로 받고 실제 답변을 기다린 뒤 범위를 확정한다. UI Other의 직접 입력은 그대로 받는다.
- 입력이 0건인 기존 도메인을 모두 자동 폐기 대상으로 삼지 않는다. 확인한 `REPLACEMENT_DOMAINS` 밖의 원장은 그대로 둔다. 새 입력이 확정한 범위 밖 도메인에 배분돼 있으면 범위나 배분을 먼저 다시 확인한다.

예: 기존 원장이 건물·계량기·정산이고 사용자가 "건물·계량기의 전체본"이라고 지정했는데 새 입력에는 건물만 있으면, 계량기도 입력 0건으로 대조하고 정산은 보존한다. 계량기의 미반영 행은 개별 제거 승인을 받은 뒤에만 폐기하며, 완료 행은 보존한다.

#### C-3-2. 순차 검증 질문 (새 도메인만)

C-3-1에서 **새 도메인**으로 정한 도메인마다 아래 5개 항목을 **1개씩 순차적으로** 질문한다. 이미 있는 도메인은 README가 있으므로 이 단계를 건너뛰고, 입력에서 바뀐 배경·용어·아키텍처만 C-4에서 변경 제안으로 다룬다. 요구사항 몇 건을 더할 때마다 다섯 질문을 다시 받으면 사람들이 이 경로를 쓰지 않게 된다.

입력에서 이미 파악된 항목은 확인형으로, 파악되지 않은 항목은 개방형으로 제시한다.

**질문 프레임 (순서대로)**:
1. **문제**: 이 도메인에서 풀려는 핵심 문제
2. **현재 프로세스**: 지금은 어떻게 하고 있는가
3. **사용자/규모**: 예상 사용자와 규모
4. **담당**: 이 도메인의 담당 PM/PO와 주요 개발자
5. **관련 레포**: 관련 GHE 레포

**순차 질문 루프** (모든 프레임이 완전히 해소될 때까지):

1. 현재 프레임을 `AskUserQuestion(questions: [질문 1개])`으로 제시한다. **확인형이든 개방형이든 권장 답변(입력에서 추출된 내용 또는 합리적 추정)을 options 첫 번째에 `(Recommended)` 라벨로 반드시 제시한다.**
   - **입력에서 추출된 항목** (확인형): "문서에서 '{추출 내용}'으로 파악했습니다. 맞나요?"
     ```
     options: [
       { label: "맞습니다 (Recommended)", description: "다음 항목으로 이동" },
       { label: "수정 필요", description: "선택하면 후속 질문에서 수정/보완 내용을 묻습니다" }
     ]
     ```
   - **입력에서 파악 안 된 항목** (개방형): `Read("modes/create.md")`의 B-2와 동일하게 권장 답변 + 모르겠음, 자유 입력은 UI Other
     ```
     options: [
       { label: "{권장 답변} (Recommended)", description: "권장 답변 설명" },
       { label: "모르겠음", description: "아직 불명확합니다" }
     ]
     ```

2. 답변을 평가한다. 확인형의 "수정 필요" 선택 시 후속 질문으로 수정 내용을 받고 실제 답변을 기다린다. 원 질문 UI Other의 자유 입력은 바로 받는다. 두 응답 모두 개방형과 같은 평가 규칙을 적용한다:
   - **명확하고 충분 (확인형 "맞습니다" 포함)**: 다음 프레임으로 이동
   - **모호하거나 불완전**: 파고들기 질문을 생성하여 현재 위치에 이어서 진행 (파고들기 질문에도 동일 규칙(권장 답변 또는 예시 후보, 자유 입력은 UI Other)이 적용된다)
   - **결정 의존성 발견**: 이 답변이 후속 프레임의 전제 또는 형태를 바꾸면, 영향받는 프레임을 재구성하거나 종속 질문을 추가한다.
   - **코드베이스로 답 가능**: 직접 탐색 후 확인하고 다음 프레임으로 이동
   - **"모르겠음" 선택**: ❓로 기록하고 다음 프레임으로 이동

3. 모든 프레임이 해소되면 **공유 이해 확인(align)** 단계를 거친다. `Read("modes/create.md")`의 B-2 align 절차와 동일하게 `Q → A` 요약을 `{ label: "맞습니다 (Recommended)" }` / `{ label: "수정 필요" }` 형태로 확인한다. "수정 필요" 시 `Q번호: 새 답변` 패턴 파싱 및 패턴 불일치 시 선택형 재질문 규칙도 `Read("modes/create.md")`의 B-2와 동일. "맞습니다"면 다음 새 도메인으로, 모두 끝나면 C-4로 진행한다. "수정 필요"면 해당 프레임을 재질문하여 루프 재진입한다.

**모호함 판단 기준 및 파고들기 방식**: `Read("modes/create.md")`의 B-2와 동일하게 적용한다.

### C-4. context 생성 또는 갱신

C-3-1에서 확정한 대상 도메인마다 수행한다.

- **`context/{도메인}/`이 없으면**: `Read("modes/create.md")`의 B-5~B-11 절차로 디렉토리와 문서를 생성한다. 다만 Q&A 답변 대신 입력에서 추출한 내용과 C-3-2 답변을 사용한다. `context/`가 아예 없으면 B-0부터 수행한다.
- **`context/{도메인}/`이 이미 있으면**: `Read("modes/update.md")`의 변경 제안·반영 절차(D-3~D-4)로 진행한다. 입력 내용과 기존 context를 비교하여 용어·아키텍처·배경의 변경 제안을 생성한다. 바뀐 것이 없으면 제안 없이 넘어간다.

**모든 대상 도메인의 context 문서 작업이 끝나면 C-4-1을 반드시 실행한 뒤 C-5로 이어서 진행한다.** 모드 B·D로 위임해도 이 경로는 요구사항 원장과 작업계획을 만들기 전에는 끝나지 않는다.

### C-4-1. 요구사항 원장 반영

추가분이면 입력을 배분한 대상 도메인마다, 전체본이면 `REPLACEMENT_DOMAINS`의 모든 도메인마다 아래를 수행한다. **입력 요구사항이 0건인 대체 대상도 생략하지 않는다.** 그 도메인은 빈 입력 목록과 기존 원장을 비교하여 7번의 폐기 제안을 수행한다. 범위 밖 원장은 수정하지 않으며, 원장 ID는 도메인마다 따로 매긴다.

C-2에서 그 도메인에 배분한 각 요구사항을 `{ id, type, text, ac, status, pr }`로 정규화하여 `LEDGER_REQUIREMENTS`를 만든다. type은 기능이면 `FR`, 비기능이면 `NFR`; 새 항목의 ac·pr은 `-`, status는 `⬜`다.

`context/{도메인}/status.md`의 `## 요구사항 원장` 표를 Read하고 다음 순서로 병합한다.

ID 일치와 핵심 문장 일치 모두 기존 ID·AC·상태·PR을 유지하고 승인된 요구사항 문장만 갱신한다.

1. 입력 ID를 유형과 `FR-N`·`NFR-N` 형식에 맞춰 검증하고 입력 전체의 ID 출현 횟수를 센다. 유효하지 않거나 입력 안에서 중복된 ID는 먼저 제거하여 ID 없는 후보로 정규화한다. 따라서 `REQ-42` 같은 비정본 ID와 중복된 `FR-1` 후보는 ID 일치 경로에 들어가지 않는다.
2. 기존 원장의 모든 ID와 입력에서 유효하고 고유한 ID를 먼저 예약하여 `RESERVED_LEDGER_IDS` 집합을 만든다.
3. 유효한 ID가 남은 각 후보를 아직 연결되지 않은 기존 행과 비교한다. 입력 ID가 기존 행의 ID와 같으면 같은 항목으로 본다.
4. 아직 매칭되지 않은 ID 없는 후보는 공백·문장부호를 제거한 핵심 문장을 아직 연결되지 않은 모든 기존 행과 비교한다. ID 매칭과 핵심 문장 매칭 모두 기존 행 하나와 후보 하나만 일대일로 연결한다. `REQ-42`로 같은 문서를 다시 분석해도 핵심 문장이 같으면 기존 FR/NFR ID를 유지하며, 중복된 `FR-1` 후보 둘을 하나의 기존 행에 모두 매칭하지 않는다.
5. 기존 행과 연결된 후보는 기존 ID·AC·상태·PR을 유지한다. 기존 원장에 없는 유효하고 고유한 입력 ID는 그대로 사용하며, 예를 들어 기존 원장에 `NFR-2`가 없고 입력에서 한 번만 나오면 `NFR-2`는 그대로 유지한다.
6. 모든 기존 행과 후보의 일대일 매칭을 마친 뒤 미매칭 후보에만 자동 ID를 할당한다. 예약 집합의 유형별 최댓값 다음 번호를 사용하고 할당 즉시 `RESERVED_LEDGER_IDS`에 추가하며, 삭제된 번호를 재사용하지 않는다. 예: 기존 `FR-1` + 입력 `FR-2` + ID 없는 FR → `FR-2`, `FR-3`.
7. `INPUT_SCOPE`가 `전체본`일 때만, 입력에서 사라진 기존 `⬜` 행을 변경 제안에 포함하고 사용자가 제거를 승인한 경우에만 `🚫`로 바꾼다. `추가분`이면 입력에 없는 기존 행은 판정하지 않고 그대로 둔다. `✅` 행은 어느 경우에도 자동 폐기하지 않는다.
8. Edit 전에 제안 표의 ID 중복을 검사하고, 완성된 제안 표를 변경 전 스냅샷의 모든 기존 행과 비교한다. 기존 `✅` 행의 ID·AC·상태·PR이 변경되면 Edit하지 않는다.
9. 매칭과 번호 할당이 끝나면 `LEDGER_REQUIREMENTS`의 각 객체를 최종 `{ id, type, text, ac, status, pr }`로 갱신한다.
10. Edit으로 기존 행을 수정하고 새 행을 표 끝에 추가한다. 기존 파일 전체를 Write로 덮어쓰지 않는다.
11. 저장한 표를 다시 읽어 같은 객체 형태로 정규화하고 ID 중복, 빈 요구사항, 허용되지 않은 상태, 기존 `✅` 행의 ID·AC·상태·PR 변경이 없는지 확인한다. 저장한 표의 행과 `LEDGER_REQUIREMENTS`가 일치하는지 같은 ID끼리 대조하고, 각 객체의 id·type·text·ac·status·pr 중 하나라도 일치하지 않으면 C-5로 진행하지 않는다.

C-5는 `LEDGER_REQUIREMENTS`의 ID만 `plan.md` 요구사항 열에 기록한다. C-2의 임시 번호나 원문에 없는 새 ID를 계획에 쓰지 않는다.

### C-5. 작업 계획 갱신

모든 대상 도메인의 C-4-1이 검증까지 통과하면 `Read("modes/plan.md")`의 작업 계획 갱신(P-0~P-9)을 실행한다. 도메인별 `LEDGER_REQUIREMENTS`의 요구사항 항목 ID를 `CHANGED_IDS`로 넘긴다.

작업 계획은 이 모드 전용 절차가 아니다. 갱신·신규·스캔·동기화 모드도 같은 파일로 계획을 맞춘다. 이 모드에서 계획을 따로 만들지 않고 공통 절차에 맡기는 이유는, 판정 기준이 경로마다 달라지면 같은 원장에서 다른 계획이 나오기 때문이다. 그래서 SKILL.md의 공통 마무리가 이 모드 뒤에 같은 절차를 다시 실행하지 않도록, 이 모드에서 P-9까지 마쳤으면 공통 마무리는 건너뛴다.
