## 모드 C: 문서 기반 (--from)

PM이 정리한 텍스트 파일을 읽어서 context를 생성하거나 갱신한다.

### C-1. 파일 읽기

`--from` 으로 지정된 파일을 Read한다.
- 지원 형식: `.md`, `.txt`, `.pdf` (PDF는 최대 20페이지)
- 이미지 파일(`.png`, `.jpg`): Read로 멀티모달 분석

### C-2. 내용 분석

파일 내용에서 다음을 추출한다:
- **도메인명**: 문서 제목이나 주제에서 추론. 인자로 도메인명이 지정되었으면 그것을 사용.
- **배경/문제**: 프로젝트 배경, 현재 문제점
- **요구사항**: 기능 요구사항, 비기능 요구사항
- **용어**: 도메인 특화 용어와 정의
- **아키텍처**: 시스템 구조, 기술 스택 언급
- **담당자**: 문서에 명시된 담당자 정보

### C-3. 추출 결과 요약 및 검증 질문

#### C-3-1. 추출 결과 요약 제시

문서에서 추출한 내용을 아래 형식으로 사용자에게 먼저 보여준다:

```
📄 문서 분석 결과

- 도메인명: {추론한 도메인명 또는 ❓}
- 배경/문제: {추출한 내용 요약 또는 ❓}
- 요구사항: {추출한 FR/NFR 수} 건
- 용어: {추출한 용어 수} 건
- 아키텍처: {추출 여부}
- 담당자: {추출한 정보 또는 ❓}
```

#### C-3-2. 순차 검증 질문

아래 5개 항목을 **1개씩 순차적으로** 질문한다. 문서에서 이미 파악된 항목은 확인형으로, 파악되지 않은 항목은 개방형으로 제시한다.

**질문 프레임 (순서대로)**:
1. **문제**: 이 도메인에서 풀려는 핵심 문제
2. **현재 프로세스**: 지금은 어떻게 하고 있는가
3. **사용자/규모**: 예상 사용자와 규모
4. **담당**: 이 도메인의 담당 PM/PO와 주요 개발자
5. **관련 레포**: 관련 GHE 레포

**순차 질문 루프** (모든 프레임이 완전히 해소될 때까지):

1. 현재 프레임을 `AskUserQuestion(questions: [질문 1개])`으로 제시한다. **확인형이든 개방형이든 권장 답변(문서에서 추출된 내용 또는 합리적 추정)을 options 첫 번째에 `(Recommended)` 라벨로 반드시 제시한다.**
   - **문서에서 추출된 항목** (확인형): "문서에서 '{추출 내용}'으로 파악했습니다. 맞나요?"
     ```
     options: [
       { label: "맞습니다 (Recommended)", description: "다음 항목으로 이동" },
       { label: "수정 필요", description: "선택하면 후속 질문에서 수정/보완 내용을 묻습니다" }
     ]
     ```
   - **문서에서 파악 안 된 항목** (개방형): `Read("modes/create.md")`의 B-2와 동일하게 권장 답변 + 모르겠음, 자유 입력은 UI Other
     ```
     options: [
       { label: "{권장 답변} (Recommended)", description: "권장 답변 설명" },
       { label: "모르겠음", description: "아직 불명확합니다" }
     ]
     ```

2. 답변을 평가한다. 확인형의 "수정 필요" 선택 시 후속 질문으로 수정 내용을 받고 실제 답변을 기다린다. 원 질문 UI Other의 자유 입력은 바로 받는다. 두 응답 모두 개방형과 같은 평가 규칙을 적용한다:
   - **명확하고 충분 (확인형 "맞습니다" 포함)**: 다음 프레임으로 이동
   - **모호하거나 불완전**: 파고들기 질문을 생성하여 현재 위치에 이어서 진행 (파고들기 질문에도 동일 규칙(권장 답변 또는 예시 후보, 자유 입력은 UI Other)이 적용된다)
   - **결정 의존성 발견**: 이 답변이 후속 프레임의 전제 또는 형태를 바꾸면, 영향받는 프레임을 재구성하거나 종속 질문을 추가한다.
   - **코드베이스로 답 가능**: 직접 탐색 후 확인하고 다음 프레임으로 이동
   - **"모르겠음" 선택**: ❓로 기록하고 다음 프레임으로 이동

3. 모든 프레임이 해소되면 **공유 이해 확인(align)** 단계를 거친다. `Read("modes/create.md")`의 B-2 align 절차와 동일하게 `Q → A` 요약을 `{ label: "맞습니다 (Recommended)" }` / `{ label: "수정 필요" }` 형태로 확인한다. "수정 필요" 시 `Q번호: 새 답변` 패턴 파싱 및 패턴 불일치 시 선택형 재질문 규칙도 `Read("modes/create.md")`의 B-2와 동일. "맞습니다"면 C-4로 진행. "수정 필요"면 해당 프레임을 재질문하여 루프 재진입한다.

**모호함 판단 기준 및 파고들기 방식**: `Read("modes/create.md")`의 B-2와 동일하게 적용한다.

### C-4. context 생성 또는 갱신

- **`context/{도메인}/`이 없으면**: `Read("modes/create.md")`의 B-5~B-11 절차로 디렉토리와 문서를 생성한다. 다만 Q&A 답변 대신 파일에서 추출한 내용을 사용한다.
- **`context/{도메인}/`이 이미 있으면**: `Read("modes/update.md")`의 변경 제안·반영 절차로 진행한다. 파일 내용과 기존 context를 비교하여 변경 제안을 생성한다.

**두 경우 모두 context 문서 작업이 끝나면 C-4-1을 반드시 실행한 뒤 C-5로 이어서 진행한다.** 모드 B·D로 위임해도 `--from` 경로는 요구사항 원장과 작업계획을 만들기 전에는 끝나지 않는다.

### C-4-1. 요구사항 원장 반영

C-2에서 추출한 각 요구사항을 `{ id, type, text, ac, status, pr }`로 정규화하여 `LEDGER_REQUIREMENTS`를 만든다. type은 기능이면 `FR`, 비기능이면 `NFR`; 새 항목의 ac·pr은 `-`, status는 `⬜`다.

`context/{도메인}/status.md`의 `## 요구사항 원장` 표를 Read하고 다음 순서로 병합한다.

ID 일치와 핵심 문장 일치 모두 기존 ID·AC·상태·PR을 유지하고 승인된 요구사항 문장만 갱신한다.

1. 입력 ID를 유형과 `FR-N`·`NFR-N` 형식에 맞춰 검증하고 입력 전체의 ID 출현 횟수를 센다. 유효하지 않거나 입력 안에서 중복된 ID는 먼저 제거하여 ID 없는 후보로 정규화한다. 따라서 `REQ-42` 같은 비정본 ID와 중복된 `FR-1` 후보는 ID 일치 경로에 들어가지 않는다.
2. 기존 원장의 모든 ID와 입력에서 유효하고 고유한 ID를 먼저 예약하여 `RESERVED_LEDGER_IDS` 집합을 만든다.
3. 유효한 ID가 남은 각 후보를 아직 연결되지 않은 기존 행과 비교한다. 입력 ID가 기존 행의 ID와 같으면 같은 항목으로 본다.
4. 아직 매칭되지 않은 ID 없는 후보는 공백·문장부호를 제거한 핵심 문장을 아직 연결되지 않은 모든 기존 행과 비교한다. ID 매칭과 핵심 문장 매칭 모두 기존 행 하나와 후보 하나만 일대일로 연결한다. `REQ-42`로 같은 문서를 다시 분석해도 핵심 문장이 같으면 기존 FR/NFR ID를 유지하며, 중복된 `FR-1` 후보 둘을 하나의 기존 행에 모두 매칭하지 않는다.
5. 기존 행과 연결된 후보는 기존 ID·AC·상태·PR을 유지한다. 기존 원장에 없는 유효하고 고유한 입력 ID는 그대로 사용하며, 예를 들어 기존 원장에 `NFR-2`가 없고 입력에서 한 번만 나오면 `NFR-2`는 그대로 유지한다.
6. 모든 기존 행과 후보의 일대일 매칭을 마친 뒤 미매칭 후보에만 자동 ID를 할당한다. 예약 집합의 유형별 최댓값 다음 번호를 사용하고 할당 즉시 `RESERVED_LEDGER_IDS`에 추가하며, 삭제된 번호를 재사용하지 않는다. 예: 기존 `FR-1` + 입력 `FR-2` + ID 없는 FR → `FR-2`, `FR-3`.
7. 기존 입력에서 사라진 `⬜` 행은 변경 제안에 포함하고 사용자가 제거를 승인한 경우에만 `🚫`로 바꾼다. `✅` 행은 자동 폐기하지 않는다.
8. Edit 전에 제안 표의 ID 중복을 검사하고, 완성된 제안 표를 변경 전 스냅샷의 모든 기존 행과 비교한다. 기존 `✅` 행의 ID·AC·상태·PR이 변경되면 Edit하지 않는다.
9. 매칭과 번호 할당이 끝나면 `LEDGER_REQUIREMENTS`의 각 객체를 최종 `{ id, type, text, ac, status, pr }`로 갱신한다.
10. Edit으로 기존 행을 수정하고 새 행을 표 끝에 추가한다. 기존 파일 전체를 Write로 덮어쓰지 않는다.
11. 저장한 표를 다시 읽어 같은 객체 형태로 정규화하고 ID 중복, 빈 요구사항, 허용되지 않은 상태, 기존 `✅` 행의 ID·AC·상태·PR 변경이 없는지 확인한다. 저장한 표의 행과 `LEDGER_REQUIREMENTS`가 일치하는지 같은 ID끼리 대조하고, 각 객체의 id·type·text·ac·status·pr 중 하나라도 일치하지 않으면 C-5로 진행하지 않는다.

C-5는 `LEDGER_REQUIREMENTS`의 ID만 `plan.md` 요구사항 열에 기록한다. C-2의 임시 번호나 원문에 없는 새 ID를 계획에 쓰지 않는다.

### C-5. 작업 계획(.dev/plan.md) 생성

요구사항이 **2건 이상**이면 작업 계획을 함께 만든다. 1건이면 건너뛴다 (계획을 세울 대상이 없다).

status.md가 요구사항 항목별 진행을 추적한다면, 작업 계획은 그 항목들을 **개발 단위로 묶고 실행 순서를 정한다**. 항목이 흩어져 있으면 무엇을 먼저 하고 무엇을 동시에 해도 되는지 알 수 없다.

#### C-5-1. 작업 묶기

`LEDGER_REQUIREMENTS`의 요구사항 항목을 작업으로 묶는다.

- 한 작업은 **AC 3~5개로 환산 가능한 크기**여야 한다 (gx-dev·gx-tdd의 AC 상한과 맞춘다)
- 화면·기능·컴포넌트 단위로 묶는다
- **파일 경계가 겹치지 않도록** 나눈다 — 겹치면 나중에 여러 사람이 동시에 작업할 수 없다
- 도메인을 가로지르지 않는다. 여러 도메인이 걸리는 작업만 예약 도메인 `통합`을 쓴다

#### C-5-2. 의존 판정

아래를 선행 작업으로 본다.

- 스키마·공통 모듈을 만드는 작업 (다른 작업이 그 테이블·타입을 쓴다)
- 데이터를 생산하는 작업 (소비하는 작업보다 앞선다)
- 인증·권한 기반 (보호 대상 기능보다 앞선다)

**근거 없이 의존을 만들지 않는다.** 판정 근거를 표 아래 각주로 남긴다. 확신이 없으면 의존을 비우고 C-5-4의 확인 게이트에서 사용자에게 묻는다.

#### C-5-3. 예약 도메인

도메인에 속하지 않는 작업은 아래 예약어를 쓴다. 이 둘은 `context/{도메인}/` 디렉토리를 만들지 않으며, 파이프라인도 context를 읽지 않는다.

| 값 | 의미 |
|----|------|
| `공통` | 스키마·기반 모듈 등 도메인 이전의 선행 작업 |
| `통합` | 여러 도메인이 걸리는 작업 |

#### C-5-4. 확인 게이트

의존 판정은 추론이므로 저장 전에 반드시 확인받는다.

```
AskUserQuestion(
  questions: [{
    header: "작업 계획",
    question: "요구사항 {N}건을 {M}개 작업으로 묶었습니다. 이대로 저장할까요?",
    multiSelect: false,
    options: [
      { label: "그대로 저장", description: "제안된 묶음과 의존 관계를 그대로 반영합니다" },
      { label: "묶음 조정", description: "선택하면 후속 질문에서 합치거나 나눌 작업을 묻습니다" },
      { label: "의존 관계 수정", description: "선택하면 후속 질문에서 바로잡을 선후 관계를 묻습니다" }
    ]
  }]
)
```

"묶음 조정" 또는 "의존 관계 수정"을 선택하면 해당 작업이나 선후 관계를 후속 질문으로 묻고 답변을 기다린 뒤 계획을 수정하여 다시 확인한다. 원 질문 UI Other에 직접 입력한 조정 내용은 후속 질문 없이 받아 같은 확인 절차에 넣는다.

제시 형식:

```
요구사항 30건을 5개 작업으로 묶었습니다.

  W00 기초 스키마·공통 모듈   공통      FR-1~3     선행 없음
  W01 이관 이력 조회          재고관리   FR-4~6     W00 이후
  W02 분류 규칙 관리          재고관리   FR-7~9     W00 이후
  W03 정산 연동               정산      FR-20~22   W00 이후
  W04 통합 대시보드           통합      FR-30      W01·W03 이후

W01·W02·W03은 서로 독립이므로 동시에 진행할 수 있습니다.
의존 근거: W00이 공통 테이블을 만들고 나머지가 이를 참조합니다.
```

#### C-5-5. 저장

**기존 파일이 있으면 Write를 쓰지 않는다.** 저장 방식이 두 갈래다.

| 상황 | 방식 |
|------|------|
| `.dev/plan.md`가 없다 | `.dev/`를 만들고 `Write`로 새로 저장한다 |
| `.dev/plan.md`가 있다 | **`Edit`로 행을 추가·수정한다.** 아래 C-5-6의 보존 규칙을 따른다 |

`Write`는 파일을 통째로 대체하므로, 이미 `완료`·`진행` 상태인 행이 있는 계획에 쓰면 그 상태가 사라진다. 누군가 작업 중인 사실과 이미 끝난 이력이 함께 날아가므로, 기존 파일에는 절대 쓰지 않는다.

```markdown
# 작업 계획

| ID | 작업 | 도메인 | 요구사항 | 의존 | 작업 위치 | 상태 |
|----|------|--------|----------|------|-----------|------|
| W00 | 기초 스키마·공통 모듈 | 공통 | FR-1~3 | - | - | 대기 |
| W01 | 이관 이력 조회 | 재고관리 | FR-4~6 | W00 | - | 대기 |
```

작성 규칙:

- ID는 `W` + 두 자리 숫자. **하이픈을 넣지 않는다** — `config.json`의 `issueKey.pattern`(`^[A-Z]+-[0-9]+$`)에 매칭되면 파이프라인이 이를 이슈 키로 오인해 브랜치명이 오염된다
- `작업 위치`는 착수 전이므로 전부 `-`
- `상태`는 전부 `대기`
- **병렬군 열을 만들지 않는다.** 의존 열에서 계산되는 파생 정보이므로 저장하면 여러 사람이 동시에 완료할 때 같은 줄을 서로 덮어쓴다

**저장 후 검증**: 저장한 표를 훑어 아래 넷을 직접 확인한다. 파이프라인의 phase-setup은 행을 찾을 뿐 그래프를 검사하지 않으므로 **이 시점이 유일한 검증 지점**이며, 통과하지 못한 계획이 그대로 의존 확인의 근거가 된다.

- ID가 중복되지 않는다
- `의존` 열의 모든 ID가 표에 실제로 있다
- 자기 자신에 의존하거나 서로 물려 순환하지 않는다
- `폐기` 상태인 작업에 의존하는 행이 없다 (그 작업은 영영 시작할 수 없다)

문제가 있으면 사용자에게 사유를 보고하고 수정 후 다시 저장한다. 재계획(C-5-6) 시에도 같은 확인을 수행한다.

이 확인을 스크립트에 맡기지 않는 이유는 설치 구조 때문이다. 플러그인이 설치된 소비 프로젝트에서는 작업 디렉토리에 `scripts/`가 없어 어떤 경로를 조립해도 닿지 않는다. 다만 **플러그인 저장소에서 직접 작업 중이라면** `python3 scripts/plan-lint.py .dev/plan.md`로 같은 검사를 기계적으로 돌릴 수 있다.

#### C-5-6. 재계획 (plan.md가 이미 있을 때)

기존 계획을 덮어쓰지 않는다. C-5-5의 저장 분기(`Edit` 사용)와 함께 적용된다 — 방식만 지키고 아래 보존 규칙을 어기면 행이 사라지는 것은 같다.

**먼저 상태로 손댈 수 있는 범위를 가른다.**

| 상태 | 처리 |
|------|------|
| `완료` | 건드리지 않는다 — 이미 코드가 들어갔다 |
| `진행` | 건드리지 않는다 — 누군가 작업 중이다 |
| `대기` | 재조정 대상 |

**그다음 대기 작업 각각을 새 요구사항과 대조해 셋 중 하나로 판정한다.**

| 판정 | 조건 | 처리 |
|------|------|------|
| **유지** | 요구사항이 그대로 살아 있다 | 변경 없음 |
| **겹침** | 새 요구사항이 기존 작업의 범위에 들어간다 | 기존 행의 `요구사항` 열을 확장한다. 새 행을 만들지 않는다 — 같은 파일을 건드리는 작업이 둘로 갈리면 병렬 배분이 깨진다 |
| **폐기** | 요구사항이 삭제되어 할 일이 없어졌다 | `상태`를 `폐기`로 바꾼다. 행을 지우지 않는다 — 왜 사라졌는지가 git 이력에만 남으면 나중에 추적이 어렵다 |

새 요구사항에서 나온 작업은 뒤에 추가한다. 변경 내역은 git이 기록하므로 파일 안에 시점별 이력을 쌓지 않는다.

**완료·진행 작업의 요구사항이 폐기된 경우**는 상태를 되돌리지 않는다. 이미 들어간 코드를 걷어내는 것은 별개의 작업이므로, 필요하면 제거 작업을 새 행으로 추가한다. 완료를 `폐기`로 뒤집으면 "무엇이 언제 들어갔는지"가 사라진다.

**폐기된 작업은 의존 대상이 될 수 없다.** 다른 작업이 폐기된 작업에 의존하고 있으면 그 의존을 끊거나 대체 작업으로 바꿔야 한다. 확인 게이트에서 함께 제시한다.

### 판정 결과 제시

```
추가 요구사항 8건을 분석했습니다.

  유지  W02 분류 규칙 관리      FR-7~9      변경 없음
  겹침  W03 정산 연동           FR-20~22 → FR-20~22,FR-31   (FR-31이 같은 화면)
  폐기  W05 레거시 이관 배치     FR-25~26    요구사항 삭제됨
  신규  W06 알림 연동           FR-32~34

  W00(완료)·W01(진행)은 대상이 아닙니다.
  주의: W07이 W05에 의존합니다 — 폐기 시 의존을 정리해야 합니다.
```

#### C-5-7. 안내

저장 후 **무엇을 어떤 기준으로 정리했고 어떻게 쓰는지**를 함께 안내한다. 처음 쓰는 사용자는 계획 파일이 생겼다는 사실만으로는 무엇을 할 수 있는지 모른다. **판정 기준을 함께 안내**해 사용자가 결과를 검토할 수 있게 한다.

```
작업 계획을 .dev/plan.md에 저장했습니다. 요구사항 30건 → 작업 5개.

무엇을 기준으로 묶었나
  · 한 작업 = 테스트 3~5개로 끝낼 수 있는 크기
  · 화면·기능 단위로, 서로 파일이 겹치지 않게
  · 공통 스키마를 만드는 작업은 앞으로 (나머지가 그 테이블을 참조합니다)

이제 이렇게 쓰면 됩니다
  "W00 시작해줘"        첫 작업을 시작합니다. 도메인과 요구사항은 말하지 않아도 됩니다
  "지금 뭐 할 수 있어?"  선행이 끝난 작업을 골라 알려줍니다
  "작업 계획 보여줘"     현재 진행 상황을 표로 봅니다

여러 명이 나눠 한다면
  W01·W02·W03은 서로 독립이라 W00이 끝난 뒤 동시에 진행할 수 있습니다.
  각자 "W01 시작해줘"처럼 부르면 착수 사실이 바로 공유되어 중복을 막습니다.

이 파일은 저장소에 함께 커밋되므로 팀원이 git pull 후 같은 계획을 봅니다.
```

계획이 1~2개 작업으로만 나왔다면 마지막 두 블록(여러 명·병렬)은 생략한다 — 나눌 것이 없는데 배분을 안내하면 혼란만 준다.
