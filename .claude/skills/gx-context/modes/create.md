## 모드 B: 신규 (Q&A 기반)

Q&A 기반으로 새 도메인을 생성한다.

### B-0. context/ 디렉토리 초기화

프로젝트 루트에 `context/` 디렉토리가 없으면 자동 생성한다:

1. `test -d context/` 로 존재 여부 확인
2. 존재하지 않으면:
   - `mkdir -p context/`
   - `context/README.md` 생성 (도메인 목록 인덱스 템플릿):
     ```markdown
     # 프로젝트 컨텍스트

     도메인 지식, 아키텍처, 용어 사전을 정리하는 공간입니다.

     ## 도메인

     | 도메인 | 설명 | 상세 |
     |--------|------|------|

     ## 공통

     - [공통 용어 사전](glossary.md)
     ```
   - `context/glossary.md` 생성 (공통 용어 사전 스켈레톤):
     ```markdown
     # 공통 용어 사전

     > 도메인을 가리지 않고 프로젝트 전체에서 쓰이는 용어입니다.
     > 도메인별 용어는 `context/{도메인}/glossary.md`를 참조하세요.

     | 용어 | 설명 |
     |------|------|
     ```
3. 이미 존재하면 건너뛴다.

### B-1. 도메인 확인

- 인자로 도메인명이 주어지면 그대로 사용한다.
- 인자가 없으면 다음과 같이 묻는다:
  ```
  AskUserQuestion(
    questions: [{
      header: "도메인명",
      question: "등록할 도메인명과 한 줄 설명을 입력해주세요. (예: payment — 결제 처리)",
      multiSelect: false,
      options: [
        { label: "{추정 도메인명} (Recommended)", description: "코드베이스에서 추정한 도메인명과 설명을 사용합니다" },
        { label: "취소", description: "도메인 등록을 중단합니다" }
      ]
    }]
  )
  ```
- 추정 도메인명이 있으면 첫 번째 후보로 채우고, 다른 도메인명과 설명은 UI Other로 입력받는다. 실제 후보가 없으면 자연어로 도메인명과 설명을 물어 답변을 기다린다.
- `context/{도메인}/`이 이미 존재하면 다음과 같이 묻는다:
  ```
  AskUserQuestion(
    questions: [{
      header: "기존 도메인",
      question: "'{도메인}'은 이미 존재합니다. 어떻게 진행할까요?",
      multiSelect: false,
      options: [
        { label: "갱신", description: "기존 도메인의 context를 갱신합니다 (모드 D)" },
        { label: "취소", description: "작업을 중단합니다" }
      ]
    }]
  )
  ```
  - "갱신" → `Read("modes/update.md")` 후 모드 D를 실행하고 모드 B를 종료한다.
  - "취소" → 작업을 종료한다.

### B-2. 공통 정보 점검과 필요한 질문

`Read("references/intake.md")`로 대화·문서 공통 정규화와 질문 선별을 수행한다. 문제, 현재 프로세스, 안 하면 생기는 영향, 사용자/규모, 담당은 정보 점검표다. 앞선 대화·문서·기존 context에 근거가 있으면 채우고 다시 묻지 않는다.

- 범위·동작·설계 제약·인수 기준을 정할 수 없는 항목만 질문한다. 독립 질문은 최대 3개씩 묶고, 답에 종속되는 질문만 순차로 묻는다.
- 담당자·배경 수치 등 비차단 미정은 ❓로 남긴다. 모르겠다는 응답을 합리적 추정값으로 채우지 않는다.
- 추론한 내용과 출처를 결정 기록에 남긴다. 사용자가 내부 선택을 맡긴 범위는 반복 확인하지 않는다. 별도 전체 다섯 항목 align 승인은 요청하지 않는다.
- 차단 질문의 실제 답변을 받기 전에는 그 결정에 의존하는 원장·계획을 확정하지 않는다. 독립적인 정보 정리는 계속할 수 있다.

### B-4. 관련 프로젝트 확인

현재 저장소·문서에 명확한 관련 레포는 근거와 함께 기록한다. 관련 레포를 모르면 빈 테이블이나 ❓로 두고 진행한다. 레포 선택에 따라 수정 대상·배포 범위가 달라지는데 선택이 미정인 경우에만 `references/intake.md`의 중요 질문으로 묻는다.

### B-5. 디렉토리 및 문서 생성

`mkdir -p context/{도메인}/` 로 도메인 디렉토리를 생성한다.

```
context/{도메인}/
├── README.md          ← 검증 질문 답변 정리
├── PROJECTS.md        ← 관련 프로젝트(레포) 목록
├── glossary.md        ← 용어 사전 스켈레톤
├── architecture.md    ← 전체 구조 요약 + 주제 문서 링크 (인덱스)
└── status.md          ← 구현 추적
```

### B-6. README.md 작성

검증 질문 답변을 아래 구조로 정리한다:

```markdown
# {도메인명}

{한 줄 설명}

## 배경

{문제 + 현재 프로세스를 서술형으로 정리}

## 안 하면 어떻게 되는가

{답변 정리. 근거 있는 정량 수치만 포함, 미확인 시 ❓}

## 사용자와 규모

{누가, 몇 명, 얼마나 자주}

## 성공 기준

{정량적 기준. 미확인 시 ❓ 표기}

## 담당자

| 역할 | 이름 | 비고 |
|------|------|------|
| PM/PO | {이름} | |
| 개발 리드 | {이름} | |

## 현재 상태

탐색 중
```

- 답변에서 ❓인 항목은 그대로 ❓로 남긴다.
- 사용자의 답변을 과도하게 다듬지 않는다. 핵심만 정리.
- `배경`·`안 하면 어떻게 되는가`·`사용자와 규모`·`성공 기준` 네 절은 gx-tdd가 PRD를 작성할 때 product-owner에 주입한다(gx-work를 거친 실행도 PRD는 gx-tdd가 쓴다). 수치를 남길수록 AC의 검증값이 구체적이 된다.

### B-9-1. status.md 작성

```markdown
# {도메인명} 구현 추적

> PRD 요구사항별 구현 상태를 추적합니다.

## 범례

- ✅ 반영됨 — 코드에 구현 완료
- ⬜ 미반영 — 정책/설계만 확정, 코드 미구현
- 🚫 폐기 — 승인된 문서 갱신에서 제거됨

## 요구사항 원장

| ID | 요구사항 | AC | 상태 | PR |
|---|---|---|---|---|

작성 규칙:
- ID는 기능 요구사항 `FR-N`, 비기능 요구사항 `NFR-N` 형식이다.
- 입력 문서의 ID가 유효하고 중복되지 않으면 유지한다.
- ID가 없거나 중복이면 유형별 기존 최댓값 다음 번호를 부여하며 삭제된 번호를 재사용하지 않는다.
- AC가 연결되기 전과 구현 근거가 없을 때는 각각 `-`를 쓴다.

-->
```
