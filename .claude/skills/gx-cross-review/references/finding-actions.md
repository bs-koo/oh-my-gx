### 5-1. 처리 대상 식별

결과에서 실제 수정이 필요한 항목을 모은다. advisor 의견은 미검증 주장이다. 근거 부족과 실제 결함을 구분하고, AC·코드·재현 근거가 없는 항목은 먼저 확인한다. 사용자가 검토만 요청했다면 결과를 보고하고 종료한다.

### 5-2. 수정 범위 결정

사용자가 이번 발견 항목의 수정을 이미 명시했다면 그 범위의 결정을 보존한다. 처음 수정 여부를 결정하는 경우 전부 수정·일부 수정·보류를 제시하고 실제 응답을 기다린다. 부분 선택은 항목 ID를 받아 확정한다. 승인하지 않은 항목을 함께 수정하지 않는다.

### 5-3. TDD 실행으로 인계

승인된 항목의 ID·파일:라인·문제·기대 동작·원문 결과 경로·승인 근거를 `${DEV_DIR}/cross-review-handoff.json`에 기록한다. 사용자가 요청한 종료점을 함께 보존한다. 같은 실행의 상태가 있으면 그 run-id와 범위를 유지한다.

`Skill(skill: "oh-my-gx:gx-tdd")`로 인계한다. Codex에서는 설치된 gx-tdd/SKILL.md를 읽어 같은 계약을 수행한다. 실제 동작 결함은 실패하는 재현 테스트부터 수정하고, 동작 불변 정리는 기존 테스트를 유지하는 REFACTOR 경로를 사용한다. coder 직접 호출이나 비TDD 우회 경로는 사용하지 않는다. 이미 실패·수정·재리뷰가 진행 중이면 같은 실행에 항목을 전달하고 두 실행 루프를 만들지 않는다.

일반 finding 인계는 정규화 units 계획과 구분한다. 필요한 AC·소스/테스트 소유권을 gx-tdd가 보완하고 G-W-T·testability·RED·verify 게이트를 유지한다. 외부 advisor의 수정 권고만으로 사용자 승인을 만들어 넣지 않는다.

### 5-4. 수정 후 재확인

수정한 항목과 해당 diff만 재확인한다. 같은 코드·명령·범위의 테스트 증거는 공통 테스트 계약으로 확인하며 전체 스위트를 습관적으로 반복하지 않는다. 결과에는 수정·미수정·보류 항목과 검증 근거의 경로를 남긴다.
