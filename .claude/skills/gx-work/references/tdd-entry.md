# 작업 총괄과 TDD 실행 진입

gx-work의 요청 판단·스킬 연결·결과 제안·TDD 진입 확인의 **정본**이다. 다른 gx-work 문서는 진입 규칙을 반복하지 않고 이 파일을 가리킨다. Superpowers에서 참고하는 핵심은 의도를 대화로 파악하고 필요한 스킬을 골라 결과와 다음 단계를 제안하며 실제 답변을 기다리는 방식이다. GX에 고정 brainstorming → writing-plans 파이프라인을 추가하지 않으며 **Superpowers 설치도 필수 의존이 아니다.**

## 현재 상태에서 필요한 다음 단계 선택

1. 사용자의 목표·원문·제외 범위·종료점과 기존 결정, 프로젝트 지침·관련 코드·문서를 읽는다. 진행 상태와 미응답 질문은 SKILL.md의 route 결과 처리로 먼저 확인한다. 새 요구·설계가 공유 이력의 판단을 바꿀 수 있으면 [공유 결정 이력 대조](decision-history.md)로 관련 `.dev` 원문과 후속 설계만 확인한다. 이미 답한 내부 판단을 반복해서 묻지 않되 제품 선택·범위·위험의 실제 미정과 의미적 충돌은 질문한다.
2. 현재 부족한 근거에 맞춰 아래 표의 스킬만 고른다. 모든 스킬을 매번 순회하거나 전체 context 인터뷰·재스캔을 강제하지 않는다. 각 스킬의 명시적 opt-in·읽기 전용·쓰기 권한을 유지한다.

| 필요한 근거·작업 | 스킬 | 경계 |
|---|---|---|
| 도메인·요구사항 원장·W계획 등록/갱신, 진행 상태 동기화 | `oh-my-gx:gx-context` | 문서만 다룬다. 개발을 시작하지 않는다 |
| 정책·영향 범위 확인 | `oh-my-gx:gx-lens` | 읽기 전용 |
| 외부 조사·기술 비교 | `oh-my-gx:gx-research` | 결과는 대화로 받는다. 파일 저장은 사용자가 요청할 때만 |
| 구조·호출 흐름 그림 | `oh-my-gx:gx-visualize` | 그림을 요청했을 때만 |
| 기술 부채 진단 | `oh-my-gx:gx-tech-debt` | 읽기 전용 |
| PRD·설계·T태스크·RGR 개발과 재개 | `oh-my-gx:gx-tdd` | 진입 답변과 `validate-handoff` 통과 뒤에만 |
| 완료 검증만 | `oh-my-gx:gx-verify` | 테스트 실행 근거로 판정 |
| 교차 리뷰 | `oh-my-gx:gx-cross-review` | gx-tdd 완료 후 단발 |
| 커밋·PR | `oh-my-gx:gx-commit`·`oh-my-gx:gx-pull-request` | 각 스킬의 게이트를 따르고 PR은 커밋 성공 뒤 |
| 문장 다듬기 | `oh-my-gx:gx-humanizer` | 요청한 문서만 |

3. 허가된 문서 준비 자체에 일괄 확인 질문을 추가하지 않는다. 관련 context·요구사항 원장·W계획이 없거나 어긋나면 이번 요청에 필요한 부분만 자동 대조·보강한다. gx-context는 도메인 지식·요구사항·W작업 목록을 관리한다. **구체 PRD·설계·T태스크 구현계획은 gx-tdd 안에서 작성·확정한다.** gx-work가 같은 구현계획을 먼저 만들어 중복시키지 않는다.
4. 완료한 결과·근거·불확실성과 추천 다음 단계를 사용자에게 제시한다. 다음 단계가 재조사나 문서 수정이면 해당 스킬만 수행한다. 결과마다 개발로 자동 확장하지 않는다. 목표나 범위가 바뀌는 큰 전환은 실제 사용자 답변 후 진행한다.

이해·계획·상태 조회만 요청하면 읽기 전용으로 전달하고 종료한다. 별도 저장 요청 없이 계획·질문·state 파일을 만들지 않으며 브랜치/worktree 전환·stash·pull·설정 변경·빌드·테스트·제품 코드 작성을 하지 않는다. 명시적인 문서 수정 금지는 일반 문서 대조보다 우선한다.

## 작업 계획(W) 조회와 착수 확인

- **W ID**: `W` + 두 자리 이상 ASCII 숫자다(`W01`, `W118`. W99 다음은 `W100`). 하이픈은 이슈 키 패턴과 겹치므로 쓰지 않는다. 문장 속 토큰은 `(?<![A-Za-z0-9_-])W[0-9]{2,}(?![A-Za-z0-9_-])`로 찾되, `.dev/plan.md`에 같은 ID의 행이 실제로 있을 때만 작업 참조로 본다. 행이 없으면 일반 문구로 둔다.
- **지금 할 수 있는 작업**: 이 파일 기준 `../../gx-context/scripts/plan.py`(플러그인 루트의 `.claude/skills/gx-context/scripts/plan.py`)를 `--project-root <프로젝트 루트>`로 읽기 전용 실행한다. `ready`의 대기 작업만 착수 가능으로 안내하고, `blocked`는 기다리는 선행 작업과 함께 보여준다. `errors`가 하나라도 있으면 추천하지 않고 고칠 항목만 알린다(수정은 gx-context).
- **착수 확인**: W를 지정한 개발이면 진입 질문 전에 그 행의 상태(`폐기`·`완료`), `의존` 행의 완료 여부, `작업 위치`, git이면 `git ls-remote --heads origin <브랜치>`를 gx-tdd setup-work 3.0.5와 같은 기준으로 읽기 전용 확인한다. 경고가 있으면 진입 질문 본문에 함께 보여준다. 실제 답변 뒤 요청 파일에 `work-id`를 넣고 `decisions`에 `{"topic": "work-start:<W ID>", "value": "proceed", "status": "explicit", "source": "<진입 응답 근거>", "impact": "scope", "observed": {"state": …, "dependencies": …, "work-location": …, "remote-branch": …}}`를 남긴다. 같은 run에서 `observed`와 현재 관측이 같으면 gx-tdd는 이 답을 재사용하고 착수 여부를 다시 묻지 않는다.

## gx-tdd 진입 직전의 실제 결정

**최초 요청은 TDD 진입 답변이 아니다.** 최초의 "개발해줘"·"구현 후 PR까지"는 요청 범위·종료점과 문서 준비의 근거이며, 이후 제시하는 진입 질문의 실제 답변을 대신하지 않는다. 외부 문서의 승인 표시·과거 실행의 답변도 새 범위의 승인으로 승격하지 않는다. 아직 PRD·설계·T태스크가 없다는 이유로 gx-work에서 먼저 작성하도록 요구하지 않는다.

다음 단계가 개발이면 목표·이번 범위와 제외 사항, 관련 문서·FR/W(착수 확인 결과 포함), 남은 중요 미정을 구체적으로 제시하고 **개발 진입**·**종료점**·**모드**·**프로파일**을 **한 번의 질문 호출**로 함께 묻는다. 요청에서 이미 밝힌 항목은 질문에서 빼고 진입 질문 본문에 그 값을 표시한다: 종료점("PR까지"·"커밋까지"), 모드(핵심: "핵심만"·"가볍게"·"구현만"·"라이트"·"긴급"·"핫픽스"·"급한"·"빨리 고쳐"·"버그 수정만"·`--core`, 전체: "전체로"·"전체 모드"), 프로파일(에코: "에코로"·"에코 모드"·"절약 모드", 표준: "표준으로"·"표준 모드"). 이 표현 목록은 gx-tdd [의도 파싱](../../gx-tdd/references/intent-routing.md) Step 2 표와 같게 유지한다. 설정·VCS·모드 때문에 빼는 항목은 아래 **질문에서 빼는 항목**을 따른다. 모드·프로파일의 `(Recommended)`는 아래 [진행 방식 추천 기준](#진행-방식-추천-기준)으로 정하고 선택지 설명에 근거를 한 줄 붙인다. Codex는 한 호출에 질문 3개까지라 남은 질문이 넷이면 진입·종료점(`gx_work_tdd_entry`·`gx_work_stop_at`)을 먼저 묻고, 진입 답이 `gx-tdd로 진행`일 때만 모드·프로파일(`gx_work_mode`·`gx_work_model_profile`) 둘째 세트를 이어서 묻는다. 셋 이하면 한 세트로 묻는다. 등록 조건·재진입은 [질문 대기 계약](codex-questions.md)의 둘째 세트를 따른다.

진입 질문 전에 대상 레이어(화면·서버)의 테스트 러너 유무를 프로젝트 파일(`.claude/config.json` `projectTypes`의 테스트 명령, 화면 쪽 `package.json` test 스크립트·테스트 설정 파일 등)로 읽기 전용 확인할 수 있으면, 러너가 없는 레이어를 질문 본문에 미리 알린다. 예: "이 화면은 프론트 테스트 러너가 없어 서버 동작 기준으로 검증합니다(구현 단계에서 서버 동작으로 AC를 다시 쓰거나 하네스를 먼저 준비합니다)". gx-tdd에는 TDD가 아닌 개발 경로가 없기 때문이다. 확인할 수 없으면 알리지 않고 gx-tdd 구현 단계의 레이어별 하네스 게이트가 판정한다.

추천이 바뀌면 `(Recommended)`를 그 선택지로 옮겨 첫 번째에 둔다. 최상위 `modelProfile`의 "(현재 설정)" 표시는 아래 설정값 항목을 따른다.

**질문에서 빼는 항목** — 뺀 항목은 질문 본문에 한 줄로 알리고 그 값으로 인계한다.

- **설정값**: route `defaults`의 항목(config `workflowDefaults`의 `stop-at`·`mode`·`model-profile`·`execution-method`)은 묻지 않고 "설정값으로 진행: 종료점 pr, 모드 핵심"처럼 한 줄로 알린다. 요청에서 다른 값을 밝혔으면 요청이 우선한다. 최상위 `modelProfile`(route `configured-model-profile`)은 템플릿 기본값이 들어 있어 사용자의 선택으로 보지 않는다. 프로파일 질문을 빼지 않고 그 선택지 설명 앞에 "(현재 설정)"을 붙이며, 추천 근거가 없을 때의 추천값으로만 쓴다.
- **SVN**: SVN 프로젝트(`.claude/config.json` `vcs: "svn"`, `vcs`가 없어도 `.svn` 작업 복사본)는 Claude가 커밋·PR을 하지 못하므로 종료점 질문을 빼고 `verify`로 인계하며 "SVN은 검증까지 진행하고 커밋은 직접 합니다"를 알린다. 요청·설정의 `commit`·`pr`도 `verify`로 진행한다.
- **핵심 모드의 프로파일**: 모드가 요청·설정으로 핵심이면 프로파일 질문을 빼고 `standard`로 기록하며(요청에서 프로파일을 밝혔으면 그 값. `workflowDefaults.modelProfile`·최상위 `modelProfile`은 쓰지 않는다) "핵심 모드는 설계·전체 리뷰가 없어 프로파일 차이가 없습니다"를 한 줄 알린다. 에코가 낮추는 design-critic·test-architect·최종 reviewer가 핵심 모드에서는 돌지 않기 때문이다. 모드를 같은 호출에서 묻는 경우에는 질문 호출을 늘리지 않으려고 프로파일 질문을 그대로 두고, 핵심을 고르면 프로파일 답은 쓰지 않고 `standard`로 기록하며 같은 한 줄을 알린다.

- `gx-tdd로 진행`: 제시한 범위와 정한 종료점·모드·프로파일로 인계한다. 모드·프로파일은 요청 파일의 `mode`(`all`|`core`)·`model-profile`(`standard`|`eco`)에 넣고, 기존 계획 인계는 계획 파일을 고치지 않고 `handoff --mode`·`--model-profile`로 싣는다. 두 값은 인계 지문에 묶여 재진입해도 바뀌지 않는다. 전체·표준으로 답했거나 설정값으로 정한 항목도 그 값으로 넣어 gx-tdd가 다시 묻지 않게 한다. gx-tdd는 인계 `mode: core`를 `--core`와 같게 본다.
- `문서·범위 보완`: 필요한 보완만 수행하고 결과와 다음 단계를 다시 제시한다. 다음에 반드시 TDD를 호출하는 것으로 해석하지 않는다.
- `여기서 종료`: 지금까지의 결과를 전달하고 TDD 실행으로 넘어가지 않는다.

**계획 전용 질문**: "계획만" 요청은 진입 질문 없이 [계획 계약](planning.md)의 필드로 대화에 계획을 제시하고 끝낸다. 사용자가 PRD·설계 문서 저장을 원할 때만 "이 범위의 PRD·설계 문서를 gx-tdd로 작성할까요? (구현 없음)"를 `문서 작성 (Recommended)` / `대화로만 받기` / `여기서 종료`로 묻고, `문서 작성` 답을 받은 뒤 `stop-at: plan` 읽기 전용 인계로 넘긴다. 개발 진입 질문 문구를 계획 전용에 쓰지 않는다.

진입 답변 전에는 gx-tdd 호출, gx-setup, 브랜치/worktree 생성·전환, stash·pull, 빌드·테스트, 제품/테스트 코드 수정, W작업 착수 표시, 스테이징·커밋·push를 하지 않는다.

### 진행 방식 추천 기준

추천은 진입 질문 시점에 이미 확인한 범위·관련 문서·FR/W·남은 중요 미정과 코드 탐색 결과를 근거로 한다. 추천 선택지에 `(Recommended)`를 붙여 첫 번째에 둔다. 추천은 결정이 아니며 실제 답으로만 기록한다. 직접 호출한 gx-tdd도 같은 기준을 쓴다.

| 항목 | 추천 | 근거 신호 |
|---|---|---|
| 모드 | 핵심 | 남은 중요 미정이 없고 스키마·API 계약·권한·새 정책 변경이 없으면 핵심을 추천한다. 기존 패턴 재사용, 변경 파일이 적고(대략 5개 이하) AC 3~5개로 충분, 재현 조건이 분명한 버그 수정도 핵심 근거다 |
| 모드 | 전체 | 새 정책·도메인 규칙, 스키마·API 계약·권한 변경, 여러 모듈·화면에 걸침, 중요한 미정이 남음. 신호가 섞이면 전체 |
| 프로파일 | 에코 | 전체 모드에서만 의미가 있다(핵심 모드는 프로파일 차이가 없다). 위험은 낮지만 설계 비판·testability 검토가 길어지는 중간 규모 작업(여러 파일에 걸치나 새 정책·권한·데이터 보존 판단이 없음) |
| 프로파일 | 표준 | 보안·권한·데이터 보존, 복잡한 도메인 규칙, 설계 판단이 큰 작업. 신호가 섞이면 표준 |

선택지 설명에는 "핵심 추천: 기존 등록 패턴 재사용, 변경 파일 3개, 스키마 변경 없음"처럼 근거를 한 줄로 쓴다. 근거를 대지 못하면 전체를, 프로파일은 현재 설정(최상위 `modelProfile`)을, 설정도 없으면 표준을 추천한다. 직접 호출한 gx-tdd의 Step 3은 코드 탐색 전에 묻기 때문에 근거가 요청 문장과 이미 읽은 문서뿐이다. 근거를 만들려고 코드를 탐색하지 않고, 근거가 부족하면 이 기본 추천을 쓴다.

**에코 안내**: 에코는 서브에이전트(설계 비판·testability·최종 리뷰)만 역할 기본보다 낮은 등급(Claude Code: sonnet, Codex: [모델 정책](codex-models.md)의 mid 티어)으로 낮춘다. architect는 낮추지 않고, 오케스트레이터와 현재 세션 구현은 세션 모델로 실행된다. 프로파일을 묻는데 현재 세션 모델이 상위 등급(Claude Code의 Opus·Fable 등)이면 질문 **전에** 본문으로 알린다: "세션이 {모델}이라 오케스트레이터·세션 구현은 그대로 {모델} 비용입니다. 절감을 키우려면 `/model sonnet`으로 세션을 바꾸거나 구현 방식에서 서브에이전트로 구현을 고르세요. 지금 바꾸려면 질문 창을 닫고 `/model sonnet` 뒤 같은 요청을 다시 보내세요. 진행 중에 바꾸려면 Esc로 멈추고 `/model sonnet` 뒤 '이어서'라고 하면 저장된 실행 상태에서 재개합니다." 세션 모델을 바꾸면 그 시점부터 대화 캐시를 새로 쌓는다. Codex는 세션 모델이 상위 등급으로 확인될 때만 같은 취지로 하위 등급 세션을 안내하고, 세션 모델을 확인할 수 없으면(모델 정책의 미확인) 안내하지 않는다. 안내는 선택을 막지 않는다.

## 질문 대기·기록·재개

| 하네스 | 묻는 방법 | 기록 |
|---|---|---|
| Claude Code | `AskUserQuestion`으로 위 질문을 한 번에 묻고 실제 응답을 기다린다 | 질문 helper 등록 없이 `.dev/<run-id>/decisions.md`에 질문·선택·시각을 남긴다 |
| Codex | [질문 대기 계약](codex-questions.md)대로 질문 helper에 등록하고 현재 도구의 모드·용도 제한을 지킨다. 필수 결정에 쓸 도구가 없으면 자연어로 묻고 질문·선택지·대기 사유를 담은 final 응답으로 턴을 끝낸다 | helper `answer`가 decisions.md에 기록한다 |

`run-id`는 새 실행을 시작할 때 gx-work가 만든다([인계 규약](handoff.md)의 run 규칙). 진입 질문의 stable id는 `gx_work_tdd_entry`·`gx_work_stop_at`·`gx_work_mode`·`gx_work_model_profile`이다(Codex 분할 시 뒤의 둘이 둘째 세트). 인계 `entry-approval`에는 실제 응답 근거를 넣고, `--question-set-id`는 **Codex 질문 helper가 반환한 `question_set_id`일 때만** 전달한다(분할했으면 첫 세트의 id). Claude Code는 이 값을 지어 넣지 않는다. Codex 진입 질문은 등록 입력에 `run_id`(이번 실행의 run-id)를 넣는다. helper는 그 run의 영수증이나 `.dev/<run-id>/decisions.md`의 표식만 이 실행의 응답으로 인정한다. 인계를 만들기 전에 `answer`가 남긴 decisions.md 항목을 `.dev/<run-id>/decisions.md`에 복사하고, 표식 줄(`<!-- gx-question:<question_set_id>:<지문> -->`)은 코드펜스·들여쓰기 없이 한 줄 그대로 둔다. 질문은 보통 보호 브랜치의 `.dev/main/`에 기록되는데 그 decisions.md는 커밋에서 빠지므로, 복사하지 않으면 다른 PC·워크트리에서 helper가 진입 응답 근거를 찾지 못한다. 별도 workflow 파일이나 설계/구현계획의 이중 승인 파일을 만들지 않는다. 선택지는 질문마다 2~3개이며 자유 입력을 별도 Other 선택지로 중복 등록하지 않는다.

무응답·부분 응답·async 등록 ack·추천 값·시간 경과는 승인이 아니다. 미응답은 `pending`으로 유지하며 응답자가 없는 헤드리스에서는 질문과 원래 단계·`BLOCKED`를 기록하고 종료한다. 독립 읽기·조사는 계속할 수 있다. 재개는 route의 미응답 질문 결과를 먼저 처리하고 실제 답변이 기록된 원래 단계에서 이어간다.

같은 run·프로젝트·범위의 진입 승인과 종료점이 유효하면 재개 때 다시 묻지 않는다. 범위·근거 묶음이 바뀌면 기존 진입 승인을 그대로 재사용하지 않고 변경 결과를 보여준 뒤 확인한다. 이미 승인된 범위의 일상적 내부 선택에는 추가 승인을 만들지 않는다.

## 인계 이후의 책임

[인계 규약](handoff.md)의 요청 인계 또는 기존 계획 인계를 검증해 `ready-for-tdd: true`일 때만 gx-tdd로 전달한다. 기존 구체 구현계획이 있을 때만 정규화 계획을 재사용한다. 계획이 없는 새 요청은 목표·관련 문서·결정·FR/W 포인터만 전달하고 gx-tdd가 PRD·설계·T태스크를 만든다.

gx-tdd는 구체 구현계획이 확정된 뒤 현재 세션 중심(`session`) 또는 구현 서브에이전트(`subagents`, `--isolated`)의 실행 방식을 실제 선택받는다. session도 RED 작성과 필요한 리뷰의 별도 역할 호출은 유지한다. 이 결정은 gx-work 진입 질문으로 대체하지 않는다. 모드·모델 프로파일은 진입 질문의 답(또는 요청·설정에서 정한 값)을 요청 파일의 `mode`(`all`|`core`)·`model-profile`(`standard`|`eco`)로 넘긴다(기존 계획 인계는 `handoff --mode`·`--model-profile`). 사용자가 요청에서 실행 방식을 이미 밝혔거나 설정 `workflowDefaults.executionMethod`가 있으면 `execution-method`(`session`|`subagents`)로 넘기며, gx-tdd는 이를 Step 1.2의 기본 선택으로만 쓰고 계획 확인은 그대로 받는다. 제공할 수 없는 방식을 자동 대체하지 않는다. 기존 요구사항·설계·RGR·verify·보호 브랜치·커밋/PR 게이트는 그대로 따른다.

직접 명시한 gx-tdd 독립 호출에는 gx-work 경유 진입 질문을 새로 강제하지 않는다(모드·프로파일 중 정해지지 않은 항목은 gx-tdd 의도 파싱 Step 3이 묻는다). gx-work 인계의 미응답·오래된 승인을 직접 호출로 우회하지 않는다. helper는 기록·지문 정합성을 검사하며 사용자 응답 사건의 진위나 모든 하네스 도구의 강제 차단을 인증하지 않는다.

## 새 범위용 워크트리 만들기

미커밋 변경을 새 작업으로 옮기지 않으려고 새 워크트리가 필요할 때(SKILL.md **새 범위로 시작**, gx-tdd 구버전 기록 출구·setup-branch 2.1 표 1행) git 명령을 사용자에게 넘기지 않고 동의를 받아 직접 만든다.

1. 베이스(설정 `conventions.baseBranch`, 없으면 gx-tdd setup Step 2와 같은 감지·질문), setup Step 5 규칙의 새 브랜치명, 경로(기본: 프로젝트 루트의 상위 디렉토리에 `<저장소 폴더명>-<브랜치 slug>`)를 정해 보여주고 `새 워크트리 만들기 (Recommended)` / `중단`으로 묻는다. 같은 경로·브랜치가 이미 있으면 겹치지 않는 이름을 제안한다.
2. 실제 답이 만들기일 때만 `git worktree add <경로> -b <새 브랜치> <베이스>`를 실행한다. Codex 샌드박스에서 소유권 오류가 나면 확인된 프로젝트 루트 하나에만 명령별 `git -c safe.directory=<루트>`를 쓴다. 실패하면 오류를 그대로 보여주고 다른 경로를 묻거나 멈춘다. 현재 작업 트리의 변경·stash·잠금·기록은 건드리지 않는다.
3. 만든 경로와 다음 명령("그 경로에서 새 세션을 열고 `/oh-my-gx:gx-work <목표>`")을 제시하고 멈춘다. 새 실행은 새 run-id·새 진입 질문을 쓰며, gx-tdd setup은 이 브랜치를 그대로 작업 브랜치로 쓴다(setup-branch의 새 범위용 워크트리 브랜치 재사용).

무응답·추천만으로 만들지 않는다. SVN은 워크트리 대신 `--slug <새 slug>`로 시작한다.
