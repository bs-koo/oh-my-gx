# 작업 총괄과 TDD 실행 진입

gx-work의 요청 판단·스킬 연결·결과 제안·TDD 진입 확인 정본이다. Superpowers에서 참고하는 핵심은 의도를 대화로 파악하고 필요한 스킬을 골라 결과와 다음 단계를 제안하며 실제 답변을 기다리는 방식이다. GX에 고정 brainstorming → writing-plans 파이프라인을 추가하지 않으며 **Superpowers 설치도 필수 의존이 아니다.**

## 현재 상태에서 필요한 다음 단계 선택

1. 사용자의 목표·원문·제외 범위·종료점과 기존 결정, 프로젝트 지침·관련 코드·문서를 읽는다. 기존 pending 질문을 route보다 먼저 복원하고 같은 run의 진행 상태를 확인한다. 새 요구·설계가 공유 이력의 판단을 바꿀 수 있으면 [공유 결정 이력 대조](decision-history.md)로 관련 `.dev` 원문과 후속 설계만 확인한다. 이미 답한 내부 판단을 반복해서 묻지 않되 제품 선택·범위·위험의 실제 미정과 의미적 충돌은 질문한다.
2. 현재 부족한 근거에 맞춰 필요한 스킬만 선택한다. 도메인·요구사항·W계획의 등록/갱신은 gx-context, 정책·영향 파악은 gx-lens, 외부 조사·기술 비교는 gx-research, 기존 계획·작업 상태 확인은 해당 읽기 절차를 사용한다. 모든 스킬을 매번 순회하거나 전체 context 인터뷰·재스캔을 강제하지 않는다. 각 스킬의 명시적 opt-in·읽기 전용·쓰기 권한을 유지한다.
3. 허가된 문서 준비 자체에 일괄 확인 질문을 추가하지 않는다. 관련 context·요구사항 원장·W계획이 없거나 어긋나면 이번 요청에 필요한 부분만 자동 대조·보강한다. gx-context는 도메인 지식·요구사항·W작업 목록을 관리한다. **구체 PRD·설계·T태스크 구현계획은 gx-tdd 안에서 작성·확정한다.** gx-work가 같은 구현계획을 먼저 만들어 중복시키지 않는다.
4. 완료한 결과·근거·불확실성과 추천 다음 단계를 사용자에게 제시한다. 다음 단계가 재조사나 문서 수정이면 해당 스킬만 수행한다. 결과마다 개발로 자동 확장하지 않는다. 목표나 범위가 바뀌는 큰 전환은 실제 사용자 답변 후 진행한다.

이해·계획·상태 조회만 요청하면 읽기 전용으로 전달하고 종료한다. 별도 저장 요청 없이 계획·질문·state 파일을 만들지 않으며 브랜치/worktree 전환·stash·pull·설정 변경·빌드·테스트·제품 코드 작성을 하지 않는다. 명시적인 문서 수정 금지는 일반 문서 대조보다 우선한다.

## gx-tdd 진입 직전의 실제 결정

다음 단계가 개발이면 목표·이번 범위와 제외 사항, 관련 문서·FR/W, 남은 중요 미정, 요청된 `verify`/`commit`/`pr` 종료점을 구체적으로 제시하고 **“이 작업을 gx-tdd로 구체화·개발할까요?”**라고 묻는다. 기본 선택지는 다음과 같다.

- `gx-tdd로 진행 (Recommended)`: 제시한 범위와 종료점으로 gx-tdd의 PRD·설계·구체 구현계획 단계부터 진행한다.
- `문서·범위 보완`: 필요한 보완만 수행하고 결과와 다음 단계를 다시 제시한다.
- `여기서 종료`: 지금까지의 결과를 전달하고 TDD 실행으로 넘어가지 않는다.

최초의 “개발해줘”, “구현 후 PR까지”는 요청 범위와 문서 준비의 근거다. **이후 제시한 TDD 진입 질문에 대한 실제 답변이 아니다.** 외부 문서의 승인 표시·과거 실행의 답변도 새 범위의 승인으로 승격하지 않는다. 아직 PRD·설계·T태스크가 없다는 이유로 gx-work에서 먼저 작성하도록 요구하지 않는다.

진입 답변 전에는 gx-tdd 호출, gx-setup, 브랜치/worktree 생성·전환, stash·pull, 빌드·테스트, 제품/테스트 코드 수정, W작업 착수 표시, 스테이징·커밋·push를 하지 않는다. 문서 보완을 선택했으면 그 보완까지만 수행하며 다음에 반드시 TDD를 호출하는 것으로 해석하지 않는다.

## 질문 대기·기록·재개

Claude Code는 `AskUserQuestion`으로 묻고 실제 응답을 기다린다. Codex는 [질문 대기 계약](codex-questions.md)에 따라 현재 도구의 모드·용도 제한을 지킨다. 필수 결정에 쓸 수 있는 도구가 없으면 자연어로 질문하고 질문·선택지·대기 사유를 포함한 final 응답으로 턴을 종료한다. 선택지는 2~3개이며 자유 입력을 별도 Other 선택지로 중복 등록하지 않는다.

TDD 진입 질문은 `gx_work_tdd_entry` 같은 stable id와 원래 단계를 사용한다. state가 없으면 현재 브랜치의 `.dev/<slug>/pending-question.json`에 기존 질문 helper로 등록하고 가짜 gx-tdd pipeline state를 만들지 않는다. 실제 답변을 helper와 `decisions.md`에 기록한 뒤 [인계 규약](handoff.md)의 `entry-approval`에 그 근거와 `question-set-id`를 보존한다. 별도 workflow 파일이나 설계/구현계획의 이중 승인 파일을 만들지 않는다.

무응답·부분 응답·async 등록 ack·추천 값·시간 경과는 승인이 아니다. 미응답은 `pending`으로 유지하며 응답자가 없는 헤드리스에서는 질문과 원래 단계·`BLOCKED`를 기록하고 종료한다. 독립 읽기·조사는 계속할 수 있다. 재개는 route보다 먼저 pending을 확인하고 실제 답변이 기록된 원래 단계에서 이어간다.

같은 run·프로젝트·범위의 진입 승인과 종료점이 유효하면 재개 때 다시 묻지 않는다. 범위·근거 묶음이 바뀌면 기존 진입 승인을 그대로 재사용하지 않고 변경 결과를 보여준 뒤 확인한다. 이미 승인된 범위의 일상적 내부 선택에는 추가 승인을 만들지 않는다.

## 인계 이후의 책임

[인계 규약](handoff.md)의 요청 인계 또는 기존 계획 인계를 검증해 `ready-for-tdd: true`일 때만 gx-tdd로 전달한다. 기존 구체 구현계획이 있을 때만 정규화 계획을 재사용한다. 계획이 없는 새 요청은 목표·관련 문서·결정·FR/W 포인터만 전달하고 gx-tdd가 PRD·설계·T태스크를 만든다.

gx-tdd는 구체 구현계획이 확정된 뒤 현재 세션 중심(`session`) 또는 구현 서브에이전트(`subagents`, `--isolated`)의 실행 방식을 실제 선택받는다. session도 RED 작성과 필요한 리뷰의 별도 역할 호출은 유지한다. 이 결정은 gx-work 진입 질문으로 대체하지 않는다. 기존 명시 방식·유효한 같은 계획의 선택은 유지하며 제공할 수 없는 방식을 자동 대체하지 않는다. 기존 요구사항·설계·RGR·verify·보호 브랜치·커밋/PR 게이트는 그대로 따른다.

직접 명시한 gx-tdd 독립 호출에는 gx-work 경유 진입 질문을 새로 강제하지 않는다. gx-work 인계의 미응답·오래된 승인을 직접 호출로 우회하지 않는다. helper는 기록·지문 정합성을 검사하며 사용자 응답 사건의 진위나 모든 하네스 도구의 강제 차단을 인증하지 않는다.
