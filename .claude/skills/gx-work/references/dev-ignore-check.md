# .dev 공유 확인 (git)

`.dev/`는 PRD·설계서·Trust Ledger·state.md·작업 계획(`plan.md`)이 들어가는 **협업 공유 대상**이다. git이 이 경로를 무시하면 `git add -A`가 `.dev` 파일만 소리 없이 빼고 커밋한다. 그러면 팀원은 작업 계획도, 누가 무엇을 착수했는지도 보지 못하고, 같은 작업을 두 사람이 시작하게 된다.

이 절차는 gx-setup, gx-context(작업 계획 저장 전 P-8), gx-tdd(phase-setup Step 6)가 같은 방식으로 실행한다. gx-work는 직접 실행하지 않고, gx-work가 연결한 gx-context·gx-tdd가 수행한다. **git 저장소에서만** 실행한다. svn은 `svn:ignore` 속성으로 따로 다룬다.

## 1. 무시 여부 확인

`.gitignore` 문자열을 직접 찾지 않고 git에 묻는다. 무시 규칙은 `.dev`, `/.dev/`, `.dev/*`, `**/.dev`, `.*`처럼 형태가 다양하고, 하위 디렉토리의 `.gitignore`, `.git/info/exclude`, 전역 excludesFile에도 있을 수 있다. 한 줄씩 grep으로 찾으면 이 중 일부를 놓친다.

프로젝트 루트에서 실행한다.

```bash
git check-ignore -q .dev/gx-ignore-probe
```

- 탐침 경로는 실제로 만들지 않는다. `check-ignore`는 존재하지 않는 경로도 규칙만으로 판정한다. 이미 커밋된 파일 이름을 쓰면 추적 중이라 무시되지 않는다고 나오므로, 새로 생길 파일을 대표하는 이름을 쓴다. 이름이 점으로 시작하면 `.*` 패턴에 파일 자체가 걸려 `.dev/` 문제와 구분되지 않으므로 점 없이 쓴다.
- 종료 코드 `1`: 무시되지 않는다. 절차를 끝낸다.
- 종료 코드 `0`: 무시된다. `git check-ignore -v .dev/gx-ignore-probe`로 출력 `{출처}:{줄}:{패턴}<TAB>.dev/gx-ignore-probe`를 읽어 2단계로 간다.
- 그 밖(128 등): 판정할 수 없다. "`.dev` 무시 여부를 확인하지 못했습니다"를 한 줄 남기고 진행한다. 이 확인은 조율 수단이지 게이트가 아니다.

판정에는 `-v`를 쓰지 않는다. `-v`는 `!` 예외 규칙이 마지막으로 맞아 실제로는 무시되지 않을 때도 그 규칙을 출력하고 종료 코드 0을 돌려준다. `-v`는 `-q`가 무시된다고 답한 뒤 원인을 찾을 때만 쓴다.

## 2. 출처별 처리

| 출처 | 패턴 | 제안 |
|------|------|------|
| 저장소 안의 `.gitignore` (하위 디렉토리 포함) | 아래의 `.dev` 전용 형식과 정확히 일치 | 해당 제외 줄만 삭제하고 아래의 런타임 보호와 보존 검증을 수행한다 |
| 저장소 안의 `.gitignore` | `.*`, `*`, `.dev*` 등 더 넓거나 전용으로 확정할 수 없는 패턴 | 원래 줄을 유지하고 아래의 공유 블록과 세부 규칙 보존 방법으로 수정안을 만든다 |
| `.git/info/exclude` | 어느 패턴이든 | 위와 같은 기준으로 처리한다. 이 머신에만 적용되는 개인 설정이다 |
| 그 밖 (전역 `core.excludesFile` 등) | 어느 패턴이든 | 고치지 않는다. 다른 저장소에도 영향을 주므로 파일 경로와 줄 번호만 알리고 사용자가 직접 고치게 한다 |

**전용 형식 판정**: 경로 구성요소 이름이 정확히 `.dev`여야 한다. `.dev`, `/.dev`, `.dev/`, `/.dev/`, `**/.dev`, `**/.dev/`와 이 경로 뒤에 `/*` 또는 `/**`만 붙은 전체 하위 제외를 전용 형식으로 본다. `/`나 `*`를 임의로 지워 비교하지 않는다. `.dev*`, `.dev?`, `.dev[0-9]`는 `.dev-private`·`.development` 같은 다른 이름에도 적용될 수 있으므로 줄을 삭제하지 않는다. `.dev/private/**`처럼 일부만 제외하는 규칙도 전체 하위 제외와 구분해 보존한다.

### 공유 예외와 기존 제외 규칙의 우선순위

수정 전에 원인 파일 전체를 읽어 기존 세부 제외·허용 규칙과 순서를 보관한다. 이 참조 파일 위치 기준 `Read("dev-sharing.gitignore")`로 번들 공유 블록을 읽는다. 블록은 **프로젝트 루트 기준** `!/.dev/`·`!/.dev/**`로 공유를 허용하면서 질문·응답·잠금·모델 호출 파일은 다시 제외한다. `.gitignore`와 `.git/info/exclude`의 기존 줄을 없애거나 재정렬하지 않고 수정안을 만든다(승인한 전용 제외 줄 삭제만 예외).

- 넓은 원인 규칙 바로 뒤에 공유 블록을 넣는다. 뒤에 있는 `.dev` 세부 제외 규칙은 그대로 둔다. **`!.dev/`와 `!.dev/**` 두 줄을 파일 끝에 무조건 추가하지 않는다.** 마지막 예외가 앞의 세부 제외까지 무효화하기 때문이다.
- 원인 규칙보다 앞에 있던 `.dev/private/**` 같은 세부 제외는 블록 뒤에도 효력이 유지되도록 같은 순서로 재기재한다. 기존 세부 허용 규칙도 함께 보존한다. 여러 경로에 적용되는 `*.log` 같은 규칙은 원래 줄을 유지하고, 필요한 경우 `/.dev/**/*.log`처럼 프로젝트 루트 `.dev` 안에만 적용되는 규칙으로 보강한다. `.dev` 밖 경로의 우선순위를 바꾸지 않는다.
- 전용 제외 줄을 삭제하는 경우에도 질문·응답·잠금·모델 호출 파일이 계속 제외되는지 확인하고, 보호 규칙이 없으면 공유 블록의 런타임 제외를 수정안에 포함한다. 런타임 파일을 공유하는 기존 허용 규칙과 충돌하면 자동으로 덮지 말고 충돌 내용을 보고한다.
- 하위 `.gitignore`의 패턴은 그 파일의 디렉토리 기준이다. 루트용 블록을 `.dev/.gitignore`에 그대로 붙이지 않는다. 상대 경로를 안전하게 맞출 수 없거나 보존 여부를 확인할 수 없으면 수정하지 않고 원인과 필요한 조정을 안내한다.

예외 두 줄은 디렉토리 진입과 하위 파일 포함을 각각 담당한다. 상위 디렉토리가 무시되면 git은 그 안의 예외 규칙을 보지 않으므로, 공유할 파일 하나만 예외 처리하는 것으로 대체하지 않는다.

## 3. 확인 후 반영

```
AskUserQuestion(
  questions: [{
    header: ".dev 공유",
    question: "{출처}:{줄}의 '{패턴}' 때문에 .dev/가 git에서 무시됩니다. 작업 계획과 산출물이 커밋되지 않아 팀원에게 공유되지 않습니다. 고칠까요?",
    multiSelect: false,
    options: [
      { label: "고치기 (Recommended)", description: "{전용 제외 줄 삭제 / 공유 블록 추가}와 기존 세부 제외·런타임 보호를 함께 반영합니다" },
      { label: "그대로 두기", description: ".dev를 공유하지 않고 진행합니다" }
    ]
  }]
)
```

- "고치기"면 승인된 수정안을 Edit으로 반영한다. 승인 전에는 파일을 바꾸지 않는다.
- 반영 후 1단계(`-q`)를 다시 실행한다. 무시 규칙이 여러 곳에 있으면 다음 출처가 나오므로 같은 절차를 반복한다. 같은 출처·줄이 다시 나오면(수정이 먹지 않음) 멈추고 보고한다.
- **공유 탐침 하나만 통과했다고 완료하지 않는다.** `git check-ignore -q --no-index <경로>`로 `.dev/plan.md`와 일반 산출물은 제외되지 않고, `.dev/<작업>/pending-question.json`·`answered-question.json`·`.question-lock`·`model-dispatches.jsonl`·`discarded-question-<시각>.json`은 계속 제외되는지 확인한다. 경로는 실제로 만들지 않아도 된다. `--no-index`는 이미 추적 중인 파일도 규칙 자체를 검사하기 위한 것이다.
- 수정 전 보관한 세부 규칙의 대표 경로와 `.dev-private` 등 원인 패턴이 함께 덮던 다른 경로도 검사해 제외·허용 결과가 유지되는지 확인한다. 보존 검증이 실패하면 성공으로 보고하지 않는다. 자신의 수정만 되돌리거나 수정안을 다시 제시해 확인받고, 다른 작업자의 변경을 덮어쓰지 않는다.
- 전역 설정처럼 고칠 수 없는 출처만 남으면 질문하지 않고 안내만 한다.
- "그대로 두기"면 같은 실행 안에서 다시 묻지 않는다. "`.dev`가 무시되어 작업 계획과 산출물이 커밋되지 않습니다"를 한 번 안내하고 진행한다.
- 응답할 사용자가 없는 헤드리스 세션에서는 파일을 고치지 않고 경고만 남긴다.

`.gitignore`를 고쳤으면 그 변경도 커밋 대상이다. 이 절차는 커밋하지 않으며, 호출한 스킬의 커밋 흐름이나 사용자가 함께 커밋한다.

## 4. 같은 run의 결과 재사용

gx-work 한 실행 안에서는 gx-context(P-8)와 gx-tdd(Step 6)가 차례로 이 절차를 만난다. 앞 단계에서 받은 답을 뒤 단계가 다시 묻지 않게 한다.

- 3단계에서 답을 받은 단계는 run 디렉토리가 있으면 `.dev/<run-id>/decisions.md`에 `.dev 공유 확인: {고치기|그대로 두기} ({출처}:{줄}:{패턴})`를 한 줄로 남긴다. 직접 호출처럼 run 디렉토리가 없으면 기록 파일을 만들지 않고 같은 대화 안에서만 기억한다.
- 뒤 단계는 1단계 `-q` 판정을 다시 한다. 무시되지 않으면 그대로 끝난다. 여전히 무시되고 같은 run의 기록이 같은 출처·줄·패턴에 대한 `그대로 두기`이면 다시 묻지 않고 "`.dev`가 무시되어 작업 계획과 산출물이 커밋되지 않습니다"만 한 번 안내한다.
- 출처·줄·패턴이 기록과 다르면 새 상황이므로 2~3단계를 다시 수행한다. 다른 run의 기록은 재사용하지 않는다.
