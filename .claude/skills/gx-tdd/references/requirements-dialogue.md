# 요구사항 문답·확정 공통 계약

전체·핵심 모드의 요구사항 판단 정본이다. requirements의 초안 작성/재사용 전, design·implement·complete 진입/재개와 phase 완료 전에 현재 요청·문서·미정을 대조한다. 같은 대화에서 이미 읽은 이 계약과 같은 범위의 사실/답변은 재사용하며 새 변경만 확인한다. 새 helper·상태 필드·인터뷰 전용 파일을 만들지 않는다.

## 1. 중요한 미정 판정

- **중요한 미정**: 답에 따라 사용자에게 보이는 동작·적용 범위·정책 수치·권한·데이터 보존/호환성·성공/실패/경계의 AC 기대값이 달라지거나, 현재 요구와 승인 문서가 충돌하는 미정이다. 미정 개수·파일 수·긴급 여부로 중요도를 낮추지 않는다.
- 요청·기존 답변·관련 문서·코드에서 먼저 근거를 찾는다. 현재 요청이 유지하는 기존 정책은 그 근거로 재사용한다. 현재 코드 동작은 관측 사실이며 새 정책에 대한 사용자 선택으로 승격하지 않는다. 사용자에게 이미 답한 수치·배경을 다시 묻지 않는다.
- 기존 `unresolved`의 topic/impact/blocking/source와 `decisions`의 explicit/inferred/unresolved·원문 근거를 재사용한다. 중요한 미정은 `blocking: true`다. 분류·해소 근거를 설명할 수 없으면 중요한 미정으로 유지한다.
- **비차단**은 결과·공개 계약을 바꾸지 않는 문서 표현/내부 정리 또는 근거가 충분한 낮은 영향의 가정이다. 이유·가정·남은 한계를 PRD/AC의 기존 가정·참고 절에 간단히 남긴다. 미정 정책 숫자·적용 대상을 임의 선택해 비차단으로 바꾸지 않는다.
- 사용자가 특정 결정을 명시적으로 위임하면 그 원문·위임 범위와 실제 선택한 값/이유를 기록하고 기존 산출물 승인에 포함한다. 포괄적인 “진행해”·추천·무응답을 정책 위임으로 추정하지 않는다. 위임 범위 밖의 중요한 미정은 계속 질문한다.

## 2. 문답 루프

1. 사용자 중단은 미정/대기 판정보다 먼저 7의 `stopped`로 처리한다. 그 외에는 현재 요청과 근거로 중요한 미정 목록을 갱신한다. 전체 PRD 분기는 phase-requirements Step 1/4의 **기존 product-owner 호출**을, 핵심 inline 분기(`use_inline_core=True`)는 **오케스트레이터 직접 문답**을 사용한다. 명시 requirements/design의 기존 PRD 경로는 유지한다. 이 참조 때문에 별도 디스패치를 추가하지 않는다. 핵심 inline에 인터뷰용 product-owner·architect·design-critic을 호출하지 않는다.
2. 중요한 미정이 없으면 `ready`로 다음의 **기존** 문서·승인 절차를 수행한다. 명확한 요청의 최소 질문 수는 0이다. 비차단 항목만 남았다는 이유로 인터뷰를 늘리지 않는다.
3. 중요한 질문은 기존 interaction-contract에 따라 **하나씩** 제시한다. 선택의 배경·결과 차이를 설명하고 실제 답변을 기다린다. 선행 답변이 필요한 질문은 그 답을 받은 뒤 구체화한다.
4. 실제 답변의 해소 범위와 근거를 기록한다. 여러 미정을 한 답변이 해소했다면 함께 반영한다. 원래 질문 중 필요한 부분만 답했다면 나머지는 계속 미정이다.
5. 답변으로 새 정책·예외·충돌이 드러나면 목록을 다시 평가하고 1로 돌아간다. 전체는 답변·현재 초안·남은 중요 미정을 같은 product-owner에게 전달하여 갱신한다. “한 번 더 호출”이나 고정 Q&A 라운드를 종료 기준으로 쓰지 않는다.
6. 중요한 미정이 남으면 초안과 미정을 표시하고 `waiting`으로 대기한다. PRD/AC 확정·phase 완료·후속 설계/RED/구현으로 진행하지 않는다. 중요한 구조·인터페이스 결정은 기존 core→all 전환의 실제 결정을 기다린다(`mode-transition`). 제품 정책 질문이 많다는 이유만으로 자동 전환하지 않는다.
7. 사용자가 중단하면 `stopped`로 현재 질문·근거·기존 산출물과 실행 범위를 보존하고 종료한다. 응답자가 없는 실행은 BLOCKED와 필요한 질문을 보고한다. 횟수를 채워 자동 확정하거나 같은 질문을 답 없이 재호출하지 않는다.

`ready`/`waiting`/`stopped`는 오케스트레이터의 단계 진행 판단이며 새 저장 상태가 아니다. G-W-T 형식 수정·설계 검토·fix loop의 기존 재시도 상한은 유지하되, 그 상한이 중요한 미정의 해소나 다음 단계 허가를 뜻하지 않는다.

## 3. 대기·재개와 쓰기 경계

Claude는 기존 interaction-contract의 실제 질문/응답 대기를, Codex는 설치된 [질문 계약](../../gx-work/references/codex-questions.md)의 도구 선택·표시·기록을 따른다. 도구의 모드/용도가 맞지 않으면 자연어로 묻고 실제 답변을 기다린다. async ack·추천/preselection·빈 응답·시간 경과는 답변이 아니다.

- **쓰기 허용 파이프라인**: 현재 실행 phase의 기존 pending·decisions를 사용한다. 기존 미응답 질문을 덮어쓰지 않고 그 질문부터 재개한다. 한 세트의 실제 `answer` 성공·해제 후 새 후속 질문을 새 question_set_id로 등록한다. 늦은 토큰·다른 id·부분 답변으로 현재 대기를 해제하지 않는다. 단독 design/implement 중 요구사항 문답도 질문의 원 phase·실행 커서를 보존하여 필요한 범위만 수행한다.
- `answer` 성공은 실제 응답을 기록했다는 뜻이며 중요한 미정 해소의 증거를 대신하지 않는다. 답변이 의미상 불충분하거나 상충하면 필요한 부분을 새 후속 질문으로 확인한다. 예컨대 기간을 물었는데 “네”라고 답했다면 임의의 기간으로 확정하지 않는다.
- **HANDOFF_READ_ONLY·문서 저장 금지·대화 전용 계획**: 질문·답변·미정을 대화에만 남긴다. `register`/`answer`도 호출하지 않으며 `.dev`·state·pending·decisions·승인 필드를 새로 쓰거나 변경하지 않는다. 기존 실행의 pending과 섞지 않고 대화의 답변 근거로만 이어간다. 미해결이면 질문을 표시하고 대기한다.
- 재개 시 원 run·종료점·현재 커서·질문과 실제 답변을 복원한다. 완료한 setup/RGR·전체 인터뷰를 초기화하지 않는다. 새 중요한 미정이 없고 기존 승인도 유효하면 그대로 재개한다.

## 4. 재사용·진입·승인

`--from-plan`·`--handoff`·기존 승인 문서의 재사용에서도 **현재 요청의 중요한 미정**을 먼저 확인한다. 과거 approved·ready 표시, 파일 존재, 종료 문구만으로 해소를 추정하지 않는다. 동일 범위·현재 근거의 유효한 답변·승인은 반복하지 않고 새 미정/충돌만 문답한다. 과거 이력에서 이미 해소된 질문을 현재 미정으로 세지 않는다.

`--phase design/implement/complete`·`--resume`도 같은 확인을 수행한다. 중요한 제품 미정이면 필요한 requirements 문답으로 돌아가 대기하며 요청 phase·원 실행 커서·stop-at을 보존한다. 답변 후 현재 요청 범위의 부족한 문서·승인만 보완한다. 기술 설계의 중요한 미정은 설계의 기존 질문·승인으로 해소하며, 설계 검토 상한이 소진돼도 미정 상태로 구현하지 않는다. 설계 단독 요청을 구현으로 넓히지 않는다.

**문답 해소는 승인 아님.** 전체는 갱신한 PRD 전문을 표시하고 기존 PRD 승인·설계·계획 승인을 수행한다. 핵심은 AC·코드 확인·plan.md를 작성하고 기존 **AC+계획 결합 승인**을 받는다. 별도 인터뷰 종료 승인을 추가하지 않는다. 답변이 기존 AC/계획을 바꾸면 core-replanning의 이력 보관·문서 변경 전 승인 무효화·변경분 검증·재승인을 유지한다. 기존 GREEN/RED·케이스 ID를 질문 때문에 지우지 않는다.

## 5. AC·PRD 반영

확정한 정책·범위·정상/실패/경계 조건을 추측 없이 G-W-T AC와 검증에 연결한다. 중요한 미정이 있으면 알려진 내용만 초안으로 제시하고 임의의 숫자나 기대값을 확정하지 않는다. core의 AC 3~5개는 소형 작업의 권장 규모이며 질문/필수 시나리오를 삭제하는 상한이 아니다. 범위가 커지면 기존 모드 전환 기준으로 판단하고 먼저 범위 선택을 받는다.

전체의 `추가 확인 사항 없음. PRD가 확정되었습니다.`는 **중요한 미정이 없어 산출물 검토에 올릴 수 있다**는 호환용 출력 신호다. 오케스트레이터가 실제 목록/근거를 대조하며, 이 문구 자체가 사용자 승인이나 저장·구현 권한은 아니다. 비차단 가정은 질문 목록과 구분해 남긴다. Phase 완료 저장은 `ready`와 해당 산출물의 기존 실제 승인 조건이 모두 충족될 때만 수행한다.
