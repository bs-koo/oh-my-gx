# Impact-Report: 변경 판단에 필요한 결과

오케스트레이터가 `IMPACT_RESULT`를 한국어 업무 언어로 합성한다. 현재 정책 보고서를 반복하지 않고 **누가 어떤 조건에서 다른 결과를 받는지** 먼저 쓴다. 근거 ID·파일:라인과 확인/추정/미확인을 유지한다. 대화에만 출력한다.

## 출력 구조

아래 순서를 사용하되 해당하지 않는 항목은 생략한다. 단, 조사하지 않은 항목을 영향 없음으로 바꾸지 않는다.

1. **바뀌는 동작**: 대상·조건·현재 → 요청 결과를 1~3문장으로 요약. 요청에 빈칸이 있으면 적용 전제를 함께 표시.
2. **영향 받는 규칙과 사용자/소비자**: 규칙별 업무 결과·직접 소비자·근거를 표 또는 짧은 불릿으로 정리. 파일 수 대신 실제 확인한 경계를 설명.
3. **데이터와 계약**: 기존 데이터 재판정, 저장값·API·이벤트·외부 연동에 생기는 차이. 동적 연결/실제 환경값은 미확인 전제를 밝힘.
4. **테스트 경계**: 변경 조건의 직전/동일/직후 값, 빈값·오류·상태/권한 조합 중 근거가 있는 경계와 기대 결과. 기존 테스트 근거와 앞으로 확인할 검증을 구별. 테스트·운영 실행은 하지 않았다고 명시.
5. **판단에 남은 확인**: 근거 없는 연결, 문서와 코드의 차이, 정책 결정 필요 사항, 실패/미실행한 분석. 질문마다 왜 변경 판단에 영향을 주는지 설명.

기본 보고서는 1~2화면 안에서 핵심을 전달한다. `--detail`이면 직접 소비자·경계 시나리오·근거 목록을 넓혀도 원본 코드를 반복하지 않는다.

## 판단의 한계

- 자동으로 “바로 진행/배포 가능” 판정을 내리지 않는다. 정적 분석이 확인한 범위와 결정을 위해 남은 조건을 설명한다.
- 근거가 없는 위험 점수·백분율·파일 수·공수·안전 보증을 만들지 않는다. 구체적 실패 조건과 그 결과를 제시한다.
- 역할 실패·미실행은 미확인으로 보고한다. 일부 결과만 있으면 해당 범위의 영향과 남은 경계를 구분한다.
- 문서 의도와 현재 구현이 다르면 둘 중 하나를 임의로 정답으로 선택하지 않는다.
- “영향 없음”은 해당 주장에 대한 직접 근거가 있을 때만 쓴다. 미발견·예산 소진·분석 실패는 근거가 아니다.

보고서 뒤에 구현·커밋·배포·추가 분석을 위한 필수 질문을 붙이지 않고 종료한다.
