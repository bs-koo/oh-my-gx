# 정책 보고서 가이드

상대경로는 이 파일 위치 기준이다. 업무 설명과 근거를 함께 전달한다. 요약은 1~2화면, `--detail`은 관련 규칙·직접 소비자·미확인 경계를 더 설명한다. 코드 덤프나 장식용 형식 혼합은 필요하지 않다.

## 기본 순서

1. **답변**: 질문 대상이 어떤 조건에 허용·차단·변경되는지 먼저 1~3문장.
2. **규칙**: 각 항목에 R ID, 확인/추정/미확인, 업무 조건·결과와 근거 위치.
3. **현재 구현과 의도**: 관련 요구사항이 있을 때 차이를 비교. 문서가 없으면 의도 미확인을 한 줄 표시.
4. **확인 범위와 남은 조건**: 실제 읽은 범위, 미해결 연결·설정·운영값·탐색 실패. 테스트/운영 실행을 하지 않았다는 한계.

조건이 간단하면 짧은 불릿을 사용한다. 여러 상태·사용자·조건을 비교할 때 표를 사용한다. 숫자는 값·단위·적용 조건·근거를 같은 항목에 둔다. 근거 ID가 여러 항목에서 재사용되면 끝에 E ID별 위치 목록을 둘 수 있다. 각 규칙에서 어느 근거인지 따라갈 수 있어야 한다.

## 예시: 문서와 현재 구현이 다를 때

아래는 형식 예시이며 실제 프로젝트 사실이 아니다.

> 현재 코드는 한도와 같은 금액을 허용합니다. 문서는 같은 금액을 차단하도록 정의하여 경계값에서 차이가 있습니다.

| 규칙 | 현재 확인한 결과 | 의도와 차이 |
|------|-----------------|-------------|
| R1 · 확인(정적 구현) | 100원 이하 허용. 구매 판정 E1 (`src/purchase/limit.py:18-25`) | 문서 P-1은 100원 미만. E2 (`context/purchase/rules.md:8-10`) |

운영 환경의 한도 덮어쓰기 값과 실제 호출 구현은 미확인입니다. 기존 테스트는 E3 (`tests/test_limit.py:12-18`)에서 경계값을 기대하지만 실행하지 않았습니다.

## 미발견 예시

“`src/purchase/`의 `check_limit` 참조와 관련 설정을 조사한 범위에서 규칙을 찾지 못했습니다. 동적 등록 구현은 확인하지 못했습니다.”

프로젝트 전체의 미구현을 단정하거나 유사 기능을 대신 제시하지 않는다. 문서상 규칙만 있으면 문서 근거와 구현 미확인을 구분한다. 조사하지 않은 원인을 일반 목록으로 나열하지 않는다.
