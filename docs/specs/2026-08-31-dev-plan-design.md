## 배경

요구사항이 여러 건일 때 "무엇을 먼저 하고 무엇을 동시에 할 수 있는가"를 알 방법이 없다.

`context/{도메인}/status.md`가 항목별 진행을 추적하지만 도메인별로 흩어져 있고, 항목 간 의존 관계가 없으며, 병렬 가능 여부를 표현하지 못한다. 사용자가 매번 status.md를 열어 직접 고르고 도메인과 요구사항을 프롬프트에 적어야 한다.

`phase-setup`은 `glossary.md`·`architecture.md`만 로드한다 (gx-tdd `phase-setup.md:163`, gx-dev `:166`).

## 스펙

### 위치

`.dev/plan.md` — `.dev/` 루트.

`.dev/{branch-slug}/`는 브랜치별 격리지만 계획은 브랜치를 가로지른다. `.dev/.active` 포인터가 이미 루트에 있어 선례가 된다 (`lint-consistency.sh:358-366`). `.dev`는 협업 공유 대상이라 gitignore 조정이 불필요하다 (gx-tdd `phase-setup.md:214`).

### 형식

```
# 작업 계획

| ID | 작업 | 도메인 | 요구사항 | 의존 | 작업 위치 | 상태 |
|----|------|--------|----------|------|-----------|------|
| W00 | 기초 스키마·공통 모듈 | 공통 | FR-1~3 | - | feat/base-schema | 완료 |
| W01 | 이관 이력 조회 | 재고관리 | FR-4~6 | W00 | feat/transfer-history | 진행 |
| W02 | 분류 규칙 관리 | 재고관리 | FR-7~9 | W00 | - | 대기 |
| W03 | 정산 연동 | 정산 | FR-20~22 | W00 | - | 대기 |
| W04 | 통합 대시보드 | 통합 | FR-30 | W01,W03 | - | 대기 |
```

**병렬군 열은 두지 않는다.** 의존 열에서 계산되는 파생 정보이므로 저장하면 동기화 대상이 하나 늘고 동시 완료 시 충돌한다. 읽는 쪽이 계산해 출력한다.

**"지금 병렬 가능" 절도 파일에 쓰지 않는다.** 같은 이유다. 사용자가 물으면 그때 계산해 보여준다.

### 필드

| 필드 | 규칙 |
|------|------|
| ID | `W` + 두 자리 숫자. 하이픈 없음. 이슈 키 정규식 `^[A-Z]+-[0-9]+$`(`config.json:5`)에 매칭되지 않게 하기 위함 |
| 작업 | 한 줄 요약. **브랜치명 생성의 입력**이 된다 |
| 도메인 | `context/{도메인}/`과 일치. 예약어 `공통`·`통합`은 context를 읽지 않는다 |
| 요구사항 | status.md 항목 ID 범위. **참조 표기일 뿐 전파에 쓰지 않는다** |
| 의존 | 선행 작업 ID. 쉼표 구분, 없으면 `-` |
| 작업 위치 | git은 브랜치명, svn은 `.dev/.active` slug. 미착수는 `-` |
| 상태 | `대기` / `진행` / `완료` — 이모지 대신 텍스트 (grep 검사 용이) |

### 예약 도메인

| 값 | 의미 | context Read |
|----|------|--------------|
| `공통` | 도메인에 속하지 않는 선행 작업 (스키마·기반 모듈) | 건너뜀 |
| `통합` | 여러 도메인이 걸리는 작업 | 건너뜀 |

린트는 이 둘을 `context/` 실존 검사에서 제외한다.

## 읽기 — `--work` 플래그

### 인자 파싱

`--work W01` 형태로 받는다. 자연어에서 작업 ID를 추론하지 않는다.

기존 플래그(`--phase`·`--core`·`--resume`·`--ralph`·`--eco`)와 같은 층위에서 파싱한다. `--work`는 모드 판정과 독립이므로 다른 플래그·자연어 파싱을 계속 진행한다.

**충돌 규칙**: `--work`와 `--resume`은 동시 사용 불가. `--resume`은 state.md에서 문맥을 복원하므로 작업 ID를 다시 받을 이유가 없다. 동시 지정 시 "`--work`와 `--resume`은 동시에 사용할 수 없습니다." 안내 후 중단한다.

### 처리 (phase-setup)

`--work`가 있을 때만 아래를 수행한다. 없으면 기존 동작 그대로다.

1. `.dev/plan.md`를 Read한다. 파일이 없으면 "작업 계획이 없습니다. `.dev/plan.md`를 만들거나 `--work` 없이 실행하세요." 안내 후 중단한다.
2. 표를 파싱해 해당 ID의 행을 찾는다. **파싱 실패 또는 행 부재 시 중단한다** (조용히 진행하지 않는다).
3. **이슈 키 추출을 건너뛴다.** `--work` 사용 시 Step 5의 이슈 키 파싱을 수행하지 않는다.
4. **브랜치명을 `작업` 열에서 생성한다.** `{type}/{작업을 슬러그화}` 형식. type은 사용자에게 확인한다 (기본 `feat`).
5. **코드 맵 키워드**를 `작업` + `요구사항` 텍스트에서 추출한다 (Step 4의 이슈 키 제외 규칙 대신).
6. **도메인 컨텍스트**를 해당 도메인만 로드한다. 예약 도메인이면 건너뛴다. 레포 매칭으로 여러 도메인을 읽던 기존 경로를 대체한다.
7. **status.md**를 같은 도메인에서 함께 로드한다 (`--work` 사용 시에만).
8. **의존 확인**: 선행 작업이 `완료`가 아니면 경고하고 AskUserQuestion으로 진행 여부를 확인한다.
9. **ARGS[0] 보강**: `작업` 열 텍스트를 요청 문구로 사용한다.
10. **착수 기록**: `작업 위치`에 브랜치명(svn은 slug)을 기입하고 상태를 `진행`으로 바꾼다. 이미 값이 `-`가 아니면 다른 사람이 착수한 것이므로 경고하고 확인받는다.
11. **state.md에 `work-id: W01`을 기록한다** — `--resume` 시 문맥 복원의 근거가 된다.

## 갱신 — 독립 Step

기존 Step 3(status.md 갱신) 뒤에 붙이지 않는다. **별도 Step으로 분리**한다.

### 진입 조건

`DOMAIN_CONTEXT` 존재와 무관하다. 아래만 본다.

```
.dev/plan.md 가 존재하고
state.md 의 work-id 가 있거나 현재 작업 위치와 일치하는 행이 있으면 실행
```

이렇게 하면 `--phase complete` 경로(환경 감지만 수행해 DOMAIN_CONTEXT가 빈 상태)에서도 동작한다.

### 삽입 지점

| 파이프라인 | 위치 | 비고 |
|------------|------|------|
| gx-tdd `phase-complete.md` | Step 3 뒤 **독립 Step 3.5** | Step 3은 ACCEPT 조건이라 core에서 미실행. 3.5는 그와 무관하게 실행 |
| gx-dev `phase-complete.md` | Step 3(경로 A/B) 뒤 **독립 Step 3.5** | 경로 분기와 무관 |
| `gx-ralph-iterate` | 반복 종료 시 | 현재 phase-complete를 거치지 않으므로 별도 지시 필요 |

### 절차

1. `.dev/plan.md`에서 `작업 위치`가 현재 브랜치(svn은 활성 slug)와 일치하는 행을 찾는다. state.md에 `work-id`가 있으면 그것을 우선한다.
2. **행이 없으면 아무것도 하지 않고 넘어간다.** `--work` 없이 시작한 작업은 계획에 없는 것이 정상이다.
3. 상태를 `완료`로 바꾼다.
4. `.dev/plan.md`를 전용 메시지로 커밋한다 (아래).

**status.md 전파는 하지 않는다.** status.md 갱신은 기존 Step 3이 AC 축으로 수행한다. plan.md의 `요구사항` 열은 참조 표기일 뿐이다. 두 파일이 서로를 덮어쓰지 않으므로 부분 통과 시 미구현이 완료로 뒤집히는 경로가 없다.

### 커밋 규칙

`.dev/plan.md`는 커밋·push가 끝난 뒤에 수정되므로 별도 커밋이 필요하다. 메시지 형식은 `docs: [plan] W01 완료`로 고정한다.

gx-dev의 context 자동 커밋(`docs: [context] …`)과 같은 층위의 예외다. `skill-routing.md`의 "내부 파이프라인에서도 동일 적용" 절 예외 목록에 명시한다.

### 되돌림

state.md 수명주기와 대칭을 맞춘다. gx-tdd `SKILL.md:559`는 "`status: completed`인 state.md에 어떤 Phase든 재진입하면 `status: in_progress`로 되돌린다"고 규정한다.

**같은 시점에 plan.md의 해당 행도 `완료 → 진행`으로 되돌린다.** 되돌리지 않으면 다른 팀원이 완료된 산출물을 전제로 후속 작업에 착수한다.

## 생성 — gx-context 확장

`--from`으로 요구사항을 읽을 때 `status.md`와 함께 `plan.md`도 만든다.

### 절차

1. 요구사항을 항목으로 파싱한다 (기존 status.md 생성 로직 재사용)
2. 항목을 작업으로 묶는다
3. 의존 관계를 판정한다
4. AskUserQuestion으로 확인받는다
5. `.dev/plan.md`에 저장한다

### 묶기 규칙

- 한 작업은 AC 3~5개로 환산 가능한 크기 (gx-tdd AC 상한과 정합)
- 화면·기능·컴포넌트 단위
- 파일 경계가 겹치지 않도록 (phase-implement 태스크 분해 규칙과 동일 근거)
- 도메인을 가로지르지 않는다. 여러 도메인이 걸리면 `통합` 예약 도메인을 쓴다

### 의존 판정

아래를 선행으로 본다.

- 스키마·공통 모듈 생성 작업
- 데이터를 생산하는 작업 (소비 작업보다 앞)
- 인증·권한 기반 (보호 대상보다 앞)

근거를 표 아래 각주로 남긴다. 근거 없이 의존을 만들지 않는다.

### 확인 게이트

의존 판정은 AI가 100% 맞히기 어렵다. 저장 전에 AskUserQuestion으로 확인받는다. 선택지는 "그대로 저장 / 묶음 조정 / 의존 관계 수정" 세 가지로 두고, 조정과 수정은 Other 자유입력으로 받는다.

### 누적 규칙

기존 계획을 덮어쓰지 않는다.

| 상태 | 재계획 시 |
|------|-----------|
| `완료` | 건드리지 않는다 |
| `진행` | 건드리지 않는다 |
| `대기` | 재조정 대상 |

새 작업은 뒤에 추가한다. 이력은 git이 관리하므로 파일 안에 시점별 이력을 쌓지 않는다.

## 충돌 대응

`plan.md`는 표 구조라 `merge=union`을 쓸 수 없다 (union은 행 순서를 보존하지 않아 표를 깨뜨린다). 이 저장소의 `.gitattributes`에는 현재 union 지정이 없다.

충돌면을 설계로 줄인다.

- 병렬군·"지금 병렬 가능"을 파일에 쓰지 않으므로 **모든 갱신이 단일 행 안에서 끝난다**
- 서로 다른 작업을 맡으면 서로 다른 행을 고치므로 git이 자동 병합한다
- 계획 수립(`--from`)은 1회, 한 사람이 수행한다

같은 작업을 두 사람이 동시에 착수하는 경우는 `작업 위치` 열이 이미 채워져 있는 것으로 감지한다 (읽기 Step 10).

## SVN

| 항목 | git | svn |
|------|-----|-----|
| `작업 위치` 값 | 브랜치명 | `.dev/.active`의 slug |
| 행 매칭 | `git branch --show-current` | `.dev/.active` 내용 |
| 갱신 Step | 실행 | 실행 (Step 3과 달리 svn에서도 동작) |
| 커밋 | 자동 | 사용자에게 안내 (터미널에서 직접 실행) |

기존 Step 3은 svn에서 건너뛰지만(gx-tdd `phase-complete.md:151`), plan 갱신은 브랜치 로그 비교에 의존하지 않으므로 svn에서도 수행한다.

## 하위 호환

| 조건 | 동작 |
|------|------|
| `--work` 미사용 | **기존 동작 그대로.** plan.md를 읽지 않고 status.md도 로드하지 않는다 |
| `.dev/plan.md` 없음 + `--work` 사용 | 안내 후 중단 |
| `.dev/plan.md` 있음 + `--work` 미사용 | 읽지 않는다. 갱신 Step만 행 매칭을 시도하고 없으면 넘어간다 |

v1의 "status.md 무조건 로드"는 철회한다. 모든 실행의 DOMAIN_CONTEXT를 늘려 `config.json:65-81`의 `contextLimits`에 압력을 주고, 배경에서 지적한 컨텍스트 부풀음을 악화시킨다.

## 린트 계약

`plan.md`는 소비 프로젝트의 런타임 데이터이므로 플러그인 저장소 CI에는 검사 대상이 없다 (`lint-consistency.sh:32`가 저장소 루트에서 동작).

**픽스처 기반으로 검사한다.**

- `tests/fixtures/plan-valid.md` — 정상 표
- `tests/fixtures/plan-cycle.md` — 순환 의존
- `tests/fixtures/plan-badref.md` — 존재하지 않는 의존 ID

검사 항목 (신규 `[25/25]`):

1. 세 픽스처에 대해 파서가 기대대로 동작하는가 (valid 통과, 나머지 2건 검출)
2. 스킬 문서 3개 지점에 고정 문구가 존재하는가
   - `--work` — gx-tdd SKILL.md, gx-dev SKILL.md, 양 phase-setup
   - `docs: [plan]` — 양 phase-complete, skill-routing.md
   - `work-id` — 양 phase-setup, 양 SKILL.md의 state.md 스키마
3. 예약 도메인 `공통`·`통합`이 context 실존 검사에서 제외된다는 문구가 존재하는가

그래프 검사(순환·의존 실존)는 `scripts/plan-lint.py`로 분리한다. 기존 `lint-consistency.sh`는 grep/sed/diff만 쓰므로 그래프 순회를 넣지 않는다. `lint-consistency.sh`가 이 스크립트를 호출한다.

번호 재부여: `[N/24]` → `[N/25]`가 되므로 `lint-consistency.sh`의 24개 echo 줄과 상단 주석 블록을 일괄 수정한다.

## 구현 순서

| 단계 | 범위 | 배포 단위 |
|------|------|-----------|
| **A** | 형식 확정 + `--work` 읽기 + 착수 기록 + 갱신 Step + 커밋 규칙 | **하나로 배포** |
| B | `gx-context` 생성 | 별도 |
| C | 린트 픽스처 + `plan-lint.py` | 별도 |

A를 쪼개면 착수 기록만 있고 완료 전이가 없어 모든 작업이 영구 `진행`으로 쌓인다. 읽기와 갱신은 한 배포 단위여야 한다.

B가 늦어져도 A만으로 기능이 성립한다 — 계획을 손으로 쓰면 파이프라인이 읽고 갱신한다.
