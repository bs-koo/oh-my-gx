# 핵심 모드 요구사항 문답 검토

이 문서는 **수정 전 분석 기록**이다. 당시 핵심 모드에는 grill-me 방식의 심화 문답 루프가 명시적으로 연결돼 있지 않았고, AC 초안 전에 중요한 미정을 발굴하고 응답에 따라 후속 질문을 이어가는 공통 계약이 약했다. 이후 사용자의 보완 요청으로 공통 문답 계약을 반영했다. 적용 결과는 [후속 검증 기록](2026-11-10-requirements-dialogue-verification.md)에 정리한다. 아래 현재 동작은 분석 당시 기준이다.

## 현재 동작

`요청·기존 문서 → ac.md → 코드 확인·plan.md → AC·계획 결합 승인 → 구현`

- [phase-requirements](../../.claude/skills/gx-tdd/phases/phase-requirements.md)의 core 분기는 오케스트레이터가 배경과 G-W-T AC를 작성하고 product-owner를 호출하지 않는다. 부족한 버그 재현 정보와 승인 시 수정 사항은 질문한다.
- [core-planning](../../.claude/skills/gx-tdd/references/core-planning.md)은 코드를 확인하고 구현을 막는 가정을 해소하도록 한다. 계획 승인만으로 제품 정책의 빈칸이 자동 발견되는 것은 아니다.
- 전체 모드의 product-owner에는 범위·정책·사용자 영향·엣지케이스·의존성 점검이 있다. 이 점검이 core의 AC 작성 전 공통 문답으로 연결돼 있지는 않다.
- G-W-T 검사로 테스트 가능한 형식을 확인할 수 있다. 사용자가 결정하지 않은 정책을 올바르게 알아냈다는 근거는 별도로 필요하다.

예를 들어 “로그인 재시도 제한”에 임의의 횟수·해제 시간을 넣어도 테스트 가능한 AC는 만들 수 있다. 적용 단위·제한 횟수·해제 조건이 문서나 코드로 확정돼 있지 않다면 사용자에게 확인해야 한다.

## Superpowers·grill-me와 비교

설치된 Superpowers 7.0.1은 brainstorming 안에서 접근 대안 선택·짧은/전체 설계 문서·승인을 거친다. writing-plans에도 계획 검토와 실행 방식 선택이 있다. ordinary 문답은 한 번에 한 질문과 응답에 따른 후속 질문을 지시하며, 명확한 소형 변경에는 생략 경로가 있다. 따라서 표시되는 단계 이름만으로 질문 깊이나 승인 횟수를 비교하면 실제보다 단순하게 해석할 수 있다.

지정된 로컬 설치 경로에서는 grill-me를 찾지 못했다. 작성자의 2026-11-10 공식 main에서 [grill-me](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md)는 [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)을 호출하는 진입점이다. 현재 절차는 선행 결정이 해결된 질문을 묶어 묻고, 답에 따라 다음 질문을 다시 정한다. 코드·환경에서 찾을 사실은 직접 조사하며 사용자 결정만 묻는다. 남은 질문이 해소되고 이해가 맞다고 확인하면 종료한다. 과거의 “한 번에 하나”라는 설명을 현재 원문에 그대로 적용하지 않는다. 릴리스 태그·SHA는 확인하지 않았다.

## 권장 계약

`필요한 문답 → AC → 구현 계획 → 기존 결합 승인 → 구현`

1. 현재 요청·문서·이전 답변·코드를 먼저 확인한다. 확인할 수 있는 사실을 사용자에게 다시 묻지 않는다.
2. 결과를 바꾸는 목표·적용 범위·정책·성공 조건·중요 예외의 미정을 찾는다.
3. 선행 답변이 필요한 질문부터 묻는다. 독립 질문은 실제 하네스가 허용하는 작은 묶음으로, 답에 종속되는 질문은 응답 후 이어간다.
4. 답변이 새 미정을 만들면 계속 구체화한다. 최소 질문 수나 고정 라운드 종료를 강제하지 않는다.
5. 구현에 영향을 주는 중요한 미정이 해소되면 답변을 AC와 검증 사례에 연결한다. 명확한 요청은 바로 AC로 진행한다.
6. 기존 AC·계획 결합 승인을 유지한다. 오케스트레이터가 수행하므로 추가 설계 에이전트·별도 승인 단계는 필요하지 않다.

## 종료 조건과 엣지케이스

| 상황 | 처리 제안 |
|---|---|
| 이미 구체적인 소형 수정 | 추가 질문 없이 기존 AC·계획 경로 사용 |
| 문서·코드에 답이 있음 | 근거를 확인하고 재질문 생략 |
| 정책 숫자·적용 대상·해제 조건 미정 | 추측으로 AC 확정하지 않고 질문 |
| 답변으로 새로운 예외가 드러남 | 중요한 미정이면 후속 문답 유지 |
| 이전 답변과 새 요청 충돌 | 충돌 지점만 확인하고 최신 명시적 결정을 연결 |
| 비핵심 가정을 위임받음 | 가정·근거를 기록하고 기존 결합 승인에서 함께 확인 |
| 버그 재현 부족 | 기존 재현 질문과 중복하지 않고 필요한 정보만 수집 |
| 중요한 구조·인터페이스 결정 필요 | 기존 전체 모드 전환 경계 적용 |
| 사용자 응답 대기·중단 | 구현으로 넘어가지 않고 기존 재개·승인 기록 보존 |

전체 모드의 “1회 Q&A 후 미해결 기록”도 질문 횟수와 진행 가능 여부를 분리해 읽어야 한다. 구현을 막는 미정의 종료 조건은 함께 점검할 가치가 있다. 이 분석에서는 gx-tdd 실행 지시나 승인 정책을 수정하지 않았다.
