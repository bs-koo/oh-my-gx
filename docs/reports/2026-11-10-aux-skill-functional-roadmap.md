# 보조 스킬 기능 개선 검토

기준 main: `6ef7517`. 사용자는 보조 스킬 결함 수정에 더해 기능 개선 관점의 검토도 요청했다. 기존 기능을 다시 이름 붙이거나 승인 단계를 늘리는 방식보다, 현재 기록과 검증 결과를 사용자 작업에 재사용하는 방향을 우선한다.

## 이번 구현에 포함한 기능

| 기능 | 사용자 시나리오 | 반환할 정보와 경계 | 비용 |
|---|---|---|---|
| 커밋 미리보기 | “이번 커밋에 들어갈 파일과 빠질 파일을 먼저 보여줘” | 변경 후보·현재 staged·제외 경로와 이유. 파일 내용·비밀값은 출력하지 않고 build/staging/commit도 하지 않는다. main에서도 조회할 수 있지만 커밋 허가를 뜻하지 않는다. | 작음: 인덱스 보호 helper의 읽기 결과 재사용 |
| 윤문 실행 이력/상태 | “최근 윤문 결과와 중단된 작업을 보여줘” | 실행 ID·모드/장르·산출물 존재/부분 기록/옛 형식·실제 final/summary 경로. 새 실행을 예약하거나 본문을 출력하지 않는다. 파일 존재와 검증 통과를 구분한다. | 작음: 새 run 메타데이터와 기존 디렉터리 조회 |
| 프로젝트 설정 진단 | “설정은 바꾸지 말고 프로젝트 구성을 진단해줘” | 등록된 타입·발견 루트·미등록 스택·부족한 설정. config·gitignore·승인 기록을 쓰지 않고 설치/네트워크/빌드/테스트도 실행하지 않는다. | 작음: 타입 탐색 결과 재사용 |

이 기능들은 CLI/helper의 실제 fixture와 스킬의 명시 조회 라우팅으로 검증한다. 자연어 자동 발견과 실제 앱 UI는 별도 smoke이며 정적 문구 검사만으로 성공했다고 표시하지 않는다.

## 보조 스킬별 기능 판단

gx-context·gx-tdd를 제외한 전문 스킬 13개를 기준으로 정리했다. 다음 후보는 결함 확정이나 구현 완료를 뜻하지 않는다. 기존 역할을 유지할 항목은 기능을 억지로 늘리지 않는다.

| 스킬 | 이번 결과 | 추가 기능 판단 |
|---|---|---|
| gx-commit | 파일 후보 미리보기, 제외·실패 복구 보완 | 게시한 HEAD에 연결된 검증 근거 조회를 verify·PR과 공유하는 후보 |
| gx-cross-review | 큰 diff 요약에서도 미추적 파일 보존 | 이전 지적 ID별 재확인 우선 |
| gx-red | 기존의 독립 실패 테스트 작성 역할 유지 | 기능 확장보다 assertion 실패와 환경 실패를 구별하는 현재 계약 유지 우선 |
| gx-green | 대상 외 테스트·실행 설정까지 기준선 보호 | 독립 기능 추가보다 테스트 불변·최소 구현 역할 유지 우선 |
| gx-refactor | 기존 GREEN 유지·동작 보존 역할 유지 | 정리 전후의 변경 이유·범위 비교는 후보이나, 별도 점수화·승인 단계 추가 우선순위는 낮음 |
| gx-verify | 현재 실행의 정확한 증거 재사용·미확정 차단 계약 유지 | 현재 트리와 게시한 HEAD의 검증 근거를 구분해 조회하는 공유 기능 후보 |
| gx-pull-request | 기존 PR 갱신·실패 안내 기능 유지 | 인증·push 없이 제목/본문만 확인하는 명시적 미리보기 후보. 현재 본문 생성 단계가 있다고 읽기 전용 조회 모드가 있는 것으로 세지 않음 |
| gx-humanizer | 실행 이력·부분 기록 조회와 안전본 보존 | 중단 run의 명시적 재개는 후보. 이력 조회가 자동 재개하지 않도록 분리 필요 |
| gx-lens | 읽기 전용 모델 입력·기록 경계 보완 | 정책 버전별 차이 비교는 후보. 기존 변경 영향 분석과 구분 필요 |
| gx-research | 지정 출력·실행별 근거 보존 | 기존 조사 업데이트·비교를 최우선 후보로 판단 |
| gx-setup | 등록/발견/누락 설정의 읽기 전용 진단 | 먼저 진단하고 필요한 등록만 이어가는 현재 경계로 충분. 진단을 자동 설치로 확장하지 않음 |
| gx-tech-debt | 오류·부분 결과와 정상 발견 분리 | 동일 범위의 신규/해결/유지 추세 비교 우선 |
| gx-visualize | 명시 backend 선택·출력 충돌 보완 | 두 revision의 구조 차이 비교는 후보. 현재 changed-since 갱신을 구조 비교 기능으로 다시 세지 않음 |

아래 세 후보가 기록 재사용 효과와 구현 범위가 가장 명확하다. 게시 HEAD의 검증 근거 공유는 그다음 후보이며, 기존 코드 지문·실행 로그·검증 시점과 commit 연결을 함께 설계해야 한다.

## 다음 기능의 우선순위

### 1. 조사 업데이트와 이전 결과 비교

사용자 질문은 “지난 조사 이후 바뀐 점만 알려줘”다. 현재 research는 새 결과를 작성하지만 이전 결론·출처 버전과의 차이를 구조적으로 관리하지 않는다. 기존 보고서와 새 실행의 근거를 연결하고 추가/변경/유지/재확인 필요 항목을 보여주면 조사 재사용과 후속 판단이 쉬워진다.

입력은 기존 보고서/run ID, 비교 기준일, 이번 조사 범위다. 출력에는 이전/현재 주장과 각각의 출처 발행일·확인일·대상 버전을 둔다. 오래된 결론을 새 승인으로 승격하지 않으며 검증 못한 주장은 미확인으로 남긴다. 수집·인용·비교 계약을 함께 다뤄야 하므로 비용은 중간이다.

### 2. 리뷰 지적의 재확인

사용자 질문은 “이전 리뷰의 지적이 모두 해결됐나?”다. 현재 교차 리뷰는 현재 변경을 분석하는 기능이 중심이다. 이전 발견 ID·근거·수정 후 diff를 받아 각각을 해결/잔존/범위 변경/확인 불가로 구분하고 재검증 증거를 연결하면 후속 리뷰 범위를 좁힐 수 있다.

파일이 달라졌다는 사실만으로 해결 처리하지 않는다. 과거 원문과 현재 코드가 연결되지 않으면 확인 불가로 남긴다. 지적 ID와 근거 스냅샷, 변경된 라인 연결이 필요하며 비용은 중간이다.

### 3. 기술 부채의 개선 전후 비교

사용자 질문은 “지난번보다 무엇이 줄었고 새로 생겼나?”다. 전체 점수 하나보다 동일 범위에서 신규/해결/유지/재분류/분석 불가를 보여주는 편이 개선 작업에 유용하다.

범위·규칙·도구 버전·코드 revision과 근거를 함께 보관한다. 분석하지 못한 유형을 해결로 세지 않으며 모델의 문장 차이를 새 결함으로 집계하지 않는다. 안정적인 발견 ID와 범위 일치 검사가 필요하므로 비용은 중간이다.

## 구현 순서 판단

이번에는 공통 보호·복구를 보완하고 즉시 재사용 가능한 조회 세 가지를 제공한다. 후속 기능은 조사 비교 → 리뷰 재확인 → 기술 부채 추세 순으로 추천한다. 실제 작업 빈도에 따라 순서를 조정할 수 있다. 추가 에이전트 수나 토큰·속도·정확도 개선율은 측정하지 않았으며 수치 효과를 보장하지 않는다.
