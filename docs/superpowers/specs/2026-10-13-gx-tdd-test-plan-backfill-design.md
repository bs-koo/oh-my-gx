# gx-tdd 단위테스트계획서 역보강 설계

작성일: 2026-10-13
대체 대상: `2026-10-12-gx-tdd-test-plan-link-design.md` (하한선 방식, 폐기)

## 1. 배경과 방향 전환

PR #93의 첫 설계는 gx-pm 단위테스트계획서(DE-13)를 gx-tdd의 **하한선**으로 썼다. 기능ID로 범위를 정하고, AC에 UT 태그를 달고, 완료 전에 계획서 케이스의 테스트 존재를 강제했다. 사용자 검토 결과 이 방향을 버린다.

- gx-tdd는 이전과 같이 **도메인·요구사항 단위**로 실행한다. 기능ID로 호출하는 흐름, 계획서 때문에 생기는 질문·태그·게이트는 없다.
- 계획서는 RFP 같은 원초 문서에서 만든 것이라 그대로 믿을 수 없다. 개발 중 구체화된 테스트가 더 정확하다.
- 그래서 방향을 뒤집는다: **gx-tdd가 작성한 테스트로 계획서를 역보강**하고, 실행 결과를 기입하고, 개정이력에 남긴다.

## 2. 사용자 결정

| 항목 | 결정 |
|---|---|
| 진입 | gx-tdd 흐름 변경 없음. 기능ID 진입·하한선 게이트 제거 |
| 쓰는 방식 | 작업마다 텍스트 원장에 쌓고, 산출물 낼 때 `/gx-test-plan` 한 번으로 계획서를 새 버전으로 갱신 (팀 단위 머지 충돌 회피) |
| 짝짓기 | 완료 단계에서 AI가 테스트와 기존 UT 행을 짝짓고 근거를 원장에 남김. 질문 없음. 사람은 PR의 원장 diff로 확인. 확신이 낮으면 기존 행에 붙이지 않고 신규 행 + "UT-045와 유사" 비고 |
| 계획서 경로 | gx-setup에서 묻고 `config.json` `testPlan.path`에 등록 |
| 결과 | verify 통과한 테스트만 `Pass`. Fail은 기록하지 않는다 |
| 담당자 | git 이름 → 실명 매핑(`testers.md`), 처음 보는 이름만 질문 |

## 3. 흐름

```
/gx-setup ── 계획서 있나요? ──> config.json testPlan.path
/gx-tdd (도메인·요구사항) ── setup → requirements → design → implement → review
   └ complete: verify 통과 → 인수 검증 → [Step 0.5 원장 작성] → 커밋(원장 포함) → PR
/gx-test-plan ── 원장 모음 → 계획서 갱신(보강·추가·결과·개정이력) → 원장에 "반영 v1.1" 표시
```

### 3.1 원장 작성 (gx-tdd phase-complete Step 0.5)

조건: `config.json` `testPlan.path`가 비어 있지 않고 그 파일이 있을 때만. 없으면 아무 말 없이 건너뛴다.

1. `de13.py tests --diff ${DIFF_FILE} --root ${PROJECT_ROOT} --out ${DEV_DIR}/ut-tests.json` — 이번 변경에서 추가·수정된 테스트 파일의 테스트 선언 목록(위치, 선언 줄, skip 여부).
2. `de13.py functions --plan <계획서> [--spec <기능명세서>] --out ${DEV_DIR}/ut-functions.json` — 기능ID·기능명·UT 수.
3. 오케스트레이터가 테스트 목록, AC(G-W-T), 계획서 해당 기능의 UT 행(`de13.py rows --plan --fn`)을 읽고 초안 `${DEV_DIR}/ut-draft.md`를 쓴다.
   - **기존**: 테스트가 기존 UT 행의 사전조건·입력·기대결과와 같은 동작을 검증하면 그 테스트ID에 짝짓는다. 계획서 기대결과가 모호하고 테스트 단언이 더 구체적이면 `기대결과(보강)`에 구체화한 문구를 적는다(같으면 비운다).
   - **신규**: 대응하는 행이 없는 동작은 신규 행 후보. 연계기능ID는 기능 목록에서 고른다. 고를 수 없으면 `미지정`.
   - 한 UT 행에 여러 테스트가 대응할 수 있다. 파라미터화 테스트·같은 동작의 변형은 한 행으로 묶는다.
   - skip인 테스트는 넣지 않는다.
   - `근거`에 한 줄로 짝지은 이유를 적는다.
4. `de13.py record --draft ${DEV_DIR}/ut-draft.md --plan <계획서> --root ${PROJECT_ROOT} --ledger .dev/ut-results/{slug}.md --date YYYY.MM.DD --tester <git user.name>` — 검증 후 원장에 병합.
   - 검증: 기존 행의 테스트ID가 계획서에 있음, `테스트 위치`(`경로:줄`)가 실제 테스트 파일의 테스트이며 skip이 아님, 신규 행의 필수 필드(입력·기대결과) 존재.
   - 기존 행은 계획서의 현재 행 지문을 채운다.
   - 병합: 원장에 이미 `반영` 값이 있는 행은 보존하고, 반영 전 행은 이번 초안으로 교체한다(같은 브랜치에서 complete를 다시 돌려도 중복이 생기지 않는다).
   - 실패(종료 코드 2)는 커밋을 막지 않는다. 경고 후 다음 complete에서 다시 시도.
5. 보고 한 줄: `단위테스트 원장: 기존 N건(보강 M) · 신규 K건 → .dev/ut-results/{slug}.md. 계획서 반영은 /gx-test-plan`.

원장은 `.dev` 아래라 verify 지문에 영향이 없고, 기능 커밋에 함께 들어간다.

### 3.2 원장 형식 (`.dev/ut-results/{slug}.md`)

```
# {slug} 단위테스트 원장

| 구분 | 테스트ID | 연계기능ID | 사전조건 | 입력 | 기대결과 | 사후조건 | 결과 | 수행일 | 담당자 | 테스트 위치 | 행 지문 | 근거 | 반영 |
```

- 구분: `기존` / `신규`
- 기존 행: `테스트ID` 필수, `기대결과`는 보강 문구(비면 변경 없음), 사전조건·입력·사후조건은 비운다.
- 신규 행: `테스트ID` 비움(반영 때 채번), 입력·기대결과 필수.
- 결과: `Pass`만.
- 테스트 위치: `경로:줄`, 여러 개면 `<br>`로 구분하지 않고 `, `로 구분.
- 반영: `/gx-test-plan`이 채운다. 예 `v1.1 REB-UT-170`(신규는 부여된 ID 포함), `v1.1`(기존).

### 3.3 계획서 반영 (`/gx-test-plan` → `de13.py apply`)

`apply --plan <계획서> --ledger-dir .dev/ut-results --testers .dev/ut-results/testers.md --author <실명> [--version X.Y] --report <json>`

1. 원장 전체에서 `반영`이 빈 행만 대상.
2. **기존 행**: 행 지문이 계획서 현재 행과 다르면 `재확인 필요`로 보고하고 건너뛴다(PM이 그 사이 행을 고쳤음). 같으면 결과=`Pass`, 수행일, 테스트담당자(실명)를 쓰고, `기대결과(보강)`가 있으면 기대결과 셀을 그 문구로 바꾼다. 같은 테스트ID가 여러 원장에 있으면 수행일이 가장 늦은 것을 쓴다.
3. **신규 행**: 데이터 시트 끝에 추가한다. 테스트ID는 기존 ID의 접두어·자릿수를 따라 최대 번호 +1부터 채번(`REB-UT-169` → `REB-UT-170`). 연계요구사항ID 등 원장에 없는 열은 같은 연계기능ID의 마지막 행 값을 복사하고, 의존성은 `없음`. 셀 서식은 마지막 데이터 행의 같은 열 서식을 따른다. `미지정` 기능 행은 추가하지 않고 보고한다.
4. 시트 범위 갱신: `dimension`, `autoFilter`, `_xlnm._FilterDatabase` 정의 이름, 결과 열 `dataValidation sqref`를 새 마지막 행까지 늘린다.
5. **개정이력**: `버전`·`개정일` 머리글이 있는 시트의 마지막 이력 행 다음에 한 줄 추가. 버전은 마지막 버전의 소수 자리 +1(`1.0`→`1.1`, `1.9`→`1.10`), 해석할 수 없으면 `--version` 필수. 개정일은 기존 형식(`YYYY.MM.DD`), 개정 사유 `개발 반영(gx-tdd)`, 개정 내용 `단위테스트 신규 K건 추가(REB-UT-170~176)·기대결과 보강 M건·결과 기입 Pass P건`, 작성자 `--author`, 승인자 공란. 이 시트의 범위·필터도 늘린다.
6. 반영할 것이 0건이면 파일을 쓰지 않고 개정이력도 추가하지 않는다.
7. **쓰기**: 같은 폴더의 임시 파일에 쓴 뒤 다시 읽어 검증하고 원본 자리로 교체한다. 원본이 엑셀에서 열려 교체가 실패하면 "엑셀에서 계획서를 닫고 다시 실행" 안내(종료 코드 2), 임시 파일은 지운다.
8. 성공하면 원장의 해당 행 `반영`을 채운다.
9. 매핑 없는 담당자가 있으면 아무것도 쓰지 않고 종료 코드 3.

스킬은 apply 전에 계획서가 git 추적 파일이고 커밋되지 않은 수정이 있으면 중단한다(PM 수정분과 섞임 방지). 반영 결과(계획서 + 원장 표시)는 사용자가 커밋한다.

## 4. gx-setup

새 단계 "단위테스트계획서 (선택)": 프로젝트에서 `*단위테스트계획서*.xlsx`를 찾아(`~$`, `.dev/`, 빌드 산출물 제외) 질문한다. 1개면 "등록 / 등록 안 함", 여러 개면 최근 2개 + "등록 안 함", 0개면 "경로 입력 / 없음". 등록하면 `config.json`에 `"testPlan": {"path": "<프로젝트 루트 기준 상대경로>"}`. 이미 값이 있고 파일이 있으면 유지. `.gitignore`에 `~$*.xlsx` 추가(svn은 `svn:ignore`).

## 5. 걷어내는 것 (PR #93)

setup-testplan.md, 환경 감지 8, `ut-scope`·`ut-floor.md`, UT 태그·게이트 1·2, 에이전트 4종의 UT 지시, de13 `scope`·`check`·`record`(구), 사본 export(`.dev/ut-results/export`), 관련 테스트·린트 포인터. 엑셀 읽기·셀 패치·skip 판정·행 지문은 재사용한다.
