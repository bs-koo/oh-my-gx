# PART 1
## TDD 소개

---

## TDD란 무엇인가

```
TDD는 "테스트를 먼저 쓰는 규칙"이 아니다.

설계 단위를 잘게 쪼개고,
그것이 검증 가능하게 구현되었는지 확인하는 것.
```

<br>

순서는 **수단**이고, 검증 가능한 단위로 쪼개는 것이 **목적**입니다.

순서를 지켰어도 테스트가 모의(mock)의 동작만 확인한다면 TDD를 한 것이 아닙니다.

<!--
많은 분들이 TDD를 "테스트 먼저"라는 순서 규칙으로만 기억합니다.
그러면 순서만 지키고 알맹이가 빠진 테스트가 나옵니다.
-->

---

## 3단계 루프: RED - GREEN - REFACTOR

```
반복 {
  1. RED       실패하는 테스트 작성
  2. GREEN     통과할 최소한의 코드 작성
  3. REFACTOR  구조 개선 및 리팩토링
}
```

| 단계 | 답하는 질문 |
|------|-----------|
| RED | 이 코드는 **무엇을 해야** 하는가 |
| GREEN | 그것만 하는 **가장 단순한** 방법은 무엇인가 |
| REFACTOR | 동작을 유지하면서 **더 낫게** 만들 수 있는가 |

<!--
루프 하나가 보통 2분에서 15분입니다.
길어지면 단위가 너무 큰 것이고, 쪼개야 한다는 신호입니다.
-->

---

## 목표 — TDD로 얻으려는 것

**1. 설계 단위의 크기를 강제로 줄인다**

테스트를 먼저 쓰려면 대상이 작고 격리 가능해야 합니다.
테스트가 어렵다는 것은 **설계가 잘못됐다는 신호**입니다.

<br>

**2. "됐다"의 기준을 주관에서 증거로 바꾼다**

"동작할 것 같다" → "47개 통과, 0개 실패"

<br>

> 커버리지 숫자는 목표가 아니라 결과입니다.

<!--
두 번째가 특히 중요합니다.
완료의 정의가 사람마다 다르면 팀의 품질 기준도 흔들립니다.
-->

---

## 목적 — TDD가 실제로 해결하는 문제

| 목적 | 설명 |
|------|------|
| 요구사항을 먼저 정리 | 입력·조건·기대 결과를 확정해야 테스트가 써진다 |
| 점진적 설계 유도 | 큰 덩어리를 한 번에 만들 수 없다 |
| 인터페이스가 자연스럽게 | 테스트가 첫 번째 호출자다 |
| 리팩토링이 가능해짐 | 회귀를 즉시 잡아주는 안전망 |
| 디버깅 시간 단축 | 실패 지점이 최근 한 단위로 좁혀진다 |

<!--
"모호한 요구사항은 테스트로 표현되지 않는다"가 핵심입니다.
테스트를 쓰다가 막히면 대부분 코드 문제가 아니라 요구사항 문제입니다.
-->

---

## 필요성 — 사전 테스트 vs 사후 테스트

```
사후 테스트의 질문:  "이 코드가 뭘 하고 있지?"   → 구현을 서술
사전 테스트의 질문:  "이 코드가 뭘 해야 하지?"   → 요구사항을 발견
```

<br>

같은 커버리지라도 얻는 것이 다릅니다.

- 사후 테스트는 **구현에 편향**됩니다 — 구현이 놓친 케이스는 테스트도 놓칩니다
- 구현이 잘못된 가정을 했다면, 테스트가 그 가정을 **굳혀버립니다**

<br>

> **RED를 목격하는 것 자체가 검증입니다.**
> 실패를 본 적 없는 테스트는 assertion을 지워도 통과할 수 있습니다.

<!--
마지막 문장을 강조해 주세요.
실패를 확인하지 않은 테스트는 그것이 무언가를 검증한다는 증거조차 없습니다.
-->

## 테스트 피라미드

```
        /\        E2E     느림 / 적게 / 시나리오 전체
       /  \       ──────────────────────────────
      /    \      통합     중간 / 적당히 / 컴포넌트 연결
     /      \     ──────────────────────────────
    /________\    단위     빠름 / 많이 / 순수 로직
```

| 계층 | 대상 | 환경 |
|------|------|------|
| 단위 | Entity, VO, Domain Service | 순수 JVM, 모든 의존성은 테스트 대역 |
| 통합 | Service, Facade | `@SpringBootTest`, Test DB |
| E2E | Controller → Service → DB | MockMvc, TestRestTemplate |

<!--
RGR 사이클에서 주로 도는 계층은 단위 테스트입니다.
RED-GREEN을 몇 초 안에 반복하려면 Spring 컨텍스트를 띄우면 안 됩니다.
통합과 E2E는 별도 태스크로 배치합니다.
-->

---

## 테스트 더블 — 역할과 도구를 구분하라

```kotlin
val repo = mock<UserRepository>()                    // 도구: mock()
whenever(repo.findById(1L)).thenReturn(User(...))    // 역할: Stub
verify(repo).findById(1L)                            // 역할: Mock
```

<br>

- `Stub`, `Mock`, `Spy`, `Fake` — **테스트에서의 역할**
- `mock()`, `spy()` — **객체 생성 도구**

<br>

하나의 mock 객체가 Stub 역할과 Mock 역할을 **동시에** 맡을 수 있습니다.

<!--
용어가 섞여서 쓰이는 게 혼란의 원인입니다.
"mock을 쓴다"는 말이 도구를 뜻하는지 역할을 뜻하는지 구분해서 말해야 합니다.
-->

---

## 테스트 더블 5종

| 역할 | 목적 | 사용 방식 |
|------|------|----------|
| Dummy | 자리만 채움 | 생성자에 전달 |
| Stub | 고정 응답 제공 (상태 기반) | `when().thenReturn()` |
| Mock | 호출 여부·횟수 검증 (행위 기반) | `verify(...)` |
| Spy | 진짜 객체 + 일부만 조작 | `spy()` + `doReturn()` |
| Fake | 실제처럼 동작하는 가짜 구현 | `InMemoryUserRepository` |

<br>

> **모의는 격리 도구이지 검증 대상이 아닙니다.**

<!--
Fake가 의외로 유용합니다. InMemory 저장소 하나 만들어 두면
mock 셋업 없이 테스트가 훨씬 읽기 쉬워집니다.
-->

---

## 모의 안티패턴 — 가장 흔한 실수

```kotlin
// 잘못됨 — 모의가 동작하는지를 검증할 뿐
val sender = mock<NotificationSender>()
whenever(sender.send(any())).thenReturn(true)
assertTrue(sender.send(Notice()))
```

```kotlin
// 올바름 — 모의는 격리에만, 검증 대상은 실제 서비스의 동작
val failingSender = mock<NotificationSender>()
whenever(failingSender.send(any())).thenReturn(false)
val service = NoticeService(failingSender, retryQueue)

service.notify(Notice())

assertEquals(1, retryQueue.size)   // 검증 대상: service
```

<!--
위 테스트는 모의가 있으면 통과하고 없으면 실패합니다.
우리 코드에 대해서는 아무것도 말해주지 않습니다.
-->

## 테스트 가능한 구조 — Before

```kotlin
class OrderService {
    fun completeOrder(userId: Long, productId: Long) {
        val user = UserJpaRepository().findById(userId)          // 직접 생성
        val product = ProductJpaRepository().findById(productId)

        if (product.stock <= 0) throw IllegalStateException()    // 도메인 규칙 노출
        product.stock--
        if (user.point < product.price) throw IllegalStateException()
        user.point -= product.price

        OrderRepository().save(Order(user, product))
    }
}
```

- 외부 의존성 직접 생성 → Mock/Fake로 **대체 불가**
- 도메인 로직·상태 변경·저장이 **한 곳에**
- 테스트 하나가 모든 케이스를 떠안음 → 실패 원인 추적 불가

<!--
이 코드는 테스트를 쓰려는 순간 막힙니다.
DB 없이는 한 줄도 실행할 수 없습니다.
-->

---

## 테스트 가능한 구조 — After

```kotlin
class OrderService(
    private val userReader: UserReader,          // 인터페이스 주입
    private val productReader: ProductReader,
    private val orderRepository: OrderRepository,
) {
    fun completeOrder(command: OrderCommand) {
        val user = userReader.get(command.userId)
        val product = productReader.get(command.productId)

        product.decreaseStock()    // 규칙은 도메인이 소유
        user.pay(product.price)

        orderRepository.save(Order(user, product))
    }
}
```

`UserTest` · `ProductTest` · `OrderServiceTest`로 분리 → **실패 지점이 즉시 드러남**

<!--
바뀐 건 네 가지입니다.
의존성 주입, 도메인으로 규칙 위임, 책임 단일화, 입력-상태변화-결과 구조.
-->

---

## 테스트하기 어려운 구조의 4가지 신호

| 신호 | 결과 |
|------|------|
| 내부에서 `new`로 의존 객체 생성 | 테스트 대역 대체 불가 |
| 한 함수가 너무 많은 책임 | 실패 원인 추적 불가 |
| 외부 API·DB 접근 하드코딩 | 실제 환경 없이 테스트 불가 |
| private 로직·static 남용 | 단위 테스트 불가 |

<br>

> 테스트가 어렵다면 테스트 실력의 문제가 아니라 **설계의 문제**입니다.

<!--
이 슬라이드가 파트 1의 결론입니다.
TDD는 테스트 작성 기법이 아니라 설계 피드백 장치입니다.
-->

# PART 2
## 수동으로 TDD 하기

---

## 수행 절차 5단계

```
1. 요구사항을 Given-When-Then으로 쓴다
2. AC를 2~15분짜리 태스크로 쪼갠다
3. RED       실패 테스트 작성 → 실패 확인
4. GREEN     최소 구현 → 통과 + 회귀 확인
5. REFACTOR  정리 → 테스트 재실행 → 깨지면 롤백
```

<br>

이후 실제 예시: **포인트 충전 한도 검증**

<!--
이 절차를 예제 하나로 끝까지 따라가 보겠습니다.
파트 3에서 이 절차가 그대로 자동화됩니다.
-->

---

## Step 1 — 요구사항을 G-W-T로

```
AC-3: 1회 충전 한도를 초과하면 충전이 거부된다
  Given: 1회 충전 한도가 100,000이고 잔액이 0인 유저가 있다
  When:  100,001 포인트 충전을 시도한다
  Then:  ChargeLimitExceededException이 발생하고 잔액은 0으로 유지된다
```

<br>

**금지 형태**

```
"포인트가 적절히 충전된다"        → 무엇을 assert할지 알 수 없음
"충전하면 에러가 나와야 한다"      → 어떤 에러인지, 잔액은 어떻게 되는지 불명
```

<!--
테스트로 바꿀 수 없는 요구사항은 요구사항이 아니라 희망사항입니다.
Then 절에 구체적인 값이 없으면 다시 써야 합니다.
-->

---

## Step 1 — Then 절 점검 3기준

- [ ] Given / When / Then **세 절이 모두** 있는가
- [ ] Then에 자동 검증 가능한 **구체값**이 있는가
      (응답 코드, 필드 값, 호출 횟수, 잔액)
- [ ] "올바르게", "적절히", "정상적으로"가 **없는가**

<br>

> 이 세 줄을 통과하지 못한 AC는 테스트로 옮길 수 없습니다.

<!--
현업에서 가장 많이 걸리는 게 세 번째입니다.
"정상적으로 처리된다"는 문장은 검증 기준이 아닙니다.
-->

---

## Step 2 — 태스크 분해

| # | AC | 컴포넌트 | RED | GREEN |
|---|-----|---------|-----|-------|
| T1 | AC-1 | User | `shouldStartWithZeroPoint` | 생성자 + point |
| T2 | AC-2 | User | `shouldIncreaseBalanceOnCharge` | `charge()` |
| T3 | AC-3 | User | `shouldRejectChargeOverLimit` | 한도 검증 분기 |
| T4 | AC-1,2 | UserService | `UserServiceTest` (Fake) | register / charge |
| T5 | AC-4 | Controller | `UserControllerE2ETest` | 예외 → 404 |

<br>

기준: **단일 AC 또는 단일 컴포넌트** / **2~15분** / **파일 충돌 없음**

<!--
한 태스크가 15분을 넘으면 쪼개야 합니다.
쪼갤 수 없다면 설계가 덩어리져 있다는 뜻입니다.
-->

---

## Step 3 — RED

```kotlin
@Test
fun `1회 충전 한도를 초과하면 예외가 발생하고 잔액은 유지된다`() {
    val user = User(id = 1L, point = 0)

    assertThrows<ChargeLimitExceededException> {
        user.charge(100_001)
    }
    assertEquals(0, user.point)
}
```

```
$ ./gradlew test
> Unresolved reference: ChargeLimitExceededException
> FAILED
```

**실패를 눈으로 확인하는 것까지가 RED입니다.**

<!--
컴파일 실패도 정당한 RED입니다.
여기서 실패를 확인하지 않고 넘어가면 나중에 그 테스트를 신뢰할 수 없습니다.
-->

---

## Step 4 — GREEN

```kotlin
class User(val id: Long, var point: Int) {
    fun charge(amount: Int) {
        if (amount > 100_000) throw ChargeLimitExceededException()
        point += amount
    }
}
```

- 대상 테스트 통과 확인
- 전체 테스트 실행 → **회귀 없음** 확인

<br>

**GREEN에서 하면 안 되는 것**

| 금지 | 이유 |
|------|------|
| 일일 누적 한도까지 구현 | AC에 없다 (YAGNI) |
| 로깅·검증·에러 핸들링 추가 | 다음 RED의 몫이다 |
| **테스트 수정** | 요구사항을 구현에 맞추는 행위 |

## Step 5 — REFACTOR

```kotlin
class User(val id: Long, var point: Int) {
    companion object {
        const val MAX_CHARGE_PER_REQUEST = 100_000
    }

    fun charge(amount: Int) {
        if (amount > MAX_CHARGE_PER_REQUEST) throw ChargeLimitExceededException()
        point += amount
    }
}
```

| 허용 | 금지 |
|------|------|
| 중복 제거, 네이밍, 매직넘버 상수화, 구조 정리 | 동작 변경, 기능 추가, 시그니처 변경, 성능 최적화 |

**정리 1건 → 테스트 실행 → 통과하면 다음, 깨지면 즉시 롤백**

## 좋은 테스트의 3기준

**1. 하나의 동작만 검증한다**
테스트 이름에 "그리고"가 필요하면 나눕니다

**2. 이름이 검증 대상을 설명한다**
`test1()` → `shouldRejectChargeOverLimit()`

**3. 실제 코드를 우선하고, 모의는 불가피할 때만**
느리거나 외부에 의존하는 부분만 대체합니다

## 그런데 — 수동 TDD의 진짜 문제

절차를 몰라서 못 하는 게 아닙니다. **지속되지 않습니다.**

| 상황 | 실제로 벌어지는 일 |
|------|-----------------|
| 일정이 급함 | "이번 한 번만" → 첫 예외가 규칙이 됨 |

## 전체 파이프라인

```

   ↓
```

## 3대 Iron Law

```
1. NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
   실패 테스트 없이 프로덕션 코드 작성 금지

2. NO PHASE SKIPPING WITHOUT AN EXPLICIT ESCAPE
   명시적 탈출구 외에 Phase 건너뛰기 금지

3. NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
   신선한 검증 증거 없이 완료 주장 금지
```

| 위반 | 조치 |
|------|------|
| Iron Law 1 | 작성된 코드 삭제 후 RED부터 재시작 |
| Iron Law 2 | 건너뛴 Phase부터 재실행 |
| Iron Law 3 | verify 게이트로 복귀 |

<!--
우선순위는 1 → 3 → 2입니다. 코드 우선 작성이 가장 심각합니다.
-->

## 게이트 5개

| # | 게이트 | 통과 조건 |
|---|-------|----------|
| 1 | G-W-T | 모든 AC가 Given-When-Then 형식 |
| 2 | testability | score >= 7 (test-architect 평가) |
| 3 | 기준선 | 기존 테스트 GREEN + 경고 수 기록 |

## 정리

**PART 1 — TDD는 테스트 기법이 아니라 설계 피드백 장치입니다**
