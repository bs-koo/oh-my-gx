# oh-my-gx 개발자 가이드

GX 사업본부 개발자를 위한 배포용 가이드. 설치부터 첫 PR까지 다룹니다.

- 대상: 개발자 (git·터미널·빌드 도구에 익숙한 독자)
- 기준 버전: v1.19.1
- 최종 수정: 2026-07-30

> 이 문서는 "설치하고 쓰기 시작하는 것"이 목적입니다. 내부 동작 원리(에이전트 디스패치 방식, Phase 실행 루프, 상태 계약)는 `docs/guide.md`를, 상황별 프롬프트 모음은 `docs/prompt-examples.md`를 참고하세요.

## 1. 한 장 요약

**무엇인가.** Claude Code 플러그인입니다. 자연어 한 줄로 요구사항 정리(PRD) → 기술 설계 → 구현 → 리뷰 → 커밋 → PR 생성까지의 개발 사이클을 직무별 에이전트 팀이 나눠 처리합니다.

**구성.** 스킬 17종 + 에이전트 17종. 스킬은 사용자가 부르는 진입점이고, 에이전트는 스킬이 내부적으로 부르는 관점 담당자입니다. 에이전트 하나는 관점 하나만 맡습니다 — 설계자는 설계만, 비판자는 비판만, 리뷰어는 리뷰만 합니다.

**명령어를 외울 필요가 없습니다.** "결제 한도 변경 기능 만들어줘"라고 말하면 적절한 스킬로 라우팅됩니다. 슬래시 명령은 정확히 지정하고 싶을 때 쓰는 수단입니다.

**시작하는 3줄.**

```
/plugin marketplace add bs-koo/oh-my-gx
/plugin install oh-my-gx@oh-my-gx
/gx-setup
```

**이 문서를 다 읽고 나면** 도메인 지식을 등록하고, 작은 변경 1건을 PR까지 올릴 수 있습니다.

## 2. 하는 일과 하지 않는 일

| 한다 | 하지 않는다 |
|---|---|
| 모호한 요청을 Q&A로 다듬어 PRD 작성 | 사용자 승인 없이 구현 진입 |
| 기술 설계 + 설계 비판 검토 | PR 머지 (사람이 직접) |
| 코드 구현 + 자기점검 | 강제 푸시 (`git push --force` 차단) |
| 리뷰 2~3관점 (스펙 충족·코드 품질·보안) | 보호 브랜치(main/master/develop) 직접 커밋 |
| 테스트 실행 증거 확인 후 완료 판정 | SVN 커밋 대행 (사용자가 터미널에서 직접) |
| 컨벤션에 맞는 커밋 메시지·PR 본문 생성 | 민감 파일을 조용히 커밋 |
| 도메인 지식을 `context/`에 축적·재사용 | |

**승인 게이트는 4곳입니다.** PRD 승인 → 설계 승인 → 리뷰 결과 확인 → 인수 검증. 각 지점에서 선택형 또는 자유입력 질문을 받습니다. 자동화는 PR 생성까지이고, 머지는 사람의 판단입니다.

## 3. 설치

### 3.1 사전 요구사항

| 항목 | 필요 여부 | 확인 방법 | 비고 |
|---|---|---|---|
| Claude Code CLI | 필수 | `claude --version` | 플러그인 실행 환경 |
| git 또는 svn | 필수 | `git --version` | 둘 다 지원. `/gx-setup`이 자동 감지 |
| gh CLI | GitHub PR 사용 시 필수 | `gh --version` | 미설치 시 `/gx-setup`이 설치를 안내 |
| JDK 또는 Node.js | 프로젝트 스택에 따라 | `java -version` / `node -v` | 빌드·테스트 게이트 실행에 필요 |
| Claude 요금제 | 필수 | — | Max는 표준 프로파일, Pro는 에코 프로파일 권장 (6장) |

지원 환경: Windows / macOS / Linux, Git / SVN, Java(Spring Boot·Gradle) / Node.js.

### 3.2 설치

프로젝트 루트에서 Claude Code를 실행한 뒤:

```
/plugin marketplace add bs-koo/oh-my-gx
/plugin install oh-my-gx@oh-my-gx
```

업데이트는 `/plugin marketplace update oh-my-gx`입니다.

### 3.3 `/gx-setup` — 반드시 직접 입력

```
/gx-setup
```

> **주의**: 이 스킬은 자연어로 호출되지 않도록 설정되어 있습니다(`disable-model-invocation`). "초기 설정 해줘"라고 말해도 실행되지 않으므로, **슬래시 명령을 직접 입력**해야 합니다.

6단계를 순서대로 진행하며, 각 단계 결과를 보고합니다.

| 단계 | 내용 | 결과 |
|---|---|---|
| 0 | VCS 감지 | git / svn 판별 후 `config.json`의 `vcs`에 기록 |
| 1 | 필수 도구 확인 | gh CLI, JDK 확인. 미설치 시 OS별 설치 명령 안내(winget·brew·choco·scoop) |
| 2 | 인증 | GitHub 인증 상태 확인 |
| 3 | context/ 안내 | 도메인 지식 등록 경로 안내 |
| 4 | Google Chat 알림 (선택) | 웹훅 URL 등록 — 한 명이 설정해 커밋하면 팀 전체가 PR 알림 수신 |
| 5 | 모델 프로파일 (선택) | 표준 / 에코 기본값 지정 |

완료 후 퀵스타트가 표시됩니다.

```
/gx-context {도메인}     → 도메인 지식 등록
/gx-lens {질문}          → 현행 분석 + 영향도
/gx-dev {요청}           → 전체 개발 사이클 (PRD~PR)
```

### 3.4 프로젝트 설정 확인 — `.claude/config.json`

`/gx-setup`이 생성합니다. 아래 항목만 확인하면 충분합니다.

| 키 | 기본값 | 의미 |
|---|---|---|
| `vcs` | `""` (git으로 취급) | `"git"` 또는 `"svn"` |
| `modelProfile` | `""` | `"standard"` 또는 `"eco"` (6장) |
| `conventions.branchTypes` | feat, fix, refactor, chore, docs, test, style, perf, ci | 브랜치 타입 허용 목록 |
| `conventions.branchFormat` | `{type}/{description}` | 브랜치 이름 형식 |
| `conventions.commitFormat` | `{type}: {message}` | 커밋 메시지 형식 |
| `conventions.prTitleMapping` | feat→FEATURE 등 9종 | PR 제목 타입 매핑 |
| `projectTypes` | java-spring, node | **빌드·테스트 명령 (아래 주의)** |
| `sensitiveFilePatterns` | `.env*`, `*.key`, `*.pem`, `credentials*`, `*secret*` | 커밋 시 경고할 파일 |
| `buildArtifactPatterns` | `build/`, `.gradle/`, `node_modules/`, `dist/` | tracked 상태면 `.gitignore` 보강 제안 |
| `timeouts` | build 300초, network 120초, install 300초 | 명령 타임아웃 |
| `notifications.googleChat` | 비활성 | PR 생성 시 Chat 알림 |

> **중요 — 지원 스택 확인.** 기본 `projectTypes`에는 Gradle 기반 Java와 Node.js 2종만 정의되어 있습니다. Maven·Python 등 다른 스택은 여기에 등록하지 않으면 빌드·테스트 게이트가 실행 명령을 찾지 못해 검증 단계에서 막힙니다.

```json
"projectTypes": {
  "java-maven": {
    "detect": ["pom.xml"],
    "build": "mvn -q compile",
    "test": "mvn -q test"
  }
}
```

`detect`의 파일이 프로젝트 루트에 있으면 해당 타입으로 감지되고, `build`·`test` 명령이 게이트에서 그대로 실행됩니다.

## 4. 첫 30분 — 첫 PR까지

작은 변경 1건을 끝까지 통과시켜 보는 것이 가장 빠른 학습입니다. 아래 순서를 그대로 따라가세요.

| 단계 | 할 일 | 발화 예시 | 소요 | 확인 포인트 |
|---|---|---|---|---|
| 1 | 작업 브랜치 생성 | `git checkout -b feat/notification-threshold` | 1분 | **파일을 고치기 전에** 만들어야 함 |
| 2 | 도메인 지식 등록 | `/gx-context` (인자 없이) | 5~10분 | 코드베이스를 스캔해 도메인 초안을 만들고 검토를 요청함 |
| 3 | 현행 정책 파악 | `/gx-lens 알림 임계값 정책 확인해줘` | 3분 | 어디에 무슨 정책이 구현돼 있는지 보고서로 확인 |
| 4 | 작은 변경 구현 | `알림 임계값 설정값 변경, 가볍게 해줘` | 10분 | "가볍게"가 핵심 모드를 트리거함 — AC 확인 → 구현 → 빌드·테스트 게이트 |
| 5 | 커밋 | `커밋해줘` | 1분 | 브랜치 타입(`feat`)을 읽어 `feat: …` 메시지 생성 |
| 6 | PR 생성 | `PR 올려줘` | 2분 | `[FEATURE] …` 제목 + Background·Summary·Changes·Checklist 본문 |

**첫날 하지 말 것.**

- 전체 모드(`전체 과정 진행`)로 시작하지 마세요. PRD·설계 Q&A까지 포함해 30분 이상 걸립니다. 흐름을 익힌 다음에 쓰세요.
- 여러 기능을 한 번에 요청하지 마세요. 변경 범위가 커지면 리뷰·게이트에서 되돌아오는 횟수가 늘어납니다.
- PR 머지를 기대하지 마세요. 자동화는 PR 생성까지입니다.

**중간에 멈춰도 됩니다.** 진행 상태는 `.dev/{브랜치명}/state.md`에 저장됩니다. "이어서 해줘"라고 말하면 멈춘 단계부터 재개하고, "지금 어디까지 됐어?"로 현황을 볼 수 있습니다.

## 5. 스킬 17종

각 스킬은 자연어로도, 슬래시 명령으로도 부를 수 있습니다. 아래 "발화 예시"가 자연어 트리거입니다.

### 5.1 설치·기반

#### `/gx-setup` — 초기 설정

- **언제**: 플러그인 설치 직후 1회. 이후 도구·인증·알림 설정을 바꿀 때.
- **발화**: 자연어 트리거 없음. `/gx-setup`을 직접 입력.
- **산출물**: `.claude/config.json`
- **주의**: 자연어로 호출되지 않습니다(3.3 참고).

#### `/gx-context` — 도메인 지식 등록·갱신

프로젝트의 도메인 용어·아키텍처·담당자·진행 상태를 `context/`에 정리합니다. 등록해두면 이후 모든 개발 스킬이 자동으로 참조해 도메인 용어를 정확히 이해합니다.

- **발화**: "컨텍스트 등록해줘", "도메인 정리해줘", "용어 정리"
- **인자**: `[도메인명]`, `--from <파일경로>`, `--sync`
- **모드는 상황에 따라 자동 결정됩니다.**

| 상황 | 모드 | 동작 |
|---|---|---|
| `context/` 없음 + 인자 없음 | 스캔 | 코드베이스 분석 → 도메인 초안 자동 생성 |
| 도메인명 지정 | 신규 | Q&A로 새 도메인 생성 |
| `--from docs/요구사항.md` | 문서 기반 | 파일을 읽어 context 생성·갱신 |
| 기존 도메인 + 인자 없음 | 갱신 | 갱신 대상 확인 후 Q&A |
| `--sync` | 동기화 | git 히스토리·PR 분석 → `status.md` 진행도 갱신 |

- **산출물**: `context/{도메인}/`, `context/glossary.md`, `context/README.md` — **커밋해서 팀과 공유합니다** (7장)
- **없어도 동작하지만**, 등록하면 산출물 품질이 뚜렷하게 올라갑니다.

### 5.2 개발 파이프라인

#### `/gx-dev` — 전체 개발 사이클

요구사항부터 PR까지 한 흐름으로 처리합니다. 가장 많이 쓰는 스킬입니다.

- **발화**: "개발해줘", "구현해줘", "만들어줘", "기능 추가"
- **흐름**: setup → requirements(PRD) → design(설계) → implement(구현) → review(리뷰) → complete(인수·커밋·PR)
- **에이전트 9종**: product-owner(PRD·인수) / architect(설계) / design-critic(설계 비판) / coder(구현) / qa-manager(코드 리뷰·스펙 충족) / security-auditor(보안·정책 감사) / researcher(조사) / hacker·simplifier(정체 시 복구)
- **Q&A 루프**: PRD와 설계는 사용자가 승인할 때까지 질문을 반복합니다. 승인 없이 구현으로 넘어가지 않습니다.
- **주요 인자**

| 인자 | 용도 |
|---|---|
| (없음) | 진행 방식·모델 프로파일을 질문으로 확정 |
| `--phase requirements\|design\|implement\|review\|complete` | 특정 단계만 실행 |
| `--core` | 핵심 모드 (소형 변경용 경량 경로) |
| `--eco` / `--standard` | 모델 프로파일 지정 |
| `--base <branch>` | 베이스 브랜치 지정 |
| `--status` / `--resume` | 현황 조회 / 재개 |
| `--ralph` | 설계 확정 후 구현을 gx-ralph 무인 루프로 전환 (전체 모드 전용 — `--core`·`--phase`·`--resume`과 충돌 시 에러, svn은 무시) |

- **자연어로도 같은 효과**: "설계만 해줘"(`--phase design`), "리뷰만"(`--phase review`), "가볍게"·"긴급"(`--core`), "develop 브랜치 기반으로"(`--base develop`), "이어서 해줘"(`--resume`), "랄프로 … 개발해줘"(`--ralph`)
- **산출물**: `.dev/{브랜치명}/` 아래 `prd.md`·`design.md`·`state.md`·`summary.md`·`diff.txt` 등 (자동으로 `.gitignore`에 추가됨)

#### `/gx-tdd` — TDD 개발 사이클

RED-GREEN-REFACTOR 사이클과 완료 검증 게이트를 강제하는 개발 스킬입니다.

- **발화**: "TDD로 개발해줘", "테스트 먼저", "테스트 주도로"
- **흐름**: setup → requirements(PRD) → design(설계 + testability 평가) → implement(RGR 사이클) → review(스펙 → 품질 2단계) → verify(테스트 실행 증거) → complete(인수·커밋·PR)
- **에이전트 15종**. `/gx-dev`와 다른 지점만 보면:

| 에이전트 | 역할 |
|---|---|
| test-architect | 설계의 테스트 가능성 평가 + 점수 산정. 점수가 낮으면 재설계를 요청 |
| red-writer | 실패 테스트만 작성. 프로덕션 코드를 보지 않는 격리 상태로 동작 |
| green-coder | 테스트를 통과시키는 최소 코드만 작성 (YAGNI 강제) |
| refactor-coder | 테스트 통과 상태를 유지하며 정리. 동작 변경 금지 |
| spec-reviewer | AC 충족만 검증 (코드 품질은 보지 않음) |
| quality-reviewer | 코드 품질만 검증 (AC는 보지 않음) |

- **verify 게이트**: 테스트 명령을 실제로 실행해 실패 0건을 확인해야 커밋·PR로 넘어갑니다. "아마 동작할 겁니다" 같은 추측성 완료 보고가 차단됩니다.
- **인자**: `/gx-dev`와 동일한 플래그 체계(`--phase`, `--core`, `--eco`, `--base`, `--status`, `--resume`, `--ralph`)를 지원합니다.

> **`/gx-dev`와 `/gx-tdd`의 차이는 세 곳뿐입니다.**
> 1. **구현 방식** — dev는 coder가 한 번에 구현, tdd는 실패 테스트 → 최소 구현 → 정리를 사이클로 반복
> 2. **리뷰 방식** — dev는 qa-manager가 스펙·품질을 함께, tdd는 스펙과 품질을 2단계로 분리
> 3. **완료 조건** — tdd에만 테스트 실행 증거를 요구하는 verify 게이트가 있음
>
> PRD·설계·커밋·PR 절차와 `context/` 참조 방식은 동일합니다. 선택 기준은 "정답을 자동 테스트로 표현할 수 있는가"입니다 — 계산·검증·결제·인증 로직과 버그 수정은 `/gx-tdd`, UI·설정·문서 변경과 테스트 인프라가 없는 레거시는 `/gx-dev`가 적합합니다. 애매하면 어느 방식으로 갈지 물어봅니다.

#### `/gx-ralph` — 무인 반복 루프 (고급)

PRD의 수용 기준(AC)을 원장으로 변환하고, 외부 러너가 AC를 1건씩 무인으로 구현하도록 준비합니다. AC가 많고 자리를 비울 수 있을 때 쓰는 선택적 기능입니다.

- **발화**: "랄프", "루프 돌려"(직접 호출) / `/gx-dev --ralph …`·`/gx-tdd --ralph …` 또는 "랄프로 …"(파이프라인에서 전환 — 기본 경로는 묻지 않음)
- **전제**: git 프로젝트, 작업 브랜치, **PRD 확정 필수**, `projectTypes`에 테스트 명령 등록
- **실행**: 준비 후 터미널에서 `bash scripts/gx-ralph.sh` (기본 최대 10회 반복)
- **상태 확인**: `/gx-ralph --status`, `.dev/{브랜치명}/progress.txt`
- **복귀**: 루프 종료 후 `--phase review` → `--phase complete`로 리뷰·인수·PR을 대화형으로 마무리
- **제약**: SVN 미지원, 모델 프로파일(eco) 미적용 — 반복 세션 오케스트레이터 모델만 `GX_RALPH_MODEL` 환경변수로 바꿀 수 있음

> `gx-ralph-iterate`는 러너가 헤드리스로 호출하는 내부 스킬입니다. 사용자가 직접 부르지 않습니다.

### 5.3 TDD 단계별 보조 스킬

`/gx-tdd` 파이프라인 없이 한 단계씩 손으로 돌릴 때 씁니다.

| 스킬 | 발화 | 역할 | 철칙 |
|---|---|---|---|
| `/gx-red` | "RED 단계", "실패 테스트 먼저" | 실패 테스트 작성 + 실패 확인 | 프로덕션 코드 작성 금지 |
| `/gx-green` | "테스트 통과시켜", "최소 구현" | 통과하는 최소 코드 | 과잉 구현 차단 (요청 안 한 기능·에러 처리 금지) |
| `/gx-refactor` | "리팩터 단계", "중복 제거 정리" | 통과 상태 유지하며 정리 | 동작 변경 금지. 테스트가 깨지면 즉시 롤백 |
| `/gx-verify` | "완료 검증", "verify 게이트" | 테스트·빌드 직접 실행 + 실패 0건 확인 | 실행 증거 없는 완료 주장 차단 |

### 5.4 커밋과 PR

#### `/gx-commit` — 커밋

- **발화**: "커밋해줘", "commit"
- **인자**: `[커밋 메시지]` (생략 시 변경 내용에서 생성)
- **동작**: 브랜치명에서 타입 파싱(`feat/…` → `feat`) → `{type}: 메시지` 생성 → 민감 파일·빌드 아티팩트 검사 → 커밋 → context 동기화 필요 여부 확인
- **주의**: SVN 프로젝트에서는 동작하지 않습니다. 터미널에서 `svn commit`을 직접 실행하세요.

#### `/gx-pull-request` — PR 생성

- **발화**: "PR 올려줘", "풀리퀘"
- **인자**: `[base-branch]` (생략 시 자동 감지)
- **동작**: 커밋 히스토리 분석 → 타입 매핑으로 제목 생성(`feat` → `[FEATURE]`) → 본문 4섹션(Background·Summary·Changes·Checklist) 작성 → PR 생성 → Chat 알림(설정 시)
- **체이닝**: "커밋하고 PR 올려줘"라고 하면 커밋 성공 후 PR로 이어집니다.

### 5.5 분석 (읽기 전용 — 코드를 고치지 않음)

#### `/gx-lens` — 정책 탐지와 영향도 분석

코드에 흩어진 현행 비즈니스 정책을 찾아 정리하고, 변경 아이디어의 영향도를 분석합니다.

- **발화**: "정책 확인", "영향도 분석"
- **인자**: `<자연어 쿼리>`, `--detail`(상세 보고서), `--idea "<아이디어>"`(영향도 분석까지 자동 진행)
- **동작**: 키워드 추출 → 정책 구현 탐색 → 정책 보고서 → (아이디어가 있으면) architect·security-auditor 병렬 분석으로 복잡도·리스크 보고
- **용도**: 코드를 고치기 전에 "지금 어떻게 돼 있는지"를 파악할 때. 인수인계·영향도 산정에 유용합니다.

#### `/gx-tech-debt` — 기술 부채 분석

- **발화**: "기술 부채 분석", "부채 확인"
- **인자**: `[도메인|경로]`, `--type code|arch|deps|test|all` (기본 `all`)
- **동작**: 4유형(코드·아키텍처·의존성·테스트)을 병렬 분석해 우선순위 로드맵을 제시. 빌드 산출물·의존성 디렉토리는 탐색에서 제외
- **용도**: 리팩토링 계획 수립, 스프린트 여유분 배정 근거

#### `/gx-research` — 외부 리서치

- **발화**: "조사해줘", "리서치", "비교해줘"
- **인자**: `<주제>`, `--output <경로>`, `--format report|comparison|summary`
- **동작**: 인터뷰로 범위를 좁힌 뒤 웹 검색을 병렬 실행. 모든 발견에 출처 URL을 명시하고, 찾지 못한 항목은 명시적으로 표시
- **산출물**: `.research/{주제}-{날짜}.md` (`.gitignore` 자동 추가)

### 5.6 검증과 문서

#### `/gx-cross-review` — 산출물 교차 검증

`/gx-dev`·`/gx-tdd`가 만든 PRD·설계서·리뷰 기록을 컨텍스트로 주입해, 구현이 산출물에 충실한지 다시 검증합니다.

- **발화**: "교차 리뷰", "교차 검증", "크로스 리뷰"
- **사용 시점**: 파이프라인 **완료 후 PR 생성 직전에 단발로**. 파이프라인 도중에 부르면 자기점검·리뷰 단계와 중복됩니다.
- **인자**: `--advisor codex|claude`, `--dev-dir <경로>`, `--base <브랜치>`, `--scope diff|stat`
- **advisor 선택**: `codex`는 다른 모델 관점까지 확보되지만 codex CLI 설치·인증이 필요합니다(`npm install -g @openai/codex` 후 `codex login`). `claude`는 추가 설치 없이 동작합니다.
- **검증 범위**: 일반 코드 품질이 아니라 AC 충족·설계 범위 이탈·신규 위험에 한정합니다.

#### `/gx-humanizer` — AI 글쓰기 흔적 교정

문서·보고서에서 AI가 쓴 듯한 문체를 자연스러운 한국어(또는 영어)로 다듬습니다. 내용·수치·인용은 건드리지 않고 문체만 바꿉니다.

- **발화**: "AI 티 빼줘", "자연스럽게 고쳐줘"
- **인자**: `<파일 경로 또는 텍스트>` (글로브 패턴, "3장만" 같은 부분 지정 가능)
- **모드 3종**

| 모드 | 동작 |
|---|---|
| audit | 패턴 감지 후 리포트만. 원문 수정 없음 |
| rewrite | 감지 + 직접 수정 (변경률 상한 적용) |
| strict | rewrite + 의미 보존 감사 + 과윤문 검토 교차 검증 |

- 8,000자를 넘는 입력은 자동으로 strict로 승급합니다.
- 심각도 P1(즉시 수정)·P2(맥락 판단)·P3(스타일)로 분류되며, 기본값은 P2까지 수정하고 P3은 리포트만 남깁니다.
- **산출물**: `.humanize/{run-id}/` 아래 단계별 파일 (`.gitignore` 권장)

## 6. 두 개의 축 — 진행 방식과 모델 프로파일

`/gx-dev`·`/gx-tdd`를 부르면 두 가지를 한 번에 묻습니다. 두 축은 서로 독립입니다.

**축 1 — 진행 방식**

| | 전체 모드 | 핵심 모드 |
|---|---|---|
| 경로 | PRD → 설계 → 구현 → 리뷰 → 인수·PR | AC 확인 → 구현 → 빌드·테스트 게이트 → 기록 → PR |
| 적합 | 새 기능, 설계 판단이 필요한 변경 | 설정값 변경, 문구 수정, 긴급 버그 수정 |
| 유지되는 것 | 전부 | 기록(`ac.md`·`summary.md`)과 빌드·테스트 게이트는 그대로 유지 |

핵심 모드도 기록과 게이트를 남깁니다 — 이 두 가지가 "그냥 프롬프팅"과의 차이입니다.

**축 2 — 모델 프로파일**

| | 표준 | 에코 |
|---|---|---|
| 에이전트 모델 | 설계·비판 검토·구현에 상위 모델 | 설계자를 제외하고 하위 모델로 하향 |
| 절차·게이트 | 동일 | **동일** (품질 게이트가 완화되지 않음) |
| 권장 요금제 | Max | Pro |

**자연어 트리거**

| 발화 | 결과 |
|---|---|
| "긴급", "핫픽스", "가볍게", "구현만", "핵심만" | 핵심 모드 |
| "에코로", "절약 모드" | 에코 프로파일 |
| "TDD로", "테스트 먼저" | `/gx-tdd` |
| "설계만", "PRD만", "리뷰만", "커밋만" | 해당 단계만 실행 |
| "이어서", "계속", "재개" | 이전 작업 재개 |
| "지금 어디까지 됐어?", "현황" | 진행 상태 조회 |

기본값을 고정하려면 `config.json`의 `modelProfile`에 `"standard"` 또는 `"eco"`를 넣으세요. 특정 실행만 바꾸려면 `--standard` / `--eco`를 씁니다.

## 7. 팀 공유 자산 — `context/` 와 `references/`

이 두 디렉토리는 **커밋해서 팀이 함께 쓰는 자산**입니다. 한 명이 등록하면 팀 전체의 산출물 품질이 올라갑니다.

### `context/` — 도메인 지식

`/gx-context`로 만들고 갱신합니다. 도메인별 용어·아키텍처·프로젝트 매핑·담당자·진행 상태가 들어갑니다. 개발 스킬이 실행될 때 관련 도메인 context를 자동으로 참조합니다.

- 여러 PM·개발자가 함께 쓰는 프로젝트라면 등록을 권장합니다.
- 코드 탐색 중 문서화되지 않은 도메인 지식이 발견되면 등록을 제안받습니다.
- 진행도는 `/gx-context {도메인} --sync`로 git 히스토리 기반 갱신이 가능합니다.

### `references/` — 외부 규격·표준

시큐어코딩 가이드, API 설계 표준, eGovFrame 규칙처럼 프로젝트가 준수해야 할 문서를 넣습니다. 설계·구현·리뷰 단계에서 자동으로 참조하고 준수 여부를 검증합니다.

기존 문서를 그대로 넣어도 동작하지만, 아래를 지키면 참조 정확도가 올라갑니다.

- 문서 상단에 요약이나 목차를 둔다 (필요한 부분만 탐색하게 됨)
- 항목에 번호나 ID(§3.2 등)를 부여한다 (설계서에서 정확히 인용됨)
- 체크리스트 형태로 쓴다 (리뷰가 항목별로 검증함)

### 커밋 정책

| 디렉토리 | 커밋 | 이유 |
|---|---|---|
| `context/` | 한다 | 팀 공유 도메인 지식 |
| `references/` | 한다 | 팀 공유 규격 문서 |
| `.dev/` | 하지 않는다 | 브랜치별 작업 산출물. 파이프라인이 `.gitignore`에 자동 추가 |
| `.research/` | 하지 않는다 | 리서치 산출물. 스킬이 `.gitignore`에 자동 추가 |
| `.humanize/` | 하지 않는다 | 윤문 중간 산출물. 미등록 시 경고를 표시 |

## 8. 자주 막히는 지점

| 증상 | 원인 | 조치 |
|---|---|---|
| "초기 설정 해줘"라고 했는데 아무 일도 안 일어남 | `/gx-setup`은 자연어 호출이 비활성화돼 있음 | 슬래시 명령 `/gx-setup`을 직접 입력 |
| 커밋이 차단됨 | main/master/develop에서 작업 중 (훅이 차단) | 작업 브랜치를 만든 뒤 다시 커밋. **파일 수정 전에** 브랜치를 만드는 습관을 권장 |
| 빌드·테스트 게이트가 명령을 못 찾음 | `projectTypes`에 프로젝트 스택이 없음 (기본은 Gradle Java·Node 2종) | `config.json`의 `projectTypes`에 `detect`·`build`·`test`를 등록 (3.4) |
| PR 생성이 403으로 실패 | gh CLI가 다른 계정으로 인증됨 | `gh auth status`로 확인 후 `gh auth switch --user <계정>` |
| PR이 자동 머지되지 않음 | 설계상 자동화는 PR 생성까지 | 머지는 직접 수행 |
| `git push --force`가 막힘 | 훅과 설정에서 차단 | 강제 푸시 대신 새 커밋으로 해결 |
| SVN에서 커밋 스킬이 동작하지 않음 | SVN은 `gx-commit`·`gx-pull-request`·`gx-ralph` 미지원 | 터미널에서 `svn commit` 직접 실행. PRD·설계·구현·리뷰는 그대로 사용 가능 |
| 토큰 소모가 크다고 느껴짐 | 표준 프로파일로 전체 모드 실행 중 | 에코 프로파일 또는 핵심 모드 사용 (6장). 게이트는 동일하게 유지됨 |
| 이전 작업이 재개되지 않음 | v1.18.0 이전 버전에서 만든 세션은 호환성이 제거됨 | 새로 시작. 진행 중이던 코드 변경은 그대로 남아 있음 |
| `--hotfix` 플래그가 동작하지 않음 | v1.18.0에서 제거됨 | 자연어 "긴급"·"핫픽스" 또는 `--core` 사용 |

**훅이 막는 것 (설정·라우팅과 무관하게 항상 동작)**

| 가드 | 동작 |
|---|---|
| G1 | 보호 브랜치(main/master/develop) 직접 커밋 차단 |
| G2 | SVN에서 Claude의 `svn commit` 실행 차단 |
| G3 | verify 게이트 미통과 상태의 커밋 시 사용자 재확인 요구 |
| G4 | `git push --force` 차단 |

**그 밖의 방어선**

- 커밋 전에 민감 파일(`.env*`, `*.key`, `*.pem`, `credentials*`, `*secret*`)이 잡히면 경고합니다.
- 빌드 아티팩트가 tracked 상태면 `.gitignore` 보강을 제안합니다.
- `/gx-tdd`의 verify 게이트는 테스트 실행 증거 없는 완료 주장을 차단합니다.
- 저장소 CI가 PR·main push마다 스킬 문서·에이전트·설정 간 정합성을 자동 검사합니다.

**사람이 하는 일**

1. PRD 승인 — 무엇을 만들지 확정
2. 설계 승인 — 어떻게 만들지 확정
3. 리뷰 결과 확인 — 지적 사항 수용 여부 판단
4. 인수 검증 확인 — 비즈니스 의도 충족 여부
5. **PR 머지**
