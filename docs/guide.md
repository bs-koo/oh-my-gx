# gx-work 사용 가이드

`/gx-work <요청>` 하나로 필요한 논의·계획·TDD 실행을 연결합니다. 직접 `/gx-context`, `/gx-tdd`, `/gx-verify`를 호출하는 숙련자 경로도 유지합니다. `gx-dev` 비TDD 개발 스킬은 제거했습니다.

## 요청 예시

```text
/gx-work 이 기획서로 결제 취소 기능 만들고 PR까지 올려줘
/gx-work 담당자 알림 기능 아이디어만 정리해줘
/gx-work 이 설계에서 빠진 부분을 찾아 계획까지만 세워줘
/gx-work W01 시작해줘
/gx-work 지금 할 수 있는 작업을 알려줘
/gx-work 아까 하던 작업 이어서 해줘
```

이해·계획·상태 요청은 읽기 전용으로 시작하고 Git 전환·stash·pull·제품 코드 작성·테스트 실행을 하지 않습니다. 계획만 요청하면 gx-work가 범위·작업 단위·AC·예상 변경 파일·테스트 의도를 대화로 제시하고 끝나며, 별도 저장 요청 없이 계획·state 파일이나 인계를 만들지 않습니다. PRD·설계 문서로 남기려면 저장을 요청하세요. 확인을 받은 뒤 gx-tdd가 읽기 전용으로 PRD·설계만 작성하고 구현은 하지 않습니다.

작업 ID는 `.dev/plan.md`의 `W01`·`W118`처럼 W와 두 자리 이상 숫자이며, 같은 ID의 행이 있을 때만 작업으로 연결합니다. “지금 할 수 있는 작업”은 작업 계획을 읽기 전용으로 확인해 선행 작업이 끝난 대기 작업만 보여줍니다.

gx-work로 개발에 들어갈 때 종료점을 묻고 PR까지를 추천합니다. 요청에 적었거나 설정 `workflowDefaults.stopAt`이 있으면 묻지 않으며, SVN은 묻지 않고 검증까지 진행합니다. 직접 gx-tdd 호출은 종료점을 묻지 않고(기본 검증) 정해지지 않은 모드·프로파일만 묻습니다. 커밋이나 PR까지 원하면 요청에 적습니다. 진행 중이거나 검증으로 끝난 작업에 “이어서 PR까지”·“커밋만”·“PR만”처럼 다른 종료점을 요청하면 종료점 변경으로 기록하고 검증을 다시 통과한 뒤 그 범위까지 이어갑니다. gx-tdd 실행 기록이 없으면 커밋·PR 스킬의 확인 절차만 수행하며 PR은 커밋이 성공한 뒤 만듭니다. `core`는 선택하는 옵션이며 TDD·검증 게이트는 유지합니다.

## 결과에 맞춰 다음 단계 선택

gx-work는 요청과 현재 상태를 보고 필요한 절차만 선택합니다. 도메인·요구사항·W작업 관리가 필요하면 gx-context, 정책·영향 파악이면 gx-lens, 외부 조사·기술 비교면 gx-research를 사용합니다. 기존 계획 조회만으로 충분하면 그 결과를 전달합니다. 모든 스킬을 순회하지 않으며 각 스킬의 읽기 전용·쓰기 범위와 명시적 선택 조건을 유지합니다.

작업 결과·불확실성과 추천 다음 단계를 보여줍니다. 다음 단계가 재조사나 문서 보완이면 그 작업까지만 수행합니다. 허가된 문서 준비 자체에는 일괄 확인을 덧붙이지 않으며, 목표·범위가 바뀌는 큰 전환은 실제 답변 후 진행합니다.

개발로 넘어가기 직전에는 범위·관련 문서/FR/W를 제시하고 **“이 작업을 gx-tdd로 구체화·개발할까요?”**와 함께 종료점·모드(전체/핵심)·프로파일(표준/에코)을 한 번에 묻습니다. 모드·프로파일은 작업 규모·위험을 근거로 추천합니다. 다음 항목은 묻지 않고 질문 본문에 한 줄로 알립니다: 요청에 이미 적은 항목, 설정 `workflowDefaults`에 값이 있는 항목("설정값으로 진행: …"), SVN의 종료점(검증), 핵심 모드의 프로파일(핵심 모드에는 에코가 낮추는 설계 비판·testability·최종 리뷰가 없습니다). 최상위 `modelProfile`은 답으로 쓰지 않고 프로파일 선택지에 "(현재 설정)"으로 표시합니다. 프로파일을 물을 때 세션 모델이 Opus·Fable처럼 상위 등급이면 질문 전에 안내합니다. 에코는 서브에이전트만 낮추므로 `/model sonnet`으로 세션을 바꾸거나 서브에이전트 구현을 고르면 절감이 커집니다. 지금 바꾸려면 질문 창을 닫고 `/model sonnet` 뒤 같은 요청을 다시 보내고, 진행 중에 바꾸려면 Esc로 멈추고 `/model sonnet` 뒤 "이어서"라고 하면 저장된 상태에서 재개합니다. `gx-tdd로 진행` / `문서·범위 보완` / `여기서 종료` 중 실제 답변을 기다립니다. 최초의 개발·PR 요청은 이 진입 질문의 답변이 아닙니다. 미응답·비동기 등록 확인은 대기이며 응답자가 없는 무인 실행은 `BLOCKED`로 종료합니다. 그 전에는 gx-tdd·setup·브랜치/worktree 변경·W착수·빌드·테스트·코드 수정·커밋을 시작하지 않습니다.

진입 후 gx-tdd가 PRD·설계·T태스크 구현계획을 확정하고, 그 계획을 보여준 뒤 현재 세션 중심(`session`) 또는 구현 서브에이전트(`subagents`, `--isolated`) 방식을 선택받습니다. 기본 방식도 RED와 필요한 리뷰는 별도 역할을 사용합니다. 같은 실행·범위의 유효한 진입 승인·계획 선택은 재사용하며 범위가 바뀌면 변경 내용을 확인합니다. 직접 gx-tdd를 호출하는 경로에는 gx-work 진입 질문을 추가하지 않습니다.

진행 중인 작업의 선택도 말로 바꿀 수 있습니다. “에코로 바꿔서 이어가”·“표준으로”는 남은 에이전트 호출부터 프로파일을 바꿉니다. “전체 모드로 해줘”는 핵심에서 전체로, 설계 전의 “핵심으로 해줘”는 전체에서 핵심으로 바꿉니다. “지금까지 한 거 커밋만”은 지금 상태 그대로 커밋할지(verify 미통과 커밋) 검증까지 마치고 커밋할지 한 번 묻습니다. “이 작업 그만둘래”는 취소 여부를 확인한 뒤 작업을 취소 상태로 바꿉니다. 기록은 남고 취소 근거는 decisions.md에 덧붙습니다. 취소 뒤의 커밋·PR에는 “verify 미통과(취소된 TDD 작업)”가 표기되며, 다시 열려면 `/gx-tdd --resume`을 사용합니다. “이어서”를 요청했거나 같은 목표·W로 다시 시작하려는데 현재 브랜치에는 이어갈 작업이 없고 다른 브랜치·워크트리에 진행 중인 작업이 있으면, 그 위치와 중단 단계를 보여주고 그 위치에서 이어갈지 묻습니다. `.claude/config.json`이나 프로젝트 타입이 없으면 진입 질문 전에 멈추고 `/gx-setup` 실행을 안내합니다.

## 핵심 모드의 계획과 승인

전체·핵심 모드는 결과·범위·정책·중요 예외를 바꾸는 미정이 해소될 때까지 질문하고, 답변에서 새 미정이 생기면 이어 묻습니다. 전체는 기존 PO가, 핵심은 오케스트레이터가 직접 수행합니다. 문서·코드·기존 답변으로 확인한 내용은 재사용하며 명확한 요청은 추가 질문 없이 진행합니다. 중요한 미정이 없어진 뒤 기존 산출물 승인을 받습니다. 문답 종료 승인을 별도로 추가하지 않습니다.

소형 변경에 핵심 모드를 고르거나 `--core`를 명시하면 gx-tdd가 `ac.md`를 작성하고 실제 코드를 확인한 뒤 `plan.md`에 변경 파일·작업 순서·의존관계·AC별 검증 방법과 가정을 정리합니다. 기본은 오케스트레이터가 직접 작성하며 구현 위치가 불명확할 때 architect를 한 번 사용합니다. AC와 계획을 함께 승인받고 실행방법을 연결한 다음 구현합니다. 문서로 종료하거나 응답을 기다리는 동안에는 구현하지 않습니다.

후속 질문에도 실제 답변이 필요합니다. 중요한 미정이 남은 상태를 질문 횟수나 과거 승인으로 넘기지 않으며, 읽기 전용 계획에서는 질문을 대화로만 주고받고 새 상태·질문 기록 파일을 만들지 않습니다. 저장을 요청한 PRD·설계 문서만 실행 폴더에 남깁니다.

같은 실행·범위·문서 지문의 유효한 승인은 재사용합니다. AC나 계획이 달라지면 변경 내용을 제시하고 다시 승인받습니다. 중요한 구조·인터페이스 결정이 필요하면 전체 모드 전환을 제안하고 실제 선택 후 정식 요구사항·설계·리뷰로 이어갑니다. 전환 중 중단돼도 기존 코드·증거와 재개 위치를 보존합니다. 종료점은 진입 질문·요청·설정으로 정한 값을 유지하며(직접 gx-tdd 호출은 `verify`) 커밋·PR은 그 범위에서 수행합니다.

AC를 추가·수정할 때는 기존 성공 케이스를 유지하고 새 케이스만 RED부터 검증합니다. 수정된 기대값은 새 케이스 ID로 연결하고 삭제된 케이스는 승인된 범위에서 은퇴시켜 이력을 남깁니다. AC가 전부 없어지면 범위 종료 확인에서 멈춥니다. 명시적인 requirements/design 단독 요청은 탐색·계획 범위로 끝나며 핵심 모드 때문에 구현으로 확장되지 않습니다.

## 문서와 계획 재사용

gx-context는 문서·대화에서 근거 있는 사실과 요구사항을 정리하고 `context/<도메인>/status.md` 원장을 보호합니다. `.dev/plan.md`는 도메인별 FR/NFR를 묶은 W작업 목록입니다. 구체 PRD·설계·T태스크 구현계획은 gx-tdd 안에서 만들며 context에서 중복 생성하지 않습니다. 계획을 다시 생성해도 진행·완료 행과 ID·AC·PR을 임의로 덮어쓰지 않습니다. 다음 작업은 선행 조건이 충족된 대기 행 중에서 안내합니다.

일반 개발은 관련 원장·작업 연결을 먼저 대조합니다. 문서가 없으면 이번 요청의 최소 FR/W만 등록하고, 이미 맞는 문서는 다시 쓰지 않습니다. 전체 context 인터뷰·재스캔은 별도 요청이나 필요가 있을 때 수행합니다. 읽기 전용·문서 금지 제한은 우선합니다. 구현 후에는 현재 AC 증거와 관련 문서 차이를 대조하고 최종 verify를 수행합니다. 일부 AC만 통과하거나 미검증이면 W작업은 완료로 바꾸지 않습니다.

기존 구체 계획이 있으면 `--from-plan <정규화 JSON>`으로 AC·파일·인터페이스·검증 방법을 재사용합니다. 계획이 없는 새 요청은 목표·문서·FR/W 포인터의 `--handoff <JSON>`만 전달하며 사전 구체 계획을 강제하지 않습니다. 인계에는 실제 TDD 진입 답변과 요청 범위의 연결을 보존합니다. 부족한 부분만 보완하고 이미 승인한 결정을 다시 인터뷰하지 않습니다. 외부 문서에 approved라고 적혀 있다는 이유로 승인됐다고 판단하지 않습니다. 기존 비TDD 상태는 보존하고 전환 범위를 명시적으로 확인합니다.

## 보조 스킬의 조회 기능

| 요청 | 확인할 내용 |
|---|---|
| `/gx-commit --preview` 또는 “커밋 대상을 먼저 보여줘” | 포함 후보·이미 담긴 파일·제외 이유. 조회 뒤 커밋하거나 파일을 새로 담지 않습니다. |
| `/gx-humanizer --history` 또는 “최근 윤문 결과를 보여줘” | 최근 실행·장르·결과 위치·산출물 존재·부분 기록·옛 형식 상태. 새 윤문을 시작하거나 원문 본문을 출력하지 않으며, 파일 존재를 검증 통과로 표시하지 않습니다. |
| `/gx-setup --inspect` 또는 “설정은 바꾸지 말고 진단해줘” | 등록된 타입·발견한 프로젝트·미등록 스택·빌드/테스트 명령 등록 여부. 명령 등록 여부는 실제 테스트 실행 성공을 뜻하지 않습니다. |

조사 업데이트 비교·리뷰 지적 재확인·기술 부채 추세의 기능 검토는 [기능 개선 검토](reports/2026-11-10-aux-skill-functional-roadmap.md)에 있습니다.

## 테스트 시간을 줄이는 설정

파이프라인은 언어 중립적입니다. 프론트엔드(JavaScript/TypeScript·Vue·React)도 실행 가능한 테스트 러너와 명령을 등록하면 같은 TDD·검증 계약을 사용합니다. 표시 스타일 대신 사용자에게 보이는 동작을 검증합니다.

예를 들어 web 프로젝트에 Vitest를 사용하고 변경 소스와 테스트 관계를 알고 있다면 설정에 다음 타입을 등록할 수 있습니다. 실제 스택의 명령과 경로로 조정합니다.

```json
{"projectTypes":{"node":{
  "detect":["package.json"],"roots":["web"],
  "test":"npx vitest run","focusedTest":"npx vitest run {files}",
  "buildOnly":"npm run build",
  "testSelection":{"mappings":[{"sources":["src/charge.ts"],"tests":["tests/charge.test.ts"]}]}
}}}
```

Python도 같은 방식으로 등록합니다. 실행 대신 수집만 하는 collect-only 명령은 검증으로 사용하지 않습니다.

```json
{"projectTypes":{"python":{"detect":["pyproject.toml"],"test": "pytest","focusedTest":"pytest {files}","buildOnly":"python -m compileall -q src"}}}
```

태스크 안에서는 해당 테스트만 실행합니다. 경계 검증은 `scripts/gx-test-plan.py`의 영향 계획을 함께 사용하고 같은 실행의 동일 증거만 재사용합니다. 실패·테스트 0건·수 미확정·코드/설정/명령/범위/로그 변경이면 다시 확인합니다. HEAD만 새 커밋으로 바뀌고 트리 내용이 같으면 검증 증거를 유지합니다.

프로젝트 타입에 `roots`, `focusedTest`, `affectedTest`, `testSelection.mappings`와 `buildOnly`를 등록할 수 있습니다. Java/Kotlin의 기본 Gradle buildOnly는 `./gradlew build -x test`입니다. 독립 프로젝트임을 확인한 경우에만 `testSelection.independent: true`로 영향 없는 프로젝트를 제외합니다. 공통 설정·의존성·미소유 경로 변경은 보수적으로 전체 검사합니다. `--full-tests`는 명시적인 전체 회귀를 요청합니다.

빌드가 custom test task까지 실행하면 그 실행을 제외하는 buildOnly를 직접 등록해야 합니다. helper가 명령의 의미를 추측해서 옵션을 덧붙이지 않습니다. SVN은 Git 증거를 재사용하지 않고 보수적인 등록 명령을 실행합니다. 구조 검사·보호 브랜치·verify 지문 게이트는 생략하지 않습니다.

`detect`에 `backend/build.gradle.kts`처럼 `/`가 들어간 값을 적으면 저장소 상대 경로로 찾고 그 파일의 디렉토리에서 명령을 실행합니다. gx-setup은 타입을 등록한 직후 테스트 계획 helper로 실제 감지되는지 확인합니다. 실행 중 감지·명령 조립에 실패하면 즉흥 명령으로 검증하지 않고 config 수정안과 함께 한 번 묻습니다. 저장소 루트 `context/` 아래 Markdown 문서는 테스트 선택에서 빼므로(코드 파일은 그대로 선택에 남습니다) 문서만 바뀌었다고 전체 테스트로 넓히지 않습니다(코드 지문에는 포함되어 같은 범위를 다시 실행합니다). 기준선에서 이미 실패하는 테스트가 있으면 `기존 실패를 알고 진행`을 고를 수 있고, 이후 검증은 그 목록 밖의 새 실패만 막으며 PR 본문에 “기존 실패 N건(이번 변경과 무관)”을 적습니다. 테스트·빌드 시간 제한은 `timeouts.build`(기본 600000ms)입니다. 전체 실행이나 오래 걸리는 명령은 시작할 때 사유·범위·지난 소요 시간을 한 줄 알리고, 상한에 가까우면 백그라운드로 실행해 완료를 기다립니다. 시간 초과는 테스트 실패와 구분해 알립니다.

## 커밋과 PR

verify를 통과하지 않은 코드(또는 통과 뒤 바뀐 코드)를 커밋하면 Claude Code의 gx-commit이 `검증 먼저` / `위험을 알고 커밋`을 한 번 묻습니다. 위험을 알고 커밋하면 그 코드에 대한 수용 기록이 남아 보호 훅과 이어지는 PR이 같은 확인을 반복하지 않으며, 수용 뒤 코드가 바뀌면 다시 묻습니다. bypassPermissions 모드에서는 스킬과 훅 모두 묻지 않고 경고한 뒤 'verify 미통과 커밋'으로 기록합니다. 베이스 브랜치 병합 커밋은 묻지 않으며, 병합 뒤 verify를 다시 통과해야 커밋·PR 게이트가 닫힙니다. Codex는 위험 수용 없이 검증을 먼저 안내하고 멈춥니다. gx-tdd는 최종 검증 전에 베이스에 새 커밋이 있으면 병합할지 묻고(일반 merge만), 병합으로 들어온 실패를 이번 변경의 실패와 나눠 보여줍니다.

main·master·develop에서 커밋을 요청하면 변경을 그대로 가지고 갈 작업 브랜치(`{type}/{설명}`)를 만들지 묻고, 답을 받은 뒤 그 브랜치에서 커밋합니다. 질문 대기·모델 호출 기록·로그·테스트 증거 같은 `.dev` 런타임 파일과 50MiB를 넘는 `.dev` 파일은 `.gitignore` 상태와 관계없이 커밋에서 뺍니다. 작업 기록을 저장소에 올리지 않으려면 설정 `devArtifacts`를 `"local"`로 두세요. `.dev/plan.md`만 커밋하고 나머지 `.dev` 변경은 뺍니다.

## 판단과 검증 결과 읽기

계획·인계·최종 결과에서는 중요한 선택의 이유와 가정, 원문 위치, 어떤 조건에서 틀릴 수 있는지 확인할 수 있습니다. 기존 설계·결정·검증 보고를 재사용하며 별도 문서를 매번 생성하지 않습니다.

팀이 Git으로 공유한 `.dev`의 PRD·설계·결정은 관련 기능·요구사항·작업 ID로 좁혀 찾습니다. 당시 원문과 후속 변경을 대조해 새 요구와 중요한 충돌이 남을 때만 유지·이번 범위에서 변경·근거 보완을 묻습니다. 문서에 명시된 결정 시각, Git 기여자와 저장 시각, 실제 응답자를 구분하며 근거 없는 이름은 붙이지 않습니다. 답변은 현재 작업의 기존 결정 기록에 출처·범위·변경 이유와 함께 연결합니다. 과거 승인 기록은 현재 개발 실행을 허가하는 답변이 아닙니다.

테스트 통과는 실행한 범위의 근거입니다. 운영 설정·배포·미실행 예외 조건은 구분해 보고하고 실제 명령·작업 경로·로그 위치를 연결합니다. 학습이 필요하면 선택 이유나 이해 확인을 요청할 수 있지만 퀴즈·추가 승인·전체 로그 출력이 필수는 아닙니다.

## 지시문과 토큰 예산

스킬은 짧은 진입 계약과 선택 단계의 참조로 나뉩니다. 모든 설명을 한 번에 읽지 않고 현재 태스크의 원문 위치·인터페이스·변경된 결정만 인계합니다. 파일 크기를 줄인 비율이 실제 토큰·비용 절감률을 의미하지는 않습니다. 20KB 진입 예산은 재첨부와 유지보수를 위한 운영 기준이며 모든 모델의 최적 프롬프트 길이라는 연구 결론이 아닙니다.

Claude와 Codex는 같은 스킬·게이트를 사용하지만 도구 호출과 자동 발견 방식은 다릅니다. 실제 설치된 역할·질문 UI·훅 신뢰는 별도 smoke로 확인해야 하며 정적 검사만으로 검증했다고 주장하지 않습니다.
