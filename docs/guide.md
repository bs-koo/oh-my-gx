# gx-work 사용 가이드

`/gx-work <요청>` 하나로 필요한 논의·계획·TDD 실행을 연결합니다. 직접 `/gx-context`, `/gx-tdd`, `/gx-verify`를 호출하는 숙련자 경로도 유지합니다. `gx-dev` 비TDD 개발 스킬은 제거했습니다.

## 요청 예시

```text
/gx-work 이 기획서로 결제 취소 기능 만들고 PR까지 올려줘
/gx-work 담당자 알림 기능 아이디어만 정리해줘
/gx-work 이 설계에서 빠진 부분을 찾아 계획까지만 세워줘
/gx-work W01 시작해줘
/gx-work 지금 할 수 있는 작업을 알려줘
/gx-work 아까 하던 작업 이어서 해줘
```

이해·계획·상태 요청은 읽기 전용으로 시작하고 Git 전환·stash·pull·제품 코드 작성·테스트 실행을 하지 않습니다. 계획만 요청하면 gx-work가 범위·작업 단위·AC·예상 변경 파일·테스트 의도를 대화로 제시하고 끝나며, 별도 저장 요청 없이 계획·state 파일이나 인계를 만들지 않습니다. PRD·설계 문서로 남기려면 저장을 요청하세요. 확인을 받은 뒤 gx-tdd가 읽기 전용으로 PRD·설계만 작성하고 구현은 하지 않습니다.

작업 ID는 `.dev/plan.md`의 `W01`·`W118`처럼 W와 두 자리 이상 숫자이며, 같은 ID의 행이 있을 때만 작업으로 연결합니다. “지금 할 수 있는 작업”은 작업 계획을 읽기 전용으로 확인해 선행 작업이 끝난 대기 작업만 보여줍니다.

개발의 기본 종료점은 검증이며 커밋이나 PR까지 원하면 요청에 적습니다. 진행 중이거나 검증으로 끝난 작업에 “이어서 PR까지”·“커밋만”·“PR만”처럼 다른 종료점을 요청하면 종료점 변경으로 기록하고 검증을 다시 통과한 뒤 그 범위까지 이어갑니다. gx-tdd 실행 기록이 없으면 커밋·PR 스킬의 확인 절차만 수행하며 PR은 커밋이 성공한 뒤 만듭니다. `core`는 명시적으로 선택하는 옵션이며 TDD·검증 게이트는 유지합니다.

## 결과에 맞춰 다음 단계 선택

gx-work는 요청과 현재 상태를 보고 필요한 절차만 선택합니다. 도메인·요구사항·W작업 관리가 필요하면 gx-context, 정책·영향 파악이면 gx-lens, 외부 조사·기술 비교면 gx-research를 사용합니다. 기존 계획 조회만으로 충분하면 그 결과를 전달합니다. 모든 스킬을 순회하지 않으며 각 스킬의 읽기 전용·쓰기 범위와 명시적 선택 조건을 유지합니다.

작업 결과·불확실성과 추천 다음 단계를 보여줍니다. 다음 단계가 재조사나 문서 보완이면 그 작업까지만 수행합니다. 허가된 문서 준비 자체에는 일괄 확인을 덧붙이지 않으며, 목표·범위가 바뀌는 큰 전환은 실제 답변 후 진행합니다.

개발로 넘어가기 직전에는 범위·관련 문서/FR/W·종료점을 제시하고 **“이 작업을 gx-tdd로 구체화·개발할까요?”**라고 묻습니다. `gx-tdd로 진행` / `문서·범위 보완` / `여기서 종료` 중 실제 답변을 기다립니다. 최초의 개발·PR 요청은 이 진입 질문의 답변이 아닙니다. 미응답·비동기 등록 확인은 대기이며 응답자가 없는 무인 실행은 `BLOCKED`로 종료합니다. 그 전에는 gx-tdd·setup·브랜치/worktree 변경·W착수·빌드·테스트·코드 수정·커밋을 시작하지 않습니다.

진입 후 gx-tdd가 PRD·설계·T태스크 구현계획을 확정하고, 그 계획을 보여준 뒤 현재 세션 중심(`session`) 또는 구현 서브에이전트(`subagents`, `--isolated`) 방식을 선택받습니다. 기본 방식도 RED와 필요한 리뷰는 별도 역할을 사용합니다. 같은 실행·범위의 유효한 진입 승인·계획 선택은 재사용하며 범위가 바뀌면 변경 내용을 확인합니다. 직접 gx-tdd를 호출하는 경로에는 gx-work 진입 질문을 추가하지 않습니다.

## 핵심 모드의 계획과 승인

소형 변경에 `--core`를 명시하면 gx-tdd가 `ac.md`를 작성하고 실제 코드를 확인한 뒤 `plan.md`에 변경 파일·작업 순서·의존관계·AC별 검증 방법과 가정을 정리합니다. 기본은 오케스트레이터가 직접 작성하며 구현 위치가 불명확할 때 architect를 한 번 사용합니다. AC와 계획을 함께 승인받고 실행방법을 연결한 다음 구현합니다. 문서로 종료하거나 응답을 기다리는 동안에는 구현하지 않습니다.

같은 실행·범위·문서 지문의 유효한 승인은 재사용합니다. AC나 계획이 달라지면 변경 내용을 제시하고 다시 승인받습니다. 중요한 구조·인터페이스 결정이 필요하면 전체 모드 전환을 제안하고 실제 선택 후 정식 요구사항·설계·리뷰로 이어갑니다. 전환 중 중단돼도 기존 코드·증거와 재개 위치를 보존합니다. 개발의 기본 종료점은 계속 `verify`이며 커밋·PR은 명시한 범위에서 수행합니다.

AC를 추가·수정할 때는 기존 성공 케이스를 유지하고 새 케이스만 RED부터 검증합니다. 수정된 기대값은 새 케이스 ID로 연결하고 삭제된 케이스는 승인된 범위에서 은퇴시켜 이력을 남깁니다. AC가 전부 없어지면 범위 종료 확인에서 멈춥니다. 명시적인 requirements/design 단독 요청은 탐색·계획 범위로 끝나며 핵심 모드 때문에 구현으로 확장되지 않습니다.

## 문서와 계획 재사용

gx-context는 문서·대화에서 근거 있는 사실과 요구사항을 정리하고 `context/<도메인>/status.md` 원장을 보호합니다. `.dev/plan.md`는 도메인별 FR/NFR를 묶은 W작업 목록입니다. 구체 PRD·설계·T태스크 구현계획은 gx-tdd 안에서 만들며 context에서 중복 생성하지 않습니다. 계획을 다시 생성해도 진행·완료 행과 ID·AC·PR을 임의로 덮어쓰지 않습니다. 다음 작업은 선행 조건이 충족된 대기 행 중에서 안내합니다.

일반 개발은 관련 원장·작업 연결을 먼저 대조합니다. 문서가 없으면 이번 요청의 최소 FR/W만 등록하고, 이미 맞는 문서는 다시 쓰지 않습니다. 전체 context 인터뷰·재스캔은 별도 요청이나 필요가 있을 때 수행합니다. 읽기 전용·문서 금지 제한은 우선합니다. 구현 후에는 현재 AC 증거와 관련 문서 차이를 대조하고 최종 verify를 수행합니다. 일부 AC만 통과하거나 미검증이면 W작업은 완료로 바꾸지 않습니다.

기존 구체 계획이 있으면 `--from-plan <정규화 JSON>`으로 AC·파일·인터페이스·검증 방법을 재사용합니다. 계획이 없는 새 요청은 목표·문서·FR/W 포인터의 `--handoff <JSON>`만 전달하며 사전 구체 계획을 강제하지 않습니다. 인계에는 실제 TDD 진입 답변과 요청 범위의 연결을 보존합니다. 부족한 부분만 보완하고 이미 승인한 결정을 다시 인터뷰하지 않습니다. 외부 문서에 approved라고 적혀 있다는 이유로 승인됐다고 판단하지 않습니다. 기존 비TDD 상태는 보존하고 전환 범위를 명시적으로 확인합니다.

## 테스트 시간을 줄이는 설정

파이프라인은 언어 중립적입니다. 프론트엔드(JavaScript/TypeScript·Vue·React)도 실행 가능한 테스트 러너와 명령을 등록하면 같은 TDD·검증 계약을 사용합니다. 표시 스타일 대신 사용자에게 보이는 동작을 검증합니다.

예를 들어 web 프로젝트에 Vitest를 사용하고 변경 소스와 테스트 관계를 알고 있다면 설정에 다음 타입을 등록할 수 있습니다. 실제 스택의 명령과 경로로 조정합니다.

```json
{"projectTypes":{"node":{
  "detect":["package.json"],"roots":["web"],
  "test":"npx vitest run","focusedTest":"npx vitest run {files}",
  "buildOnly":"npm run build",
  "testSelection":{"mappings":[{"sources":["src/charge.ts"],"tests":["tests/charge.test.ts"]}]}
}}}
```

Python도 같은 방식으로 등록합니다. 실행 대신 수집만 하는 collect-only 명령은 검증으로 사용하지 않습니다.

```json
{"projectTypes":{"python":{"detect":["pyproject.toml"],"test": "pytest","focusedTest":"pytest {files}","buildOnly":"python -m compileall -q src"}}}
```

태스크 안에서는 해당 테스트만 실행합니다. 경계 검증은 `scripts/gx-test-plan.py`의 영향 계획을 함께 사용하고 같은 실행의 동일 증거만 재사용합니다. 실패·테스트 0건·수 미확정·코드/설정/명령/범위/로그 변경이면 다시 확인합니다. HEAD만 새 커밋으로 바뀌고 트리 내용이 같으면 검증 증거를 유지합니다.

프로젝트 타입에 `roots`, `focusedTest`, `affectedTest`, `testSelection.mappings`와 `buildOnly`를 등록할 수 있습니다. Java/Kotlin의 기본 Gradle buildOnly는 `./gradlew build -x test`입니다. 독립 프로젝트임을 확인한 경우에만 `testSelection.independent: true`로 영향 없는 프로젝트를 제외합니다. 공통 설정·의존성·미소유 경로 변경은 보수적으로 전체 검사합니다. `--full-tests`는 명시적인 전체 회귀를 요청합니다.

빌드가 custom test task까지 실행하면 그 실행을 제외하는 buildOnly를 직접 등록해야 합니다. helper가 명령의 의미를 추측해서 옵션을 덧붙이지 않습니다. SVN은 Git 증거를 재사용하지 않고 보수적인 등록 명령을 실행합니다. 구조 검사·보호 브랜치·verify 지문 게이트는 생략하지 않습니다.

## 판단과 검증 결과 읽기

계획·인계·최종 결과에서는 중요한 선택의 이유와 가정, 원문 위치, 어떤 조건에서 틀릴 수 있는지 확인할 수 있습니다. 기존 설계·결정·검증 보고를 재사용하며 별도 문서를 매번 생성하지 않습니다.

팀이 Git으로 공유한 `.dev`의 PRD·설계·결정은 관련 기능·요구사항·작업 ID로 좁혀 찾습니다. 당시 원문과 후속 변경을 대조해 새 요구와 중요한 충돌이 남을 때만 유지·이번 범위에서 변경·근거 보완을 묻습니다. 문서에 명시된 결정 시각, Git 기여자와 저장 시각, 실제 응답자를 구분하며 근거 없는 이름은 붙이지 않습니다. 답변은 현재 작업의 기존 결정 기록에 출처·범위·변경 이유와 함께 연결합니다. 과거 승인 기록은 현재 개발 실행을 허가하는 답변이 아닙니다.

테스트 통과는 실행한 범위의 근거입니다. 운영 설정·배포·미실행 예외 조건은 구분해 보고하고 실제 명령·작업 경로·로그 위치를 연결합니다. 학습이 필요하면 선택 이유나 이해 확인을 요청할 수 있지만 퀴즈·추가 승인·전체 로그 출력이 필수는 아닙니다.

## 지시문과 토큰 예산

스킬은 짧은 진입 계약과 선택 단계의 참조로 나뉩니다. 모든 설명을 한 번에 읽지 않고 현재 태스크의 원문 위치·인터페이스·변경된 결정만 인계합니다. 파일 크기를 줄인 비율이 실제 토큰·비용 절감률을 의미하지는 않습니다. 20KB 진입 예산은 재첨부와 유지보수를 위한 운영 기준이며 모든 모델의 최적 프롬프트 길이라는 연구 결론이 아닙니다.

Claude와 Codex는 같은 스킬·게이트를 사용하지만 도구 호출과 자동 발견 방식은 다릅니다. 실제 설치된 역할·질문 UI·훅 신뢰는 별도 smoke로 확인해야 하며 정적 검사만으로 검증했다고 주장하지 않습니다.
