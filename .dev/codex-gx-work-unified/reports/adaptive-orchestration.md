# GX에 맞춘 총괄 스킬과 전체 개선 보고

gx-work가 목표·자료·진행 상태에 맞춰 필요한 GX 스킬을 선택하고, 결과와 다음 단계를 제안하며 실제 사용자 답변으로 진행하도록 개선했다. superpowers에서 참고한 것은 의도 파악과 단계 전환 방식이며, 도메인 문서와 구현계획의 책임은 GX의 기존 역할에 맞췄다. 플러그인 이름은 oh-my-gx다.

## 책임과 결정 시점

| 담당 | 책임 |
|---|---|
| gx-work | 의도와 상태 파악, 필요한 전문 스킬 연결, 결과/다음 단계 제안, 사용자 결정, 작업 재개 |
| gx-context | 도메인 문서·요구사항 원장·W작업 목록과 의존/진행 상태 |
| gx-tdd | PRD·설계·구체 T태스크 구현계획·RGR 구현·리뷰·최종 검증 |

gx-context의 W작업 목록은 무엇을 어떤 순서와 의존성으로 진행하는지 관리한다. 코드 변경 위치·테스트·구현 절차를 담는 구체 T태스크 계획은 gx-tdd가 작성한다. 기존 구현계획이 있으면 재사용하고, 없으면 목표·문서·FR/W 포인터를 전달해 gx-tdd가 기존 단계에서 계획을 만든다.

개발로 넘어가기 전에 범위·관련 문서/W·종료점과 남은 미정을 제시하고 “이 작업을 gx-tdd로 구체화·개발할까요?”를 묻는다. 진행/문서 보완/종료의 실제 답을 기다린다. 최초 일반 개발·PR 요청, async ack, 추천 항목은 이 답변이 아니다. context·근거 정리 자체에 포괄 승인 질문을 추가하지 않으며 의미적 충돌은 해소한다.

TDD 안에서 구체 계획을 작성하면 그 계획을 보여주고 현재 세션 중심/구현 서브에이전트/계획 문서 종료를 묻는다. 한 답으로 계획 검토와 실행방법을 함께 기록한다. 이미 방식을 명시했으면 계획 검토만 확인하고, 같은 run·계획의 유효한 선택은 재사용한다. 현재 세션 방식도 RED와 필요한 리뷰의 별도 역할은 유지하며, 서브에이전트 방식은 --isolated 구현 경로다. Ralph는 기존 명시 opt-in 경로를 유지한다.

gx-context와 gx-tdd는 계속 개별 호출할 수 있다. 직접 gx-tdd를 호출한 경우에는 gx-work의 진입 질문을 추가하지 않으며, gx-tdd 내부의 계획 검토·실행방법 확인은 유지한다.

## 요청 예시

아래는 Claude Code의 `/gx-work` 표기다. Codex에서는 `$gx-work`로 같은 요청을 전달한다. 실제 필요한 스킬은 요청과 현재 자료에 따라 달라진다.

### 기능 개발

`/gx-work 계량기 사용량 조회 결과를 엑셀로 내려받고 싶어. 기존 조회 필터와 권한 정책은 유지하고 PR까지 올려줘.`

1. 기존 문서·코드·작업 상태를 확인한다. 정책이 불분명하면 필요한 gx-lens 분석을, 외부 기술 판단이 필요하면 gx-research를 선택한다. 모든 스킬을 순회하지 않는다.
2. 필요한 도메인 문서·요구사항/W 연결만 보강하고 결과·불확실성을 보여준다.
3. 다음 개발 범위와 PR 종료점을 보여주고 TDD로 진행/문서 보완/종료를 묻는다.
4. 진행 답변 후 gx-tdd가 PRD·설계·T계획을 작성한다. 계획을 검토하고 구현 방식에 답하면 RED→GREEN→REFACTOR로 구현한다.
5. 현재 AC 실행 증거와 실제 문서 차이를 대조한 뒤 최종 verify를 수행하고, 요청한 커밋·PR까지 진행한다.

예상되는 대화는 다음과 같다. 실제 문서명·W번호·범위는 확인한 자료를 사용한다.

> **gx-work**: 기존 조회 조건과 다운로드 권한을 확인했고 관련 도메인 문서와 작업계획을 연결했습니다. 다음 범위는 엑셀 다운로드, 권한 검증, 조회 조건 재사용이며 종료점은 PR입니다. 이 범위로 gx-tdd를 진행할까요? 진행 / 문서 보완 / 여기서 종료를 선택해 주세요.
>
> **사용자**: 진행해줘.
>
> **gx-tdd**: PRD·설계와 구체 구현계획을 작성했습니다. 이 계획을 검토하고 구현 방식을 선택해 주세요. 현재 세션에서 진행 / 구현 서브에이전트로 진행 / 계획 문서까지만 정리 중 선택할 수 있습니다.
>
> **사용자**: 이 계획으로 서브에이전트 방식으로 진행해줘.

이 답변 이후 구현을 시작한다. 중간에 도메인 정책이 충돌하면 해당 결정만 확인하며, 이미 답한 내용과 같은 실행의 유효한 선택은 이어서 사용한다.

### 정책 조사

`/gx-work 현재 엑셀 다운로드 권한 정책을 확인해줘. 코드는 바꾸지 마.`

필요하면 gx-lens로 현재 정책·의도 문서·근거 위치·미확인 조건을 정리한다. 코드 수정이나 TDD로 자동 확장하지 않는다. 다음 단계가 필요하면 그 이유와 선택을 제시한다.

### 문서와 작업 분할

`/gx-work 이 요구사항을 도메인 문서와 작업계획에 정리해줘. 개발은 나중에 할게.`

gx-context로 관련 원장·W목록을 정리하고 그 결과에서 종료한다. 구체 코드 구현계획을 만들거나 TDD를 실행하지 않는다.

### 계획만 검토·재개

`/gx-work 기존 구현계획에서 빠진 부분만 검토해줘.`는 관련 계획을 검토해 전달한다. 새로운 TDD 계획 작업이 필요하면 다음 단계로 제안하고 실제 답을 받는다. 승인된 TDD 계획 전용 인계는 read-only와 실행 허가를 분리하여 탐색/문서 내용까지만 수행하고 코드·테스트·state 초기화로 넘어가지 않는다.

`/gx-work 아까 하던 작업 이어서 해줘.`는 pending 질문과 기존 run·계획·방법·검증 증거를 복원한다. 다른 새 목표를 기존 작업에 섞지 않으며 SVN에서도 state/활성 포인터가 없는 질문을 복원한다.

## 스킬별 이전과 개선

비교 기준은 최초 main 43acaee(1.37.0)와 PR #97의 최종 변경이다. 이번 후속 구현만으로 이 모든 기능이 새로 생겼다는 뜻이 아니다.

| 스킬 | 변경 성격 | 기존 | 개선 후 |
|---|---|---|---|
| gx-work | 신규 총괄 기능 | 공통 진입점 없음. 이후 초기안은 계획을 정규화해 바로 TDD에 넘김 | 필요한 스킬 선택·결과/다음 단계 제안·실제 결정·재개를 맡는 총괄. 고정 순서와 사전 구현계획 강제 제거 |
| gx-context | 기능·사용 흐름 | 도메인 문서/원장/W 자동 갱신은 이미 존재. 반복 확인과 계획 오류 보완 여지 | 근거/결정 재사용, 실제 미정만 질문, 전체 원장·W 구조 검사, 최소 변경과 ID·이력 보호. 구현계획 역할은 맡지 않음 |
| gx-tdd | 기능·사용 흐름 | PRD→설계→RGR→리뷰→검증. phase별 자료 재작성·검증 반복 가능 | 요청/기존 계획 인계 구분, 계획 검토+구현방법 선택, 승인/방법 재개, 변경 영향 검사, 문서 반영 후 최종 검증 |

| gx-ralph | 완료 연결 | PRD 기반 반복 준비/상태 기능과 명시 opt-in | 역할 유지. 루프 종료 뒤 누적 리뷰·문서 대조·최종 검증으로 연결하는 계약을 명확화 |

| gx-humanizer | 지시문 로딩 | 언어·strict·매체 설명을 긴 본문에 함께 로드 | 현재 언어/모드/문서 종류의 참조만 읽도록 분리. 의미 보존 등 기존 제약 유지 |
| gx-setup | 지시문·설정 재사용 | 프로젝트 타입·VCS 인증·알림 설명을 함께 로드 | 선택한 환경의 참조만 사용하고 이미 있는 설정을 재사용. 일상 gx-work에서 자동 호출하지 않음 |
| gx-visualize | 지시문 로딩 | 뷰별 상세 설명을 진입문에 포함 | 서비스 맵 상세는 해당 뷰에서만 로드. 명시 요청 조건과 기존 시각화 기능 유지 |
| gx-commit | 검증 재사용 | 검증/빌드 반복 가능 | 현재 트리와 일치하는 유효한 검증 근거를 공유하고 보호 브랜치·현재 지문 게이트 유지 |
| gx-pull-request | 검증·결과 인계 | PR 작성 전 검증 반복 가능 | 검증된 변경·요청 종료점과 근거를 이어받아 PR 생성. 새 PR URL은 실행 기록에 보존 |
| gx-red | 제목·설명 | 단독 RED 단계 | 역할 유지. 명시 호출 조건과 실패 테스트 작성 설명 정리 |
| gx-green | 제목·설명 | 단독 GREEN 단계 | 역할 유지. 최소 구현 목적과 RED 선행 조건 설명 정리 |
| gx-refactor | 제목·설명 | 단독 REFACTOR 단계 | 역할 유지. 동작/테스트 유지와 코드 정리 목적 설명 정리 |
| gx-research | 제목·설명 | 출처 있는 조사·비교·요약 | 기능 유지. 과업/결과 중심의 제목·호출 설명 정리 |
| gx-tech-debt | 제목·설명 | 기술 부채 진단·우선순위 | 기능 유지. 제목과 읽기 전용 진단·개선 로드맵 설명 정리 |

gx-dev는 제거했다. 그 역할을 새 실행기로 복제하지 않고 구현 실행은 gx-tdd로 통일했다. 원래 gx-dev 진행 상태는 자동 변환하지 않는다. 플러그인·스킬 제목/소개는 gx-design의 간결한 작업 중심 문체를 참고하되 브랜드는 oh-my-gx를 유지했다.

## 토큰·테스트 비용

관련 문서 절·요청/계획 포인터·현재 태스크만 인계하고 선택되지 않은 상세 참조를 상시 로드하지 않는다. 각 태스크에서는 관련 테스트를 실행하고, 완료 경계에서는 변경 영향에 따라 검증 범위를 정하며, 같은 실행의 유효한 성공 증거를 재사용한다. 따라서 전체 테스트를 태스크마다 반복하는 부담을 줄이되 공통 설정·의존성 변경이나 범위가 불명확한 경우에는 전체로 확장한다.

새로운 총괄·결정 계약은 지시문을 늘리므로 실제 순 토큰/지연/비용 절감률을 측정했다고 주장하지 않는다. 긴 프롬프트가 항상 나쁘다는 일반 법칙도 주장하지 않는다. 연구와 정적 측정은 [token-efficiency.md](token-efficiency.md)를 따른다.

## 마지막 검토와 검증

사용자가 요청한 완료 후 백그라운드 엣지 검토는 별도 읽기 전용 에이전트가 한 번 수행했다. 25개 파일에서 다음 두 문제를 발견해 수정했다. 원시 로그는 무시되는 logs/orchestration-*.log에 있다.

| 발견 | 보완 |
|---|---|
| HIGH: 계획 전용 인계의 조기 종료 안내와 필수 phase 루프가 충돌해 개발로 진입할 수 있음 | 표준 phase/state 루프 이전에 읽기 전용 인계를 분기·종료하도록 명시하고 허용 예외에도 반영 |
| MEDIUM: 저장된 최초 요청 출처 변경과 ready-for-tdd의 false 변경을 놓침 | 요청 출처를 승인 지문에 포함하고 ready-for-tdd도 재검증 시 비교 |

두 사례 모두 실패 재현을 회귀에 추가한 뒤 수정했다. 이 검증은 저장된 인계의 일관성을 확인하며, 실제 사용자 응답 사건은 하네스의 질문·답변 기록으로 확인해야 한다.

- 새 helper 회귀는 20개이며 기존 진입/배포를 포함한 54개가 마지막 보완 후 통과했다. 새 TDD gate 4개와 공개 문서 4개도 통과했다.
- Codex 통합 263개를 한 번 실행해 질문 수정 대기 문구 1건이 실패했다. 의미를 보존하며 기존 질문 대기 계약을 복원했고 해당 질문 모듈·새 게이트·helper 34개 재검사가 통과했다. 첫 전체 실행을 전체 성공으로 기록하지 않는다.
