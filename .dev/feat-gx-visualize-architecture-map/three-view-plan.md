# 세 가지 시각화와 기능 선택 화면 개선

2026-10-16 사용자 요청: 전체 시스템 구성, 메서드 변경 영향, 실제 요청 지연을 시각화하는 방식을 조사하고 우선 기능 선택 시 관련 코드만 보여주는 화면을 개선한다.

## 1. 전체 시스템 구성

시스템 경계와 실행 애플리케이션·DB·외부 시스템을 먼저 보여주고 선택한 영역의 도메인·API·코드로 확대한다. [C4의 공식 설명](https://c4model.com/diagrams)은 context/container/component/code의 확대 수준을 구분하며 필요한 수준만 쓰도록 안내한다.

현재 스캐너의 노드는 소스 코드 구조다. 실제 실행·배포 단위를 그리려면 실행 설정·배포 파일 또는 명시적인 구성 메타데이터가 추가로 필요하다. 서비스 클래스 이름만으로 독립 배포 서비스를 만들지 않는다. 기존 도메인 개요는 재사용하고 시스템 수준 메타데이터 연결을 후속 단계로 둔다.

## 2. 메서드를 바꾸면 어디에 영향이 있는가

메서드 식별자에 소유 타입과 매개변수 시그니처를 포함하고, 호출 위치·호출자·호출 대상의 역참조 색인을 저장한다. 선택 메서드를 기준으로 호출자와 영향받는 진입점 후보만 펼친다. 다형성·동적 호출·미해소 대상은 후보로 구분한다.

현재 서비스·매퍼는 클래스 노드이므로 이번 기능 선택 UI는 관련 클래스·테이블 연결을 보여준다. 특정 API가 클래스 안의 어느 메서드·SQL 분기를 실행하는지 확정하지 않는다. 메서드 분석은 Java 구문·타입 해소를 갖춘 별도 색인 단계가 필요하다. [IntelliJ의 호출 계층](https://www.jetbrains.com/help/idea/viewing-structure-and-hierarchy-of-the-source-code.html)처럼 선택한 메서드의 호출자·호출 대상만 펼치는 탐색을 목표로 한다.

## 3. 실제 요청이 어디서 느려졌는가

소스만으로는 실제 시간을 만들 수 없다. trace ID, span ID, 부모 ID, 시작·종료 시각, 서비스·operation·상태와 수집 환경·기간이 있는 실측 입력을 사용한다. [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)가 이 부모 관계와 시간 근거를 정의한다. 처음에는 선택한 trace의 가져오기 또는 [Jaeger의 조회 UI/API](https://www.jaegertracing.io/docs/2.22/architecture/) 연결로 시작한다.

서비스 안 특정 메서드 시간까지 필요하면 그 메서드의 계측이 있어야 한다. [OpenTelemetry Java 메서드 계측](https://opentelemetry.io/docs/zero-code/java/agent/annotations/)을 사용할 수 있다. 중첩·병렬 span 시간을 단순 합산해 요청 전체 시간으로 표시하지 않으며, 계측하지 않은 구간은 0ms로 채우지 않는다. 샘플 trace의 분포를 전체 요청 분포로 단정하지 않는다.

기존 `trace` 뷰는 요구사항 추적이므로 런타임 화면 이름은 ‘요청 실행·지연’으로 구분한다. 이번 변경에는 새 CLI 뷰나 계측을 넣지 않았다.

## 생성 비용을 줄이는 방향

- 현재: 로컬 스캔과 렌더러가 구조를 생성한다. 기능 선택·검색·관련 그래프 계산은 생성된 JSON을 브라우저에서 재사용해 모델을 호출하지 않는다. 도메인마다 AI에게 그림을 새로 작성시키지 않는다.
- 후속: 프로젝트 식별자·파일 해시·분석기 버전·설정으로 색인을 캐시하고, 변경 파일과 영향을 받는 심볼 해소만 갱신한다. 현재 스킬의 매 실행 전체 스캔 계약은 이번 변경에서 바꾸지 않았다.
- 메서드 설명: 사용자가 설명을 요청했을 때만 선택 메서드 주변 코드·변경 diff·관련 부분 그래프를 전달한다.
- 실측 분석: 선택한 trace를 로컬에서 정규화하고 시간·부모 관계를 계산한다. 모델에는 전체 로그 대신 필요한 span과 요약을 전달한다.
- 실제 토큰 절감률과 금액은 측정하지 않았다. 실행 로그·전체 JSON을 대화로 길게 출력하지 않고 개수·진단·산출물 경로를 요약한다.

## 이번 UI 구현

API/화면이 있는 service 도메인의 첫 화면에 기능 선택 목록과 계층별 관련 코드, 선택 노드의 파일·연결 근거를 둔다. 전체 도메인 그림과 전체 목록은 별도로 펼친다. `calls`·`requests`·`reads`·`writes`가 기본이며 타입 의존 후보는 옵션으로 포함한다. 공유 테이블·다른 API·외부 도메인을 통해 무관한 기능을 합치지 않는다. 기존 깊은 링크, 원본 IR, 분석 진단은 보존한다.

기능 선택 화면에서 발견한 연결 누락도 수정했다. `service` 경로·패키지 안 `@Component` Reader·Executor·Linker를 서비스 계층으로 포함한다. 계층 밖 유틸·무주석 지원 클래스·`@ComponentScan`은 이 규칙으로 포함하지 않으며 기존 DAO 저장소 분류를 유지한다. 실제 소스 재스캔에서 `IntakeSearchService`와 `IntakeQueryFacade`의 미해소 호출 8개가 복구됐다.

## 검증 기록

- UI 구현 후 기존 아키텍처 247건, 시각화 135건, 기능 부분 그래프 12건 통과. 추가 분류 수정 후 스캐너 정확성·기존 스캔 91건 통과. 이 두 실행 집합은 일부 중복된다.
- 새 부분 그래프는 공유 DB의 역방향 확장, 다른 API 혼입, 외부 도메인 경계, 순환, 깨진 관계, 선택적 타입 의존을 검증했다.
- 브라우저 첫 배치에서 실제 `intake`(Mermaid)와 `accessreport`(Archify)의 데스크톱·모바일 42개 검증 통과. API 선택·빈 검색·깊은 링크·중복 DOM ID·전체 그림 펼치기와 Archify 레이아웃 안정화를 확인했다.
- UI detector에서 이번 CSS·JavaScript 3개 파일의 지적 없음. Codex 리소스 동기화 검사와 저장소 일관성 린트 통과. 사용자 기존 변경의 후행 공백은 보존했다.
- 메서드 단위 영향 분석, 배포 구성 색인, 실측 trace 가져오기는 조사·설계 범위다. 새 CLI 모드나 계측을 구현한 것으로 보고하지 않는다.
- 실제 `D:/SQ/kreb-grep-2026-web` 전체 갱신 완료: 625개 노드, 1,141개 관계, 35개 도메인(Archify 17·Mermaid 18), 실패 도메인 0개. 로컬 진입점이 있는 30개 도메인에 기능 선택 화면을 적용했다.
- 둘째 브라우저 배치의 기능 탐색·보조 클래스→매퍼→테이블·깊은 링크·반응형 검증 42개 통과. 생성 진행 중 Mermaid 자산을 기다리던 전체 그림 열기 2개는 전체 생성 완료 후 별도 기능 검사에서 모두 통과했다. 최종 데스크톱·모바일 SVG 존재·너비 양수·브라우저 오류 없음 확인. 시각 확인은 두 배치로 끝냈다.
- 분류 변경에 연결된 변경 비교 18건·도메인 분할 15건도 재실행해 통과했다. 독립 리뷰에서 발견한 `@Component *Dao` 분류 우선순위 회귀를 수정했고, 리뷰어가 직접 호출로 해소를 확인했다.
