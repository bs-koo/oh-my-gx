## 2026-09-18 11:07 · archify 설치

**Q.** T5(Archify IR 변환기)는 `archify` 전역 설수가 전제입니다. 어떻게 할까요?

선택지:

- 설치하고 T5 진행 (권장) — `npx skills add tt-a1i/archify -g`로 전역 설치합니다. MIT 라이선스, Node 22 있음. 설치 후 `archify demo`로 실제 IR 스키마를 실재해야 변환기를 썰 수 있습니다 — 스키마 없이는 지어내지 않게 계획에 명시해뇨습니다. 사업부 배포 시에도 개발자마다 설치가 필요하므로 지금 실제 설치 경험을 한 번 거치는 것이 안내 문서에도 도움이 됩니다.
- T5 보류, 나중에 진행 — T4·T6·T7·T8을 먼젌 마치고 T5만 남깁니다. archify 백엔드는 사용자가 설치한 환경에서만 동작하고, 그전엔 mermaid/static 폴백으로 동작합니다. 부랑 없이 머지 가능하며 언제든 T5만 따로 실행할 수 있습니다.
- archify 포기, 폴백을 정식 경로로 — 생성기를 mermaid/static만으로 한정하고 T4·T5를 모두 드랍합니다. 사업부 개발자가 별도 설치할 것이 없어 배포가 가밡지만, archify의 검증 산출만한 그림 품질을 포기합니다. 이 경우 설계서 수용 기준 5번을 수정해야 합니다.
**→** (직접 입력) archify라는 툴 없이도 생성할 수 있지않을까?

## 2026-09-18 11:10 · 렌더 방식

**Q.** archify 없이 그림을 만드는 방법을 고를세요. (현재는 어느 경로로도 그림이 나지 않는 상황입니다)

선택지:

- 자제 SVG 렌더러 (권장) — 우리 IR은 5계지 사슬이라 계증 레이아웃이 단순합니다. 열은 역할(화단·API·서리믄·리팝지토리·테이붔), 행은 사슬로 고정해 Python으로 SVG를 직짝 찍어냅니다. 의존성 0, 오프라인 동작, 파일 수 KB, git 커밋에 부담 없으며 인쇄도 깔끔합니다. 대신 레이아웃 코드를 우리가 쓰고 상호작용(클릭·필터)은 최소한에 그칩니다.
- Mermaid JS 인라이닝 — mermaid.min.js를 플러그인에 번들링해 HTML에 집어넣습니다. 구현이 가장 적고 flowchart·sequenceDiagram을 모두 공짜로 얻지만, HTML 한 개가 ~1MB가 되어 **우리가 이 HTML을 git에 커밋하기로 정한 것과 충돌**합니다. 갱슸마다 1MB가 이력에 쌓입니다.
- Mermaid CDN 로드 — HTML은 작지만 여는 시점에 인터넷이 필요합니다. 사업부 내부리·오프라인에서 그림이 사라지고, 설계서가 명시한 "자제 포함 HTML" 원진을 어깁니다. 권하지 않지만 가장 빠릅니다.
- archify 설치해서 해결 — 원래 계획대로 archify를 전역 설치하고 T4·T5를 진행합니다. 그림 품질과 검증 영수증이 가장 좋지만, 사업부 개발자 **전원이 개별 설치**해야 하고 미설치자는 그림을 못 봅니다.

## 2026-09-18 11:12 · 렌더 주체

**Q.** 그림을 어느 주일에게 맡길까요?

선택지:

- 자제 SVG 렌더러 (권장) — 열은 역할(화면·API·서버스·리팜지토리·테이붔), 행은 사슬로 고정해 Python으로 SVG를 생산합니다. 사업부 개발자는 아무 설치도 하지 않고, 오프라인에서 동작하고, 커밋하는 HTML은 수 KB입니다. archify는 설치한 사람만 쓰는 선택 백엔드로 유지. 대가: 레이아웃 코드를 직접 쓰고(새 태스크 1개) 상호작용은 생략합니다.
- archify를 레포에 벤더링 — MIT이니 `bin/archify.mjs`와 의존을 플러그인 안에 넣어 배포합니다. 개발자 설치가 필요 없고 archify 품질을 그대로 얻지만, 남의 Node 코드가 우리 레포에 들어오고 업스트림 보안·버전 추적을 우리가 지고 가야 합니다. Node 런퇀은 여전히 필요합니다.
**→** 전역 설치 (원래 계획) — `npx skills add tt-a1i/archify -g`로 설치하고 T4·T5를 진행합니다. 그림 품질과 검증 영수증이 가장 좋고 다이어그램 5종·PNG·공유통글까지 얻지만, 사업부 개발자 전원이 개별 설치해야 하고 미설치자는 그림을 못 봅니다.
- 일단 표로 가고 그림은 보류 — 현재 정적 HTML(노드 목록·관계 표·근거 카드)로 T6~T8을 마비하고 렌더러는 다음 사이클로 넣습니다. 파이프라인·증분 갱슸·산출물 관리는 전부 동작합니다. 단, "시간적으로 판단"이라는 원래 목표는 달성되지 않은 상황으로 머문니다.

**A.** 전역 설치 (원래 계획)

## 2026-09-18 13:06 · dataflow 범위

**Q.** 데이턼 플로우를 어떤 범위로, 언제 할까요?

선택지:

**→** 테이붔 수준, 현 계획 끝난 뒤 (권장) — 기존 스캔 데이턼로 dataflow 뷰를 추가합니다 — 어느 기능이 어느 테이붔을 읽고/쓰는지, 한 요구가 어떤 테이붔을 건드리는지가 단계(stages)로 보입니다. 새 산줄 추울 필요 없어 작은 증분입니다. 현재 T5/9이니 지금 끄어들면 이미 동작하는 것의 출시가 밀립니다.
- 테이붔 수준, 지금 현 계획에 추가 — Task 10으로 집어넣어 이번에 함께 내보냅니다. 한 번에 끝나지만 T6~T9가 뒤로 밀리고, 지금 우선재인 한국어 라벨 적합(T6 2단위)보다 늦게 달립니다.
- 컴럼 수준까지 무리해봐도 좋다 — SQL에서 컴럼 생별자도 추출합니다(리터럴 값은 절대 제외). 다만 `SELECT *`·동적 `<if>` SQL에서는 부분만 나오며, 나오지 않은 곳을 "없다"과 구분해 표시해야 합니다. 그 구분을 모하면 부정한 설계도가 됩니다.
- 내가 지정하는 곳만 정밀하게 — 전체 자동 추출 대심, 사용자가 지정한 특정 기능·테이붔에 대해서만 상세 데이턼 플로우를 만듭니다. 정확도는 높지만 매번 지정해야 하고 자동 갱슸의 이점이 적습니다.

**A.** 테이붔 수준, 현 계획 끝난 뒤 (권장)

## 2026-09-18 15:06 · 그림 분할

**Q.** 실제 사업부 프로젝트(kreb-grep-2025-admin, Java 456개)에 스캐너를 돌려봤습니다. 추출은 잘 됩니다(86노드, 근거 file:line 포함). 그런데 전체를 한 장으로 그리면 archify 검증이 109건으로 실패합니다 — 대부분 연결선이 다른 박스를 관통하는 문제이고, 86노드 한 장은 사람이 읽기도 어렵습니다. 어떻게 나눌까요?

선택지:

**→** 도메인/모듈별 분할 (권장) — 모듈 하나당 한 장. 실측: code 모듈(15노드) → 검증 통과 0건, auth(7노드) → 2건, reb(32노드) → 8건. 계약에 이미 있는 --domain 플래그와 context/{도메인} 구조에 그대로 맞습니다. 대부분의 모듈이 깨끗하게 나오고 아주 큰 모듈만 남습니다
- 진입점 체인별 분할 — 화면/API 하나당 한 장(이 프로젝트면 30장). 노드가 5개 안팎이라 검증은 거의 확실히 통과하지만 장수가 많아 전체 구조 파악에는 오히려 불리합니다
- 지금 구조 유지, 큰 저장소는 폴백 수용 — 코드 변경이 가장 적습니다. 작은 모듈·소규모 저장소에서만 그림이 나오고, 큰 저장소는 정직하게 표로 떨어집니다(T8이 부재를 명시합니다). 사업부의 실제 저장소 대부분이 큰 편이면 그림을 거의 못 보게 됩니다

**A.** 도메인/모듈별 분할 (권장)
