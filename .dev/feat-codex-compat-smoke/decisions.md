## 2026-08-28 15:35 · 구현 방식

**Q.** 6시간 중 구현 구간(10:40~13:00)을 3명이 어떻게 나눌까요?

선택지:

- 순수 릴레이 (추천) — 드라이버 1명이 gx-tdd를 돌리고 교대. 충돌 0, state.md 일관, 발표 스토리 명확. 결과물 작동은 10점뿐이라 속도보다 프로세스가 이득
**→** 구현만 3분할 — 설계까지 릴레이 후 AC를 3명이 나눠 각자 구현. 산출물 양은 늘지만 각자 노트북이라 git 충돌·통합 비용이 큼
- 드라이버 + 보조 2명 — 1명이 계속 파이프라인을 돌리고 나머지는 발표자료·테스트데이터·문서. 흐름은 가장 안정적이나 2명의 git 기여가 안 남음

**A.** 구현만 3분할

## 2026-08-28 15:35 · 리허설 대상

## 2026-08-31 10:38 · 생성 주체

**Q.** plan.md의 작업 묶기·의존 판정을 어디서 할까요?

선택지:

**→** gx-context 확장 (추천) — --from으로 요구사항 읽을 때 status.md와 함께 plan.md도 생성. 이미 요구사항을 읽고 있어 재사용이 크고, 한 번 호출로 context+status+plan이 같이 나온다
- 새 스킬 /gx-plan — 계획 수립 전용 스킬. 역할이 명확하고 재수립도 독립 호출 가능. 다만 스킬이 늘고 gx-context와 요구사항 읽기가 겹친다
- 수동 작성 + 읽기만 자동 — 표 형식만 정하고 사람이 직접 작성. dev/tdd는 W-nn 읽기만 지원. 가장 빠르고 판정 품질 위험이 없다

**A.** gx-context 확장 (추천)

## 2026-08-31 10:38 · 구현 범위

**Q.** 9월 22일까지 어느 범위까지 만들까요? (3주 남았고 리허설 시간도 필요합니다)

선택지:

- 읽기 우선 (추천) — plan.md 형식 확정 + dev/tdd가 W-nn 인식해 도메인·요구사항 자동 주입. 생성과 상태 갱신은 수동. 핵심 가치를 가장 작게 확보
- 생성까지 자동 — 요구사항에서 묶음·의존을 AI가 판정해 plan.md 생성 + 읽기. 완성도는 높지만 판정 품질 검증에 리허설이 더 필요
**→** 완전 자동 — 생성 + 읽기 + 완료 시 상태 자동 갱신 + status.md 전파까지. 3주에 만들고 검증하기엔 빠듯하다

**A.** 완전 자동
